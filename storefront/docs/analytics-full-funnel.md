# Сквозная аналитика Pseudex: что измеряется и что означает результат

## Три разных слоя

1. **Публичные действия** — согласованные браузерные `reachGoal`: начало регистрации, видимые тарифы, выбор плана, успешное копирование, переходы к документации/контактам; дополнительно чтение раздела, FAQ, конфигуратор и воспроизведение инструкции. Параметры — закрытые перечисления, без текста формы, контактов, произвольных URL и ключей.
2. **Результаты аккаунта** — подтверждённая почта, выданный ключ, наблюдаемое подключение/маскирование, первая реальная оплата. Сервер передаёт их только при отдельном действующем разрешении acquisition-v1. `paid` берётся из оплаченного счёта и его `paid_at`/`total`, не из перехода на страницу успеха. Нулевые оплаченные счета не являются поступлением денег и не мешают первой положительной оплате.
3. **Внутренние бизнес-факты** — повторные платежи, удержание, квалификация проекта, приёмка агентного сценария и подтверждённые сотрудником продления/возвраты. Они не отправляются автоматически в Яндекс в рамках acquisition-v1. Отсутствие записи о возврате не означает ноль возвратов. Ручная классификация не называется подтверждением платёжного провайдера.

Каталог не равен обещанию, что каждый источник уже автоматизирован. На экране привлечения видна граница реализации. Повторный платёж не обязательно продление; `first_mask` не доказательство правильного вызова инструмента; клик Enterprise не полученная заявка.

## Разрешение и отзыв

Старое браузерное `yes` и договорное согласие при регистрации **не разрешают** серверную передачу оплаты. Новая цель обработки выбирается отдельной, изначально пустой галочкой.

Двухфазный протокол сначала выдаёт подписанный HttpOnly receipt без ClientID, затем привязывает действительный строковый ClientID из согласованного SDK и совпадающей cookie. Незаполненный receipt не разрешает экспорт. Запоздалый callback или POST не может оживить уже отозванную запись.

Новое разрешение связывается только с новым аккаунтом. Подтверждение почты само по себе не подтверждает согласие, которое мог дать другой человек при регистрации чужого адреса: на активации нужны исходный receipt и отдельная галочка владельца почты. В другом браузере автоматически связь не восстанавливается — это неизвестная атрибуция, а не повод угадывать личность.

Отзыв работает через настройки публичной аналитики и страницу `/analytics/preferences`; после выхода из аккаунта — по управленческой cookie, после входа с другого устройства — для разрешений этого пользователя. Никакого SDK на этой странице или в кабинете нет. Удаление всех данных браузера не может само уведомить сервер: остаются вход в настройки, обращение оператору и срок действия. Отзыв не удаляет уже переданные сведения из внешнего сервиса задним числом.

ClientID — псевдонимный идентификатор, не анонимные данные. Его максимальный срок здесь 21 день. Экспорт допускается до 20 дней от подтверждённого публичного касания и события, оставляя запас на обработку. Приватная активность этот срок не продлевает. Старые `Organization.source_yclid`/`Visit.yclid` не считаются согласием и не используются новым экспортёром; новая очистка не выдаётся за очистку всех исторических полей.

## Доставка и планировщик

По умолчанию обе новые настройки выключены:

```text
PSEUDEX_ACQUISITION_LINK_ENABLED=0
PSEUDEX_ACQUISITION_EXPORT_ENABLED=0
PSEUDEX_YANDEX_CONVERSIONS=0
```

Первый флаг открывает отдельное согласие, второй — серверный экспорт. Старый yclid-only экспорт с ними несовместим. Включать после проверки целей, политики, миграций и тестового прохождения; наличие OAuth само по себе ничего не включает.

Отдельный Compose-сервис `acquisition` запускает `manage.py acquisition_sync --limit 20` каждые пять минут. Он не получает ключи эквайринга/лицензирования и не блокирует бизнес-цикл. Очистка истёкших идентификаторов идёт и при выключенной отправке. Здоровье сервиса отражает успешный проход, но не доказывает сопоставление каждой конверсии.

Перед внешним POST сохраняется неопределённая запись. Повтор после таймаута или смерти процесса не отправляет файл снова. Сверка выполняется по неперсональному nonce через список загрузок. При неполной/неоднозначной сверке нужен разбор, а не автоматический повтор.

- `accepted` — Яндекс вернул корректный ID загрузки.
- `processed` — файл обработан; это не доказательство сопоставления каждой строки.
- `unknown` — результат неоднозначен, новые отправки приостановлены до сверки.
- `linkage_failure` — идентификатор не удалось связать с визитом.

Ни ClientID, ни содержимое CSV, ни контакты не выводятся в журналы. Блокировка записи разрешения упорядочивает отправку и отзыв: после подтверждённого отзыва новая отправка не начинается. Уже начатую отправку нельзя обещать «отозвать из сети».

## Экран оператора и Директ

`/{ADMIN_PATH}/ops/acquisition/` требует staff и подтверждённый второй фактор. Он показывает когорту новых аккаунтов, покрытие согласиями, доставку, удержание и чтение отчётов Директа по выбранной кампании/группе/объявлению. Формы защищены CSRF.

Отчёт Директа проверяет связь кампании с текущим счётчиком. Цели берутся по актуальным ID; запросы разбиваются по десять целей. Полные строки объединяются по стабильным ID/дате, расходы между частями не складываются. Большие ID — строки, деньги — Decimal, неизвестное — не ноль. Атрибуция явно LC, НДС включён один раз. Отчёт запрашивается оператором; отдельное автоматическое расписание его обновления здесь не обещается.

Конверсии Директа — целевые визиты, а не уникальные организации. Не выводить CAC или победителя по CTR из этих чисел без проверки покрытия, зрелости когорты и соответствия денежных окон. Расходы/бюджет, модерация и показы этим кодом не изменяются.

Удержание считается по зрелым окнам 7/14/30 дней и изменениям накопленных счётчиков. Пропуски, сбросы и недостаточные наблюдения — неизвестно. Вместе с долей активных показывается доля наблюдаемых клиентов. Проверенные квалификация/приёмка/финансовая классификация могут регистрироваться сотрудником по неперсональному коду документа; эта форма не проводит платёж, возврат или отмену.

## Вебвизор

На публичных страницах с Метрикой разрешены только HTTPS-домены интерфейса из официального списка. Caddy не перекрывает вычисленную приложением политику своим `DENY`. WebSocket/домены Вебвизора разрешены только там же. Закрытые страницы, слешless-корни кабинета/входа, активация, welcome и управление согласиями остаются `frame-ancestors 'none'`, `X-Frame-Options: DENY` и без SDK.

Это интеграция доработки Георгия, а не разрешение встраивания любому сайту. Успешная отправка целей может сосуществовать с ранее заблокированным WebSocket: нельзя объяснять нули целей одной этой ошибкой.

## Проверка перед заявлением о готовности

Локальные тесты используют временную БД, синтетические письма, подмену API и реальные браузерные действия без внешних SDK. Они не заменяют production-проверку PostgreSQL, Caddy и доставки в Метрику.

После platform-only выпуска проверить: версии и здоровье сервисов; миграции и флаги; публичные/закрытые заголовки; consent/отзыв; фактические цели в кабинете Метрики и отчётах Директа. Реальная оплата требует отдельного разрешения; нельзя создавать фиктивную боевую paid-конверсию ради зелёной проверки. Проверка на тестовом счётчике/платёжном стенде должна называться тестовой, а не доказательством реальной продажи.
