# Memory-read tripwire — «кто пытался прочитать движок» (WS-7)

Отвечает на запрос: **100% знать, кто конкретно попытался прочитать память/исходник движка.**

## Честная рамка (сначала лимиты, потом решение)

Чтение памяти движка root'ом на СВОЕЙ машине **невидимо коду внутри движка** — это операция
ядра, не заходящая в наш процесс (теорема, `research/2026-09-15-ram-extraction-hardening.md`).
Поэтому детектор работает **СНАРУЖИ** движка — привилегированным наблюдателем в его PID-неймспейсе
(или на хосте) — и ловит то, что привилегированный наблюдатель ВИДЕТЬ может, а на попытку —
**репортит вендору в реалтайм**, чтобы улика ушла с машины до того, как root затрёт локальный лог.

**Что ловит:**
- `gdb -p` / `gcore` (ptrace-attach → виден как TracerPid воркера);
- `dd if=/proc/<pid>/mem` / карвер, держащий открытый fd на `/proc/<pid>/mem` (ловится, пока
  идёт — по определению медленное — многомегабайтное чтение).
- (+ auditd-правила ниже) `process_vm_readv` — fd-less/ptrace-less чтение, слепое пятно поллера;
  `/dev/mem`, `/dev/kmem`, `/proc/kcore`.

**Чего НЕ гарантирует (не продавать как гарантию):** подготовленный root, который СНАЧАЛА выключит
наблюдателя (`auditctl -D`, kill поллера, выгрузка eBPF) или прочитает через свой kernel-модуль,
обойдёт всё. Но: (а) наблюдатель шлёт **heartbeat**, и умолкший наблюдатель — сам по себе сигнал,
который вендор видит (как детект тишины метеринга); (б) чтобы обойти, атакующему нужно СНАЧАЛА
нейтрализовать аудитор — заметное действие, поднимающее цену. Это **триппвайр + деттеренс**, не
«невозможно».

## Два слоя (ставить оба)

### 1. Поллер (always-on, репорт вендору) — `pseudex/tripwire.py`
Гоняется как **привилегированный сайдкар** в PID-неймспейсе движка. Тот же релизный бинарь,
`PSEUDEX_ROLE=tripwire`. На каждую НОВУЮ попытку: CRITICAL-лог локально + `POST /v1/tripwire`
на licensing-сервер (tenant-key auth, как метеринг) → вендор видит на `GET /admin/tripwire`:
`org, reader_uid/pid/comm/exe/cmdline`. Пишет КТО, никогда содержимое.

Пример compose-сервиса рядом с движком:
```yaml
  tripwire:
    image: ${REGISTRY}/pseudex:${VERSION}
    pid: "service:sidecar"          # PID-неймспейс движка
    cap_add: ["SYS_PTRACE"]         # читать /proc/<pid>/status соседей
    environment:
      PSEUDEX_ROLE: tripwire
      PSEUDEX_LICENSE_URL: https://license:8443
      PSEUDEX_LICENSE_CA: /certs/ca.pem
      PSEUDEX_KEY: ${PSEUDEX_KEY}
      PSEUDEX_ORG: ${PSEUDEX_ORG}
    restart: unless-stopped
    depends_on: [sidecar]
```

### 2. auditd-правила (syscall-уровень) — `audit-pseudex.rules`
Закрывают `process_vm_readv`-пробел поллера. Ставятся на хост клиента (см. шапку файла).

## Проверено
- `test_tripwire.py` — вендор-сторона (запись+атрибуция+фильтр по org, root uid=0 сохраняется).
- Живой E2E на стенде: карвер открыл `/proc/16/mem` → поллер засёк → репорт → `/admin/tripwire`
  показал `org=acme, reader_uid=0, comm=python3, cmdline=...open("/proc/16/mem")`.

## Итог по «100%»
- **Кто ПЫТАЛСЯ прочитать** (ptrace/held-fd/process_vm_readv, пока аудитор жив) — атрибутируется
  поимённо и уходит вендору в реалтайм. Для распространённого карв-инструментария — да, видим.
- **Абсолютных 100% против подготовленного root** нет (теорема): он выключит аудитор первым — но
  оставит след (умолкший heartbeat) и заплатит цену. Плюс **атрибуция результата** (Tardos/canary)
  остаётся: если украденное всплывёт, назовём чью лизу унесли.
