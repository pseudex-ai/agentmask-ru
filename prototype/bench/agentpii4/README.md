# AgentPII-RU v4 — «шлюз не ломает агента»

Бенчмарк для шлюза псевдонимизации перед LLM-агентом с инструментами. Мерит
не «дошло ли настоящее значение до аргумента» против эталона, написанного
руками (v3), а **остался ли вызов агента тем же, каким он был бы без нас**.

Версия 0.4 · 9 видов сценариев · 11 инструментов по документации реальных RU API ·
360 случаев (пилот 120) · три плеча · русский язык

---

## Что мерим

Одному и тому же диалогу дают одну и ту же модель три раза:

| плечо | что видит модель | куда идут вызовы |
|---|---|---|
| **C** — контроль | настоящий текст | свежий мок, как есть |
| **I** — вмешательство | текст через `RealGateway` (производственный путь: `mask_messages`/`mask_tools` на входе, `unmask_arguments` на каждом вызове, результат мока — через маскирование обратно) | тот же свежий мок, после детокенизации |
| **C′** — второй контроль | настоящий текст | свежий мок |

**Эффект шлюза = agreement(I, C) − agreement(C′, C).** Второй контроль — это
шумовой пол модели на том же случае; без него любое расхождение I с C
приписывается шлюзу, включая то, что модель делает сама с собой.

Согласие считается на **трёх уровнях и печатается тремя строками**, никогда
одним числом: L1 — последовательность имён инструментов; L2 — множества ключей
аргументов; L3 — **типизированное состояние мока** после прогона (рядом —
дословное, и разрыв между ними показывает, что прощает парсер).

## Почему эталон — состояние, а не строка

У каждого инструмента строгий парсер по документации настоящего API (CDEK v2,
Яндекс Доставка, DaData, ЮKassa, паспорт/СНИЛС по контрольным суммам, amoCRM,
SMS Aero) и состояние, которое вызовы меняют. Парсер принимает ровно то, что
документированный API принимает, отказывает с именем документированного правила
и **никогда не чинит**: `8916…` при требовании E.164 — отказ. Строгость мока
сокращается в парной разности, потому что C идёт через тот же мок.

## Таксономия per-field

Для каждого поля каждого вызова — один класс (первое совпадение выигрывает):
`agree` → `absent`/`extra` → `residual` (наша подмена или её кусок дошла до
инструмента) → `validated_refused` (мок отверг I, принял C) → `derived`
(значение объясняется ПОДМЕНОЙ: индекс из фейкового города, возраст из фейковой
даты, инициалы из фейкового имени) → `other_person` → `stale_value` →
`container_embedded` → `reformatted` → `fragment` → `composed` → `other`.

`derived` и `validated_refused` движок **не чинит по построению** и они
печатаются отдельно от того, что он чинит. `residual` — дефект продукта.
Отдельно для КАЖДОГО поля в КАЖДОМ плече — `transform_of`: что модель сделала с
тем, что видела. Гистограмма в плече C — мера провокационной силы корпуса:
корпус, на котором модель только копирует дословно, ничего не проверил.

## Эталон построен, а не найден

`Writer` собирает текст из кусков и записывает смещения при сборке;
`validate.prove_no_search` (sys.setprofile) доказывает, что ни один сценарий не
искал значение в готовой строке. В 12 случаях `text.find(value) != start` —
поправка клиента ставит старый адрес раньше нового.

## Как запустить

```bash
cd prototype && source .venv/bin/activate && export PSEUDEX_LICENSE_ADMIN_TOKEN=devtoken
for m in pools parts derive writer tools mock stats taxonomy compare records; do PYTHONPATH=. python3 bench/agentpii4/$m.py; done
PYTHONPATH=. python3 bench/agentpii4/build.py --check      # корпус + доказательства, не пишет
PYTHONPATH=. python3 bench/agentpii4/build.py              # corpus.json + ladder.json
PYTHONPATH=. python3 bench/agentpii4/smoke.py              # уровень A: фейковый шлюз, ожидаемые вердикты, $0
PYTHONPATH=. python3 bench/agentpii4/smoke.py --engine     # три плеча через НАСТОЯЩИЙ шлюз, скриптовый агент, $0
PYTHONPATH=. python3 bench/agentpii4/harness.py --tier nano --repeats 1 --ceiling 12     # живой пилот
PYTHONPATH=. python3 bench/agentpii4/harness.py --report bench/runs/<дата>/v4-live-nano/<run>.arms.jsonl
```

`smoke --engine` — это скриптовый агент с политиками (копирует, раскладывает,
выводит производные, валидирует, роняет поля), и его отчёт озаглавлен
«СКРИПТОВЫЙ АГЕНТ»: он проверяет ТРУБУ, не модель, и никогда не смешивается с
живым числом. Но за первый день он нашёл в движке четыре дефекта на нулевой
бюджет — см. `docs/tz-agentpii4.md` §7.

## Статистика

pass^k на случай; кластерный бутстрап по различным значениям ПД (один телефон в
трёх случаях — один жребий); McNemar exact на дискордантных парах (помечен
«без кластеров»); ICC(случай) и ICC(значение) с DEFF = 1+(m̄−1)·ICC; при нуле
расхождений печатается односторонний пол Clopper–Pearson, никогда 100%.

## Чего v4 сознательно не делает

Не судит закрытые ответы моделью (детерминированный пол; LLM-судья только на
финальный ответ плеча I), не запускает мульти-модель (после пилота), не чинит
движок по результатам — это следующий этап и решается по ИЗМЕРЕННЫМ частотам.
