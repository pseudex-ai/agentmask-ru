# BENCHMARK — аудит приватного agentpii4 и что v5 обязан закрыть

Аудит НАШЕГО приватного бенчмарка `prototype/bench/agentpii4/` (коронная
драгоценность, **не публикуется**), со сверкой с фундаментальными метриками, что
всплыли в публичном `agentmask-ru`. Дата: 2026-09-22. Метод: чтение кода
(`schema.py`, `compare.py`, `report.py`, `harness.py`, `corpus.json`). Цель —
основание для решения **как строить v5** (следующее поколение). Де-риск направления
tool_result: `research/2026-09-22-toolresult-derisk.md`.

## 1. Что такое agentpii4 (устройство)

**Трёх-armed живой бенчмарк «шлюз не ломает агента».** Три плеча: I (gateway),
C и C′ (control без шлюза). Живая модель (backend) + мок-CRM (`records.py`,
`gateway.py`) с `seed_records`, которые инструменты ВОЗВРАЩАЮТ. Вердикт —
парный (I↔C, C↔C′), TOST при δ=3pp с кластерным бутстрапом. 834 кейса.

**Уровни (`compare.py`, `report.py::LEVELS`):** L0 `action` (сделал ли arm вызов),
L1 `tools` (те же инструменты), L2 `keys` (те же ключи), L3 `state` (та же запись
в CRM, по ТИПУ), L3 `values` (то же ЗНАЧЕНИЕ), L3 `verbatim` (то же значение
БАЙТ-В-БАЙТ = форма). Плюс отдельно: **leak** по типу/регистру (`report.py:138`),
**negatives/over-masking** (`report.py:192`, добавлено недавно).

## 3. Матрица корректности метрик (v4 × фундаментальные из публичного)

| фундаментальная метрика | v4 | как |
|---|---|---|
| Утечка (значение дошло до модели) | **есть-верно** | `report.py` leak по типу/регистру, дамп |
| Over-masking (negatives не тронуты) | **есть-верно** | `report.py:192`, добавлено недавно |
| «Сделал ли arm вызов вообще» (floor) | **есть-верно** | `comparable`: оба пары должны сравниваться (закрытый дефект D1) |
| Значение дошло до инструмента | **есть** (L3 `values`) | но как СРАВНЕНИЕ двух плеч, не как абсолют |
| **Форма (agent-form-fidelity)** | **СТРУКТУРНО СЛЕПА** | L3 `verbatim` сравнивает, что записали ДВА плеча; живая модель нормализует ОДИНАКОВО в обоих (`compare.level_state`), навязанная шлюзом форма не видна — ровно то, что публичный поймал (Б24), а v4 «control и gateway согласны» |
| overlap≠coverage (частичная утечка = утечка) | **под вопросом** | leak — по ЗНАЧЕНИЮ; поэлементного «выжил кусок» (как публичный `surviving_pieces`) нет — частичная утечка может засчитаться как не-утечка |
| Честная coverage (город/маркер — не ПД) | **н/п** | у v4 нет coverage-как-в-публичном; leak по значению |
| **round_trip в ФОРМЕ агента (ответ + tool_result)** | **сложена в уровни, слепа к форме** | ответ судится `must_contain`/`must_not_contain` + judge; форма ответа/результата не меряется отдельно |

**Закрытые дефекты скоринга (CLAUDE.md «инструмент, который не может провалиться»):**
D1 `comparable` (оба пары), D2 `absent_required` (self-test `compare.py:482`),
D3 «floor: сделал ли arm вызов», D4 negatives — по коду закрыты, с self-тестами.

## 4. Слепые пятна (главное)

1. **Форма агента — структурно не видна.** Живая модель нормализует значение в
   ОБОИХ плечах, поэтому навязанная шлюзом форма (наш недельный класс багов:
   именительный для имён, «улица» в адресе, телефон в каноне вместо «8…»)
   на `verbatim`-уровне даёт «согласие». Публичный ловит scripted-агентами
   (copier/rewriter) детерминированно. **Это — крупнейший разрыв.**
2. **Плечо tool_result есть, но НЕ судится по форме.** 455/834 возвращают данные;
   утечка в результате ловится (спаны по всем сообщениям), но **round_trip и
   ФОРМА возвращённого значения в ОТВЕТЕ** не меряются — тонут в 3-arm уровнях,
   слепых к форме. Де-риск (`research/2026-09-22-toolresult-derisk.md`) показал,
   что именно здесь наша уникальная ось.
3. **overlap≠coverage** не разведены: leak по значению, поэлементной coverage нет.
4. **Типы:** INN, PLATE — 0 кейсов; clean-регистр — 6 (тонко для сравнения со
   шлюзами, что сильны на clean).

## 5. Список дыр, которые v5 обязан закрыть

- **Д1. Видеть форму.** Добавить ДЕТЕРМИНИРОВАННОЕ плечо (scripted copier/rewriter,
  как в публичном) ИЛИ форма-оракул поверх живой модели, чтобы навязанная форма
  становилась ЧИСЛОМ. Форма — ПО ПЛЕЧАМ: схема (tool arg) · ответ (проза) ·
  **tool_result**.
- **Д2. tool_result → answer как БАЗА** (владелец): большинство кейсов = «вызвал
  тул → получил реальный результат → ответил из него», все типы ПД, с метрикой
  формы ответа и маскировки результата.
- **Д3. overlap≠coverage:** поэлементная coverage (не только leak по значению).
- **Д4. Полнота типов:** INN, PLATE в корпус; решить долю clean.
- **Д5. Телефония/SSE:** голос уже 55% — добавить стриминговые сценарии (SSE
  «откроет телефонию», `docs/tz-roadmap-from-oss.md` §1.4); плечо tool_result в
  голосе особенно важно.

владельцем; варианты в плане `polymorphic-shimmying-wreath.md` Phase C.**
