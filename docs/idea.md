# Pseudex — концепция продукта

> **Одно предложение:** Pseudex — это middleware (прокси-шлюз) для AI-агентов, который держит реальные персональные данные в РФ и показывает любой модели — дешёвой локальной или зарубежной — только обезличенные токены, не ломая при этом tool-call'ы. Бизнес из СНГ получает возможность использовать недорогой ИИ, **не нарушая 152-ФЗ**.

> **Слоган-кандидаты:** «Модель не видит лишнего» · «Дешёвый ИИ без утечки данных» · *Your models never see the real data.*

---

## 1. Проблема

Бизнес в СНГ хочет встраивать AI-агентов в реальные процессы: поддержка, запись, обработка заявок, работа с заказами. Чтобы это было экономически осмысленно, хочется использовать **дешёвый инференс** — локальные модели на своих GPU или зарубежные API.

Две стены на пути:

1. **152-ФЗ.** Отправить реальные персональные данные клиента (ФИО, телефон, адрес, СНИЛС) в зарубежную или просто чужую модель — это незаконная передача персональных данных. За это штрафуют (оборотные штрафы 1–3% выручки с 2025 г.). Значит «просто подключить OpenAI» нельзя.

2. **Tool-call'ы — главная техническая засада.** Базовую генерацию ещё можно «замаскировать»: заменить ФИО/телефон в тексте на `[ИМЯ]`/`[ТЕЛЕФОН]` перед отправкой в модель. Но как только у агента появляются инструменты, которые **по телефону находят заказ**, **по ФИО оформляют запись** и т.п. — модель генерирует вызов инструмента:

   ```
   find_order(phone="+79991234567")
   ```

   и эти параметры — **обязательны и реальны**: инструменту нужно настоящее значение, чтобы найти заказ. Просто «замаскировать» их нельзя — тогда инструмент не отработает. Вот это место не решает почти никто.

**Суть проблемы в одной фразе:** агенту нужно *действовать* над реальными персональными данными (искать, записывать, менять), но сама модель при этом *не должна их видеть* — иначе утечка и нарушение закона.

---

## 2. Решение

**Обратимая токенизация вокруг границы модели и tool-call'ов.** Реальные данные никогда не пересекают границу модели; карта «токен ↔ реальное значение» (vault) хранится в РФ. Модель становится **расходником** — можно подставить любую: дешёвую локальную, зарубежную, какую угодно.

### Поток данных

```
1. Сообщение пользователя (содержит PII)
   → [Pseudex: находит PII, заменяет реальное → токен; карта хранится в РФ]
2. → LLM (видит только токены; может быть дешёвой/локальной/зарубежной)
3. → LLM генерит вызов:  find_order(phone="<PHONE_7f3a>")
   → [Pseudex: токен → реальный телефон ТОЛЬКО на сервере, в РФ]
4. → Инструмент отрабатывает с реальным значением, возвращает заказ (а в нём — ещё PII)
   → [Pseudex: PII заказа → токены, та же карта (консистентно)]
5. → LLM (видит токенизированный заказ, может рассуждать дальше)
6. → Финальный ответ LLM с токенами
   → [Pseudex: токен → реальное значение перед показом пользователю]
```

**Ключевые свойства:**
- Реальные персональные данные **физически не уходят** ни в модель, ни наружу.
- Vault и карта токенов **остаются в РФ**.
- Модель **взаимозаменяема** — отсюда доступ к дешёвому инференсу.
- Токены **формат-сохраняющие** (выглядят как валидный телефон/почта), чтобы инструменты и валидаторы не падали.
- Токены **консистентны** в рамках сессии (одно значение → один токен), чтобы модель могла связывать сущности между шагами.

---

## 3. В чём соль (почему это работает именно так)

Это та же архитектура, что у западного лидера **Skyflow LLM Privacy Vault** («two-way data rehydration» через MCP-gateway): обезличить аргументы на входе, детокенизировать строго на сервере в момент вызова инструмента, ре-токенизировать результат на выходе. То есть подход **проверен** — мы не изобретаем велосипед, мы переносим доказанную архитектуру на рынок СНГ с локальным рвом.

---

## 4. Юридическая позиция (152-ФЗ) — простым языком

Цель продукта — **не «вывести клиента из-под 152-ФЗ»** (это невозможно и не нужно), а **дать ему не нарушать закон**.

- **Главное нарушение, которого боятся:** передача реальных ПД в зарубежную/чужую модель. Pseudex это убирает: наружу уходит только токен-«номерок», по которому человека не вычислить → запретной передачи нет → **нарушения нет.**
- **Клиент остаётся обычным оператором ПД** (хранит реальные данные в РФ) — это нормально и правильно, так и должно быть.
- **Важный нюанс (чтобы не обещать ложного):** обратимая токенизация, где ключ хранится у тебя, юридически **не является «обезличиванием»** (Приказ РКН №140 от 19.06.2025; ст. 13.1 с 01.09.2025: шифрование без уничтожения ключа — не анонимизация). Значит данные в vault'е всё ещё «персональные», и клиент остаётся оператором. **Это не проблема для нашей цели** — мы продаём «не нарушай», а не «ты освобождён».
- **Правильный питч:** *«Реальные данные остаются в России и не попадают в модель → вы безопасно используете дешёвый локальный или зарубежный ИИ, не нарушая 152-ФЗ и резко снижая риск утечки».*
- **Неправильный питч (так нельзя):** «с нами вы больше не под 152-ФЗ / ваши данные анонимны» — юридически неверно, юрист клиента это поймает.

> Позиция «идентифицируемое — в РФ, наружу только токены» — это защищаемая и куда более безопасная практика, чем отправлять сырые ПД, но это **не статутный safe harbor**. Точная формулировка комплаенса — часть продукта (стоит юриста по 152-ФЗ).

## 5. Рынок и почему сейчас

**На Западе категория проверена и за неё платят (precedent):**
- **Skyflow** — ~$100M поднято, ~2 млрд вызовов vault/квартал, корп-контракты ~$195K/год, ARR в десятки миллионов. Единственный с tool-call-native архитектурой.
- **SentinelOne покупает Prompt Security за ~$250M** (авг 2025). Palo Alto (Prisma AIRS), Microsoft, Cloudflare, AWS (AgentCore) — все шипят смежное. Категория **funded и консолидируется.**

**В СНГ tool-call петли НЕТ ни у кого** (подтверждено тремя независимыми источниками: Ideco, исследование Hivetrace/Raft, основатель Brikko). Что есть:
- **Just AI Jay Guard** — обратимая маскировка **только текста**, хороший RU-NER, on-prem. Tool-call нет.
- **Cloud.ru Guardrails** — обратимая маскировка, но **заперта на свои модели** (нет нейтральности).
- **red_mad_robot Guardrails** — маркетинг-уровень, tool-call не подтверждён.
- Классический DLP (InfoWatch, Solar, Zecurion и т.д.) — статическое обезличивание БД, не LLM-шлюз.

**Это чистый арбитраж «проверено на Западе → нет в СНГ»:** модель доказана деньгами, а Skyflow в РФ не придёт (санкции, нет русского PII-NER, нет 152-ФЗ-привязки). Дверь открыта.

## 6. Кому продаём

Бизнес в СНГ, который строит AI-агентов, касающихся клиентских ПД, и хочет дешёвый/локальный/зарубежный инференс без риска:

- **Поддержка и заказы:** бот находит заказ по телефону, статус по ФИО, оформляет возврат.
- **Запись / бронирование:** клиники, салоны, сервис — агент записывает по имени и телефону.
- **Внутренние агенты:** работа с CRM, заявками, договорами, где в данных полно ПД.

Идеальный первый клиент: компания, которая **уже хочет агента, но боится отправлять данные клиентов в модель** (особенно зарубежную) и/или хочет сэкономить на дорогом инференсе.

> Наш целевой кейс — **passthrough идентификатора** (найти/записать по телефону/ФИО). Именно он идеально ложится на токенизацию (см. ограничения в §9).

## 7. Моат (защищённость)

Не данные, а:
1. **Качество распознавания русских ПД (RU PII NER)** — сердце продукта И главное место утечки. ФИО, телефон, СНИЛС, ИНН, паспорт, адрес, email, номер карты. Пропустил реальный кусок → нарушение. Хороший русский детектор сам по себе барьер.
2. **Tool-call петля** — детокенизация аргумента → выполнение → ре-токенизация результата. Этого нет ни у кого в СНГ.
3. **On-prem + нейтральность к модели** — в отличие от Cloud.ru, работаем с любой моделью, ставимся в контур клиента.
4. **Правильное 152-ФЗ позиционирование** — корректный комплаенс-нарратив + юрист = доверие, которое не скопировать за день.

> Skyflow — доказательство, что подход стоит денег, и одновременно игрок, который в РФ не зайдёт. Мы — «локальный Skyflow для tool-using агентов» раньше, чем кто-либо локальный это соберёт.

## 8. Честные риски и ограничения

- **Модель не может рассуждать над самими ПД.** «Извлеки город из адреса», «это мобильный или городской» — модель видит токен, не сможет. → Продукт силён для *passthrough идентификатора* (наш целевой кейс), слабее для «рассуждать про содержимое ПД». Это ограничение у **всех** в категории, включая Skyflow.
- **Детекция <100% = тихая утечка.** Если детектор пропустил реальное ФИО в свободном тексте — оно уйдёт в модель. Поэтому качество RU-NER критично + нужен defense-in-depth (несколько слоёв проверки).
- **Косвенные идентификаторы.** Адрес + диагноз, дата + сумма + город могут выдать человека и без имени. Нужно думать не только о прямых ПД.
- **Это реальный инженерный продукт, не проект на выходные.** Vault, low-latency на критическом пути, консистентность токенов, обработка multi-turn/RAG. Это плюс (защищённость), но и порог входа.
- **Vault — единая точка отказа и латентности.** Нужны HA и продуманный бюджет задержек.

## 9. Архитектура (верхний уровень)

Компоненты:
- **Detector** — распознавание ПД в тексте и в структурах: RU NER (ФИО, адреса) + regex/валидаторы (телефон, СНИЛС, ИНН, паспорт, карта, email).
- **Vault** — хранилище карты «реальное ↔ токен» в РФ. Формат-сохраняющие, детерминированные/консистентные в сессии токены. Шифрование, контроль доступа к полям (RBAC/CBAC), аудит.
- **Proxy / Gateway** — перехватывает: (а) входящие сообщения и контекст, (б) **аргументы tool-call'ов**, (в) **результаты инструментов**, (г) финальный ответ. Делает swap-in/swap-out в нужных точках.
- **Policy & Audit** — политики (что токенизировать, кому можно детокенизировать), журнал доступа к ПД на уровне полей.

Режимы интеграции (по примеру Skyflow):
- **OpenAI-совместимый прокси** (минимальная интеграция — поменять base URL).
- **MCP-gateway** между агентом и инструментами (для tool-call петли).
- **SDK** для встраивания в контур.

## 10. MVP — узкий первый шаг

Собрать **только tool-call петлю** на одном конкретном сценарии и проверить её целиком:

> Агент на **дешёвой/локальной модели** находит заказ по телефону, **не видя реального номера**.

Минимальный состав:
1. **RU PII detector** (для начала: телефон/email/ФИО через regex + лёгкий NER).
2. **Vault** (даже in-memory/Postgres на старте): реальное ↔ токен, формат-сохраняющий, консистентный в рамках сессии.
3. **OpenAI-совместимый прокси**, который делает swap-in/swap-out вокруг: сообщений, **аргументов tool-call**, **результатов инструмента**, финального ответа.
4. **Базовый аудит** (что детокенизировали, когда, для какого инструмента).

Критерий успеха MVP: пройти весь цикл «вопрос с телефоном → дешёвая модель → tool-call → реальный поиск заказа → ответ пользователю», при этом **в логах модели реального телефона нет нигде.**

## 11. Планка, чтобы со временем догнать Skyflow

- Двунаправленный **MCP-совместимый перехват tool-call'ов** (детокенизация перед выполнением, ре-токенизация результатов).
- Формат-сохраняющие + сессионно-консистентные **детерминированные токены**.
- Безопасный vault с **RBAC/CBAC** и аудитом на уровне полей.
- **Высокий recall** мультиязычного контекстного детектора + fallback-слои.
- Сохранение сущностей в токенах (снизить потерю в рассуждениях).
- Data residency (РФ), HA, low-latency.

## 12. Открытые вопросы

1. **Юридический review:** окончательно зафиксировать позицию «токены наружу — это не передача ПД» с юристом по 152-ФЗ; оформить как часть продукта/гарантий.
2. **Reasoning над ПД:** как обрабатывать кейсы, где модели реально нужно содержимое (частичная детокенизация? семантически-сохраняющие токены?).
3. **Косвенные идентификаторы:** политика для адресов, дат, сумм, медданных.
4. **Бюджет латентности:** допустимая задержка на запрос с учётом детекции + vault.
5. **Модель монетизации:** per-request / per-seat / on-prem-лицензия; цена относительно экономии на инференсе.
6. **Go-to-market:** кто первый клиент, через какой канал (прямые продажи / интеграторы / облака).
