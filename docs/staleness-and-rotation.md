# Протухание и N-version ротация (WS-6 / M3)

Защита IP на обычном железе стоит не на секретности (root-клиент видит тюнинг в RAM —
теорема), а на **дорого + отслеживаемо + быстро протухает**. Этот документ — про третий
столб: сделать украденный снапшот бесполезным быстрее, чем он окупится, и чтобы крэк
одной версии не переносился на следующую.

Экономическое обоснование: 86 Denuvo-игр на Steam 2014–2022 — после крэка теряется
~19% выручки в неделю, после ~12 недель новые продажи ничтожны (Volckmann, Entertainment
Computing). Защита обязана держать не «вечно», а срок полезной жизни снапшота. Протухание
делает этот срок коротким.

## 1. Протухание (staleness) — два рычага, оба УЖЕ несущие

**A. TTL < окна дрейфа ГАР.** Захваченный plaintext-бандл обслуживает не дольше `TTL+grace`
(`pseudex/license.py` degradation ladder). ГАР-словарь улиц ротируется дважды в неделю
(`licensing/fetch_gar.py`), поэтому украденный снапшот улиц протухает внутри собственного
окна. Сервер уже держит потолок: `licensing/server.py::_DRIFT_TTL_CEILING_SECONDS = 7 дней`
предупреждает, если `TTL+grace` его превышает. **Держать `PSEUDEX_LEASE_TTL_SECONDS`
коротким** (дефолт 24 ч; чем короче, тем уже и окно root-патча метеринга — см. §3).

**B. Ре-тюн-каденс.** ГАР — дважды в неделю; авторский тюнинг (`assets_source.py`) —
каждый релиз. Украденный тюнинг-снапшот теряет ОТНОСИТЕЛЬНУЮ ценность по мере того, как
мы улучшаем детекцию: он застревает на качестве дня кражи, наш — растёт.

## 2. N-version ротация (каждый релиз) — крэк одной версии не переносится

Идея Moving Target Defense (NIST): каждый релиз — новая раскладка, так что вскрытие одной
не даёт следующую.

**Канарейки + fingerprint** (`licensing/canary.py`, `licensing/fingerprint.py`)
детерминированы от `PSEUDEX_CANARY_SECRET`. Ротация per-release:
- **Процесс:** генерить новый `PSEUDEX_CANARY_SECRET` каждый релиз (`make-release-keys.sh`).
  Тогда универсум fingerprint'а и коды каждого org другие → крэк/стрип меток одной версии
  не переносится, и метки одного релиза не совпадают с метками другого.
- **Сохранение атрибуции:** сервер ДЕРЖИТ историю секретов (по релизам). `fingerprint.accuse`
  / `canary.identify` должны перебирать исторические секреты, иначе утечка ДО ротации
  перестанет атрибутироваться. **TODO (тулинг, до массовой ротации):** параметризовать
  `accuse`/`identify` набором исторических секретов; сейчас они берут один текущий.

**Обфускация** (WS-1, DIY name-mangling): ротировать соль переименования + build-salt
каждый релиз, чтобы деобфускация одного бинаря не переносилась на следующий — та же
N-version-инвариантность, что у меток.

## 3. Аномалия метеринга (M2) — root-патч виден и ограничен

Root-патч, выключающий `/v1/meter`, занижает счёт в пределах ОКНА TTL (потом обязательный
re-lease), а сам счёт уже зажат полосой `[granted−Q−R, granted]` (`store.py`), так что
занижение ограничено полосой (~0.84%), не 100%. Молчание видно числом: `unacked_quanta`
(кванты без проверенного отчёта) и `ack_regressions` (расход поехал назад — один ключ, два
движка) копятся per-org и БИЛЛЯТСЯ по полу.

Новое (WS-6): **флит-отчёт** `store.metering_anomalies()` → эндпоинт `GET /admin/anomalies`
(admin-токен) сводит подозрительные org для оператора: молчащий (root-патч) или делящий
ключ движок всплывает для ручного разбора. Детект+атрибуция, не enforcement — остаток
против root ограничен полосой и теперь ВИДЕН. Watchdog может опрашивать эндпоинт для
тревог. Тест: `prototype/test_metering_anomaly.py`.
