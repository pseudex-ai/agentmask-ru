## 1. Модель формы: последовательность хопов, живой агент, проверка внутри плеча I [РЕШЕНО]

**Хоп** = один переход значения ПД через шлюз. Два вида, у каждого — ВЛАДЕЛЕЦ формы:

| вид | переход | направление | чья форма | проверка (детерминированная, агент живой) |
|---|---|---|---|---|
| **IN** | текст источника → модель | маска | **источника** | `form(подмена) == form(значение источника)` |
| **OUT** | модель → потребитель | размаска | **агента** — как он написал подмену | `form(реал) == form(подмены, как её написал агент)`; форму агента ЧИТАЕМ из его вывода |

Источники IN: **юзер** (сообщение), **тул** (результат), **документ/чанк RAG**
(содержимое), **память** (раннее упоминание). Потребители OUT: **аргумент тула**,
**ответ юзеру**, **сообщение другому агенту/человеку** (эскалация, summary),
**шаблон** (SMS/письмо).

**Минимальная петля — 4 хопа:** IN-юзер → OUT-аргумент → IN-результат →
OUT-ответ. **Цепочка инструментов удлиняет её:** результат тула A → IN → агент
кладёт в тул B → OUT-аргумент(B) — то, что мы назвали «5-й хоп»; результат B →
IN → ответ → OUT. Мультивызов = много OUT-аргументов и IN-результатов за тёрн.

**Почему v4 это не видел:** сравнение плеч I↔C форму гасит (обе живые модели
нормализуют одинаково); проверка ВНУТРИ плеча I видит всё. На классе Б24:
падеж, родовое слово, запись телефона — всё FAIL без скриптов.

**Состояние движка:** IN-юзер — адрес ✅, остальное частично; OUT-аргумент ✅;
**IN-результат ✗** (форма токена, не тула); **OUT-ответ ✗** (числа в каноне).
v5 сначала ИЗМЕРЯЕТ, следующий план — закрывает.

### 1.1 Сравнитель формы по типу — новый компонент [РЕШЕНО; признаки уточнить]

`form_match(type, produced, reference) -> same | differs(признак…)` — с причиной.

| тип | признаки |
|---|---|
| NAME | класс регистра, падеж, порядок частей, инициалы/полное, транслит |
| PHONE | префикс (+7/8/голый), группировка, разделители, скобки |
| LOC | регистр, родовое слово (есть/нет/сокр.), маркеры д./кв. (слитно/раздельно/полные), запятые, порядок город–улица, по полям/строкой |
| DOB/DATE | нотация, разделитель, паддинг, короткий год, словами |
| EMAIL | регистр |
| CARD/SNILS/INN/PASSPORT/PLATE | группировка, разделители, пробелы, регистр |

Пишется **независимо от движка** (не импортирует `pseudex/`), иначе инструмент не
может провалить то, что меряет.

## 2. Инструменты: покрытие вертикалей и форматов возврата [РЕШЕНО принцип; состав ОТКРЫТО]

Разнообразие нужно потому, что **у каждого API своя форма возврата** — IN-результат
меряет подстройку под КАЖДУЮ. Наборы по вертикалям:

| вертикаль | инструменты | формат возврата = тест IN-результата |
|---|---|---|
| доставка/курьер | create, book, track, reschedule | адрес в нормализации курьерки |
| справочники (DaData-подобные) | `address_suggest`, `normalize_contact` | **канон** «г Самара, ул Луговая, д 10», «+7 (916) …» — жёстче всего |
| клиника | book, slots, patient_find | ДР ISO, СНИЛС с разделителями |
| банк/платежи | create, refund, status, client_find | карта группами, **ИНН** (0 кейсов сейчас), суммы |
| поддержка/тикеты | find, create, escalate | история с реалом в свободном тексте |
| календарь | slots, book, reschedule | даты/время в разных нотациях |
| мессенджеры/почта | sms, email, template | подстановка в шаблон (OUT в тексте) |
| госуслуги/документы | passport_verify, doc_check | паспорт, СНИЛС, **PLATE** (0 кейсов) |
| **поиск / RAG** | search, retrieve | N чанков с ПД (IN ×N), запрос с ПД (OUT) |
| **файлы/документы** | read_file, import_csv, parse_form | ПД внутри документа (IN-документ) — большой рынок |
| телефония/голос | голосовые + стриминг | голос 55% корпуса; IN-результат в голосе |

**Формы возврата** (у каждого тула хотя бы несколько): одиночная запись ·
**список** (выбрать/сопоставить) · **вложенный объект** (по полям) ·
**ошибка с реалом в тексте** · **пусто/не найдено** · канон-нормализация ·
форма, ОТЛИЧНАЯ от той, что дал юзер · свободный текст с ПД · чанки документа.

v4: 31 инструмент (`tools.REGISTRY`), в основном CRM — ревизия по этой таблице.

## 3. Таксономия агентного поведения — что обязан покрыть корпус [РЕШЕНО принцип «ничего не упустить»; доли ОТКРЫТО]

Каждый пункт — семья кейсов с обязательными хопами и своими метриками.

### 3.1 Структура вызовов за тёрн
| поведение | суть | что меряем сверх базы |
|---|---|---|
| **одиночный вызов** | база | 4 хопа |
| **повтор одного тула** | ошибка параметров → повтор с исправленными (телефон переформатирован, имя иначе) | форма на КАЖДОМ OUT-аргументе; ошибка-результат с реалом в тексте (IN); консистентность подмены между попытками |
| **один тул, разные цели** | find(A), find(B) | две личности, нет перекрёстного заражения |
| **последовательная связка** | корзина → заказ → адрес к заказу; найти → обновить → уведомить | **цепочка**: результат A → аргумент B (IN→OUT), накопление состояния, ответ по всем |
| **параллельные вызовы** | N вызовов одним тёрном | N OUT сразу, консистентность, результаты приходят вместе, ответ интегрирует |
| **fan-out → выбор** | найти N кандидатов → выбрать → действовать | список в IN, сопоставление по значению (где плейсхолдер слепнет) |
| **условное ветвление** | найден → обновить / не найден → создать | логика агента на подменах = логика контроля (уровни v4) |
| **найти → показать → подтвердить → действовать** | юзер в петле | память между ходами, OUT-ответ, потом OUT-аргумент из подтверждённого |

### 3.2 Формы данных в результате
список · вложенный объект (адрес по полям) · ошибка/пусто с реалом · шаблон ·
канон · свободный текст (история тикета) · **много записей одной личности**.

### 3.3 Память и контекст [РЕШЕНО]
- значение с хода 1 используется на ходе 7 — **консистентность** (одна
  подмена), **стабильность** (не перечеканена), без коллизий при многих значениях;
- **анафора**: «ему», «на тот адрес», «тот же телефон» — агент разрешает из
  контекста, шлюз держит подмену;
- длинный контекст: много ходов, много личностей;
- summary/эскалация: пересказ диалога с ПД другому агенту/человеку — OUT с
  многими значениями.

### 3.4 Поиск и RAG [РЕШЕНО]
- запрос в поиск с ПД (OUT-аргумент) → N чанков с ПД (IN ×N, в т.ч. чужих
  людей — не смешать) → агент отвечает/действует;
- RAG-чанк с несколькими личностями: консистентность и разделение.

### 3.5 Документы и файлы [РЕШЕНО — большой рынок]
- агент читает файл (договор, анкета, CSV-импорт `crm_import_csv`, форма):
  IN-документ (ПД внутри), извлечение в тул (OUT), ответ;
- форматы: CSV/таблица, свободный текст, структурированная анкета, скан-текст с
  шумом; много записей в одном документе.

### 3.6 Уже есть в v4 (сохранить, дополнить хопами 3–4)
correction · decompose · derive (инициалы/транслит) · normalize · validate ·
compare · summary · container · lookup_list · prompt_rule · long_* · chain ·
tool_chain · result_feed · search_rank · voice_raw/itn.

### 3.7 Голос/телефония [РЕШЕНО как ось]
голос уже 55% — добавить стриминговые сценарии (SSE), IN-результат в голосе.

## 4. Метрики — много, каждая с тестом на корректность [РЕШЕНО]

### 4.1 Сохраняем из v4
уровни парные `action`/`tools`/`keys`/`state`/`values`/`verbatim` + TOST δ=3pp,
кластерный бутстрап, пол 1/n, `comparable`; `leak` по типу/регистру; `negatives`.

### 4.2 Переносим из публичного (доработать под живой агент)
`leak` · **`coverage`** (ни один кусок не выжил; честная — город/родовое/маркер
не ПД) · `typed` · **`round_trip`** (абсолют, не только сравнение плеч) ·
`round_trip_repaired` (диагностика, **не успех**) · `end_to_end` · `overmask` ·
**`consistency`** · **`stability`** · `rewrite_ratio` · `shared_block` · срезы:
регистры / ярусы имён / cue / семьи / **вертикали инструментов**.

### 4.3 Новые для v5
- **`form_<hop>` по типу** с причиной расхождения (§1.1) — главная новая ось;
  агрегаты: по хопу, по типу, по вертикали, по поведению (§3.1).
- **`toolresult_masked`** — реал из результата тула не дошёл до модели.
- **`answer_real`** — ответ клиенту содержит реал в форме агента.
- **`chain_*`** — цепочка A→B: форма на переходе, значение не потерялось.
- **`multi_*`** — N вызовов: все OUT верны, порядок, полнота, консистентность.
- **`memory_*`** — консистентность/стабильность через ходы, анафора.
- **`doc_*` / `rag_*`** — ПД в документе/чанках: замаскировано, извлечено верно,
  чужие личности не смешаны.
- **`residual`** — подмена дошла до тула/ответа = критическая ошибка.

### 4.4 Тесты корректности метрик [РЕШЕНО — обязательно]
По дисциплине `e2e/audit_gates.py`: у **каждой** метрики — фикстуры, на которых
она ОБЯЗАНА быть красной/зелёной (ноль, единица, adversarial); бенчмарк
**отказывается печатать отчёт**, если метрика на своих фикстурах не разделяет.
Правила: инструмент, который не может провалиться, — не инструмент; overlap ≠
coverage — обе цифры; ground truth = канон написанного из того, что построил
генератор; без фолбэков «пришло как написано»; «нет эффекта» — только TOST.

## 5. Судья [РЕШЕНО]
- **Разделение:** форма в ответе — сравнитель (§1.1); **смысл, полнота,
  контекст диалога — судья.**
- **Судит восстановленный ответ (взгляд клиента)** против реального оракула:
  сопоставил ли агент возвращённую запись верно, не выдумал ли, ответил ли на
  вопрос, учёл ли контекст/память. Отдельно флаг `residual` — чтобы подмена в
  ответе не обманула судью.
- Sonnet — судья, Haiku — диалог. **Калибровка** на ручной выборке (согласие с
  человеком по типам ПД и семьям), порог доверия, спред по повторам.

тикеты×2, эскалация, merge) — проходя ревизию: у каждого проставить форму

### 8.2 Доли кейсов (цель v5 ≈ 1 200–1 500; v4 = 834, из них 455 с результатом)

Статистическое основание: на семью нужно **≥120 кейсов для ±10pp** (small-tier по
`TIER_SIZES`), весь корпус ≥600 для ±5pp по уровню; holdout 20% откладывается
ДО отладки; кластеры ≥3 у ≥8 личностей (ICC меряется, не предполагается).

| поведение (§3.1–3.5) | доля | ≈кейсов | обязательные хопы |
|---|---|---|---|
| **всего с результатом тула (база)** | **≥ 75%** | ≥ 900 | IN-результат + OUT-ответ |
| одиночный вызов | 15% | 180 | 4 |
| повтор одного тула (ошибка параметров) | 10% | 120 | OUT×2, IN-error |
| последовательная связка A→B(→C) | 15% | 180 | цепочка IN(A)→OUT(B) |
| параллельные вызовы | 8% | 100 | OUT×N разом |
| fan-out → выбор из списка | 8% | 100 | IN-list, сопоставление |
| условное ветвление | 7% | 85 | логика на подменах |
| юзер-в-петле (найти→показать→подтвердить) | 7% | 85 | память + OUT-ответ + OUT-арг |
| память/анафора через ходы | 10% | 120 | consistency, stability |
| поиск/RAG | 8% | 100 | IN-chunks ×k, чужие личности |
| документы/файлы | 8% | 100 | IN-документ, извлечение |
| один тул, разные цели | 4% | 50 | две личности |

Регистры: голос ≈ 45% (сейчас 55%), chat 25%, sloppy 15%, **clean 10%** (сейчас
0,7%). Типы: **INN ≥ 60, PLATE ≥ 60** (сейчас 0; ≥ `MIN_TYPE_DENOMINATOR`),
остальные — не ниже v4. Существующие 834 не выбрасываются: 455 с результатом
получают обязательные хопы 3–4, остальные — ревизию.

### 8.3 Определения новых метрик и их фикстуры

Единый формат, как в публичном `score.py`: `Line(hits, total)` → доля,
Клоппер–Пирсон, «сертифицирует ≥» при 100%. Ни одна не печатается без своих
фикстур (§4.4). Обозначения: **e** — элемент ПД, **h** — хоп.

| метрика | hits / total | фикстуры can-fail (0 · 1 · adversarial) |
|---|---|---|
| `form_h<IN\|OUT>[type]` | e, у которых `form_match == same` / e, прошедшие этот хоп | падеж-сбой · точное совпадение · та же строка, но другой регистр |
| `toolresult_masked` | результаты тула, где ни один реал не дошёл до модели / результаты с ПД | реал в результате · всё замаскировано · реал в тексте ошибки |
| `answer_real` | ответы, где каждый e — реал в форме агента / ответы с ПД | подмена в ответе · реал · реал в чужой форме |
| `chain_value` | переходы A→B, где реал в B == реал из A / все переходы | потерян · сохранён · сохранён с другим значением того же типа |
| `chain_form` | переходы A→B с `form_match == same` на OUT(B) / переходы | форма тула утекла в B · форма агента · смешанная |
| `multi_all_out` | тёрны, где ВСЕ OUT-аргументы верны (значение и форма) / тёрны с N≥2 | один из N сломан · все верны · N верны, порядок другой |
| `multi_consistency` | тёрны, где одно значение → одна подмена во всех вызовах / тёрны N≥2 | две подмены · одна · одна на ошибку-повтор |
| `retry_form` | повторы тула, где OUT формы совпали с формой агента в КАЖДОЙ попытке / повторы | 1-я верна, 2-я нет · обе · агент сменил форму на 2-й — мы подстроились |
| `memory_consistency` | значения, упомянутые >1 хода, с одной подменой / такие значения | перечеканено · одна · анафора без подмены |
| `memory_stability` | подмены, не изменившиеся между запросами / подмены | сменилась · нет · сменилась при новом разговоре (норма) |
| `rag_masked` | чанки с ПД, где ни один реал не дошёл / чанки | реал чужого человека · всё замаскировано · перемешаны две личности |
| `rag_identity_kept` | чужие личности в чанках, не смешанные с клиентом / чужие личности | смешаны · разделены · один общий телефон |
| `doc_masked` | документы, где весь реал замаскирован / документы | одна строка CSV утекла · всё · шум скана обошёл маску |
| `doc_extracted` | извлечённые из документа e, дошедшие в тул реалом / извлечённые | подмена в тул · реал · реал не того поля |
| `residual` | ответы/аргументы БЕЗ подмены / все | подмена уехала · чисто · подмена в ошибке тула |

Переносимые публичные — с их знаменателями как в `score.py`: `leak`/`coverage`
над всеми e, `round_trip` над изменёнными-с-параметром, `end_to_end` над всеми с
параметром, `overmask` над negatives, `consistency`/`stability` над наблюдениями
со вторым упоминанием, `typed` над e с объявленным типом. `round_trip_repaired`
— только диагностика.

### 8.4 Сравнитель формы — финальные признаки по типу

`form_match(type, produced, reference) -> same | differs({признаки})`. Каждый признак
— булев, извлекается из строки, сравнивается попарно. Пишется без импорта `pseudex/`.

| тип | признаки (все обязательны) |
|---|---|
| NAME | `case_class` (lower/Title/UPPER/mixed) · `gram_case` (им/род/дат/вин/тв/пр — по pymorphy3 голосованием) · `order` (Ф-И-О / И-Ф / И-О-Ф) · `parts` (сколько частей) · `initials` (нет/И./И.О.) · `script` (кириллица/латиница/транслит-таблица) · `hyphen/particle` |
| PHONE | `prefix` (+7 / 8 / 7 / голый) · `grouping` (3-3-2-2 / 3-3-4 / слитно) · `separators` (пробел/дефис/точка) · `parens` |
| LOC | `case_class` · `generic` (нет/полное/сокращение, какое) · `generic_position` (перед/после) · `house_marker` (нет/д./дом, слитно/раздельно) · `flat_marker` (нет/кв./квартира, слитно/раздельно) · `commas` · `city_present`/`city_position` · `by_fields` vs строка · `building/entrance markers` |
| DOB/DATE | `notation` (dd.mm.yyyy / dd/mm/yy / ISO / словами / «др» без точек) · `separator` · `padding` · `year_len` (2/4) · `month_form` (число/слово/падеж) |
| EMAIL | `case_class` |
| CARD | `grouping` (4×4 / слитно) · `separator` |
| SNILS | `separators` (XXX-XXX-XXX YY / слитно) |
| INN | `length` (10/12) · `separators` |
| PASSPORT | `series_number_split` (XX XX XXXXXX / XXXX XXXXXX / слитно) |
| PLATE | `case_class` · `spaces` · `region_sep` |

Вердикт печатает НАБОР расхождений, чтобы отчёт говорил «падеж и регистр», а не «нет».

Уточнения по итогам реализации сравнителя (22.09.2026, `bench/agentpii5/RULINGS.md` R-05…R-08):

- **Воздержание.** Признак попадает в `differs` только если значения различаются
  И ни одна из сторон не несёт метку воздержания (`contracts.FORM_ABSTAIN`):
  `NAME.gram_case = unknown`, `LOC.generic_position = none`, а также `none` для
  `case_class` (NAME/LOC/EMAIL/PLATE) и `NAME.script` у строки без букв. Иначе
  собственные приёмочные пары спецификации невыполнимы: у латинской записи
  имени нет русского падежа, у адреса без родового слова нет его позиции.
- **`other` у `PHONE.prefix` и `CARD.separator`** — строка, не подошедшая ни под
  одну названную форму, получает метку, а не проваливается в последнюю ветку.
- **`LOC.city_present` неотделим от `city_position`** (отсутствие города — тоже
  позиция): проверка изоляции признака принимает пару.

### 8.5 Калибровка судьи

- **Выборка:** 300 ответов, стратифицированных по типу ПД × семье × регистру
  (≥ 20 на страту, где есть); 20% — из holdout. Разметка вручную владельцем/
  доверенным человеком по одной шкале: `верно / частично / неверно / выдумал`.
- **Что судья видит:** ВОССТАНОВЛЕННЫЙ ответ (взгляд клиента) + реальный оракул
  (`oracle_literals`) + контекст диалога; **не видит** подмен. Форму НЕ судит —
  это `form_h<OUT-ответ>`. Отдельно флаг `residual` до судьи: если подмена уехала
  в ответ — ответ `неверно` автоматически, судья не спрашивается.
- **Порог:** согласие судьи с человеком ≥ 0.85 (сырое) и κ ≥ 0.70 на всей
  выборке И на каждом типе ПД с ≥ 20 примерами. Ниже — правим промпт/оракул,
  повторяем; **отчёт с некалиброванным судьёй не публикуется внутри**.
- **Стабильность:** K=3 повтора судьи на 50 случайных; расхождение > 10% —
  судья не годен (температура/промпт).
- **Модели:** Sonnet — судья, Haiku — диалог (решение владельца). Бюджет —
  `QUERY_CAP_USD` и `SpendLedger`, как в v4.
- **Пере-калибровка** при смене модели судьи, промпта или ≥ 20% корпуса.
