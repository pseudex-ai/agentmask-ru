## 0. Что мы уже знаем — коротко

1. **v4 уникален и остаётся базой.** Живой 3-armed TOST «шлюз не ломает агента»
   (834 кейса, 22 семьи, 55% голос, mock-CRM с возвращаемыми записями) — не
   перестраивать, а **эволюционировать**. [РЕШЕНО]
2. **v4 не считает самые ключевые части.** Он смотрел только «поменял ли агент
   поведение» (сравнение плеч). Он **не проверял форму** и **не судил плечо
   tool_result→answer** отдельно. Это пропущенные МЕТРИКИ, а не ограничение
   живой модели. [РЕШЕНО — аудит `wiki/BENCHMARK.md`]
3. **Скриптовых/детерминированных агентов в v5 нет.** Детерминированная форма —
   это для тестов, не для бенчмарка. Агент — живой. **Детерминирована ПРОВЕРКА**
   («совпала ли наша форма с формой агента»), а не агент. [РЕШЕНО]
4. **Форма меняется на 4 хопах**, и на каждом свой владелец формы. [РЕШЕНО]
5. **tool_result должен стать базой** — реальная работа агента: вызвал тул →
   получил результат → ответил; плюс много ходов за тёрн. [РЕШЕНО]
6. **Инструменты агента должны быть разнообразны** — «только CRM» сильно плохо.
   [РЕШЕНО как принцип; набор — ОТКРЫТО]
7. **Метрики публичного бенчмарка переносим, дорабатываем и дополняем** — это
   самое важное. [РЕШЕНО как принцип; точный список — ОТКРЫТО, см. §4]

## 1. Модель: 4 хопа формы, живой агент, проверка внутри плеча шлюза [РЕШЕНО]

Одно значение ПД за один ход агента проходит шлюз 4 раза. На каждом переходе
есть ВЛАДЕЛЕЦ формы, и шлюз обязан подстроиться под него — для **каждого типа
ПД**, не только имён:

| хоп | переход | направление | чья форма | как проверяем (детерминированно, агент живой) |
|---|---|---|---|---|
| **1** | юзер → модель | маска | **пользователя** (регистр, падеж, запись даты, слитность, пунктуация) | `form(подмена) == form(значение юзера)`; форма юзера известна из кейса |
| **2** | модель → тул (аргумент) | размаска | **агента** — как он написал подмену в схему | `form(реал в туле) == form(подмена, как её написал агент)`; форму агента ЧИТАЕМ из его tool_call |
| **3** | тул → модель (результат) | маска | **тула** — формат, в котором CRM/API вернул реал | `form(подмена в результате) == form(значение тула)`; mock-тул отдаёт реал в СВОЁМ заданном формате |
| **4** | модель → юзер (ответ) | размаска | **агента** — как он сформулировал в ответе | `form(реал в ответе) == form(подмена, как её написал агент в ответе)`; читаем из ответа |

**Ключевой факт (исправленный диагноз):** сравнение плеч I↔C форму не видит
(обе живые модели нормализуют одинаково), но проверка **внутри плеча I** —
«наш выход в форме входа агента?» — видит всё. На классе Б24 проверено:
«Максима Дмитрова»→«Игорь Анфалов» (падеж) FAIL; «Вязовая»→«улица Бисертская»
(родовое слово) FAIL; «89032403663»→«9161234567» (запись телефона) FAIL.
Скрипты не нужны.

**Текущее состояние движка по хопам:** 1 — адрес ✅ (`915a365`), имена/даты/
телефон частично; 2 — ✅ (`in_form_of`, `agent_form`); 3 — ✗ (берём форму
токена, не тула); 4 — ✗ (телефон/числа в каноне, не в «8…» агента). Хопы 3 и 4
— зазоры движка, которые v5 должен ИЗМЕРЯТЬ, а следующий план — закрывать.

### 1.1 Сравнитель формы по типу — новый компонент [РЕШЕНО как компонент; детали ОТКРЫТО]

Одна детерминированная функция `form_match(type, produced, reference) -> verdict`
с признаками формы ПО ТИПУ (не «равны ли строки»):

| тип | признаки формы |
|---|---|
| NAME | класс регистра (lower/Title/UPPER), падеж, порядок частей (Ф И О / И Ф), инициалы vs полное, транслит |
| PHONE | префикс (+7 / 8 / голый), группировка/разделители, скобки |
| LOC | регистр, родовое слово (есть/нет/сокращение), маркеры д./кв. (слитно/раздельно/полные слова), запятые, порядок город–улица |
| DOB/DATE | нотация (dd.mm.yyyy / ISO / словами / короткий год), разделитель, паддинг |
| EMAIL | регистр |
| CARD/SNILS/INN/PASSPORT | группировка, разделители, пробелы |
| PLATE | регистр, пробелы |

Вердикт: `same` / `differs(признак…)` — чтобы в отчёте было видно, ЧТО именно
не совпало (регистр? падеж? маркер?), а не только «нет».

Движок уже держит эти признаки в `agent_form.py`, `date_form.py`,
`morph_places.in_form_of`, `translit.py` — сравнитель бенчмарка пишется
**независимо** (не импортирует движок), иначе инструмент не может провалить то,
что меряет.

## 2. Кейсы [РЕШЕНО принципы; объёмы и наборы — ОТКРЫТО]

### 2.1 tool_result → answer как БАЗА
- Большинство кейсов содержат обязательные хопы 3 и 4: тул ВОЗВРАЩАЕТ реал
  (mock в своём формате), агент отвечает ИЗ результата.
- Многоходовый диалог из контекста и памяти: значение встречается на разных
  ходах в разных формах (юзер строчными → CRM +7 → агент «8…»), проверяем
  консистентность (одно значение → одна подмена) и форму на каждом хопе.
- v4 уже даёт 455/834 кейсов с `seed_records` и семьи chain/long_* — их
  ДОРАБОТАТЬ (§2.4), не писать с нуля.

### 2.2 Несколько ходов за один тёрн [ОТКРЫТО — обсудить]
- Агент за один тёрн делает 3–4 вызова: один инструмент повторно, разные
  инструменты, цепочка «найти → обновить → уведомить», параллельные вызовы.
- Вопросы: как считать форму при N вызовах (каждый — свой хоп 2), как судить
  порядок/полноту, как это ложится в TOST-уровни.

### 2.3 Разнообразие инструментов [ОТКРЫТО — обсудить, критично]
- «Только CRM» — сильно плохо. Нужны НАБОРЫ инструментов по вертикалям и
  разные ФОРМАТЫ возвращаемых данных (у каждого API своя форма → хоп 3 меряет
  подстройку под каждую).
- Кандидаты (обсудить): CRM · доставка/курьер · клиника · банк/платежи ·
  тикеты/поддержка · календарь/встречи · e-mail/мессенджер · справочники
  (DaData-подобный normalize/suggest) · поиск по базе · госуслуги/документы ·
  телефония (голосовой сценарий, SSE).
- v4 уже имеет 31 инструмент (`tools.REGISTRY`) — большинство CRM-ориентированы.

### 2.4 Доработка текущих кейсов [РЕШЕНО принцип]
- Пройти 834 кейса и 22 семьи: добавить хопы 3–4 там, где тул возвращает
  данные; задать ФОРМАТ возврата mock-тулов явно; заполнить дыры типов
  (**INN, PLATE — 0 кейсов**); решить долю clean (сейчас 6).

## 3. Метрики — инвентарь и что берём [ОТКРЫТО — самое важное, дообсуждаем]

### 3.1 Есть в v4 (сохраняем)
- Уровни парные I↔C, C↔C′: `action` (сделал ли вызов), `tools`, `keys`,
  `state` (по типу), `values` (значение), `verbatim` (байт-в-байт) + TOST при
  δ=3pp, кластерный бутстрап, пол разрешения 1/n, `comparable` для обоих пар.
- `leak` по типу/регистру; `negatives` (over-masking); судья ответа
  (`must_contain`/`must_not_contain` + LLM-судья на плече I).

### 3.2 Переносим из публичного (доработать под живой агент)
| метрика | смысл | что доработать |
|---|---|---|
| `leak` | изменено до того, как увидела модель | есть |
| **`coverage`** | изменено ЦЕЛИКОМ, ни один кусок не выжил (`surviving_pieces`) | **нет в v4** — ввести; честная: город/родовое слово/маркер — не ПД |
| `typed` | тип определён верно | ввести |
| **`round_trip`** | тул получил реал (из изменённых) | в v4 растворён в `values` — вынести абсолютом |
| `round_trip_repaired` | то же, считая канон доставленным | ввести как диагностику (НЕ как успех) |
| `end_to_end` | тул получил реал из ВСЕХ | ввести |
| `overmask` | negatives не тронуты | есть (`negatives`) |
| `consistency` | второе упоминание — та же подмена | ввести (память/контекст) |
| `stability` | подмена не менялась между запросами | ввести |
| `rewrite_ratio` | переписан текст вне защищённых спанов | ввести |
| `shared_block` | подмену нельзя атрибутировать одному спану | ввести как флаг качества |
| по регистрам / ярусам имён (common/diminutive/foreign/tail) / cue-без-cue / семьям | срезы | есть частично — расширить |

### 3.3 Новые для v5
- **`form_h1`…`form_h4`** — совпадение формы на каждом хопе, ПО ТИПУ, с
  причиной расхождения (§1.1). Главная новая ось.
- **`toolresult_masked`** — реал из результата тула не дошёл до модели (хоп 3
  как утечка), отдельно от leak входа.
- **`answer_real`** — ответ клиенту содержит реал (не подмену, не «починенный»
  канон) в форме агента (хоп 4).
- **`multi_call_*`** — при N вызовах за тёрн: все ли хопы 2 верны, порядок,
  полнота. [ОТКРЫТО]
- **`residual`** — подмена, дошедшая до тула/ответа (фейк уехал) — как
  критическая ошибка.

### 3.4 Правила, которые нельзя нарушить (из CLAUDE.md, эмпирически)
- Инструмент, который не может провалиться, — не инструмент: каждая метрика
  должна иметь способ стать красной; `round_trip_repaired` — не успех.
- overlap ≠ coverage: частичная утечка — утечка; обе цифры печатать, не сливать.
- Ground truth = канон ТОГО, ЧТО НАПИСАНО, из того, что построил генератор.
- Скорер без фолбэков «пришло как написано».
- Ни McNemar, ни CI не доказывают «нет эффекта» — TOST при заранее заданном δ.
