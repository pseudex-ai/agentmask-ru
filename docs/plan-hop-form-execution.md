# Исполнительный контракт goal: 19 пунктов, 5 этапов, DeepSeek-first

**Текущий режим, решение владельца 2026-09-28:** автономный DSH workflow
остановлен. Codex лично пишет оставшиеся исправления и тесты до приёмки 19/19;
прежнее требование ≥90% строк от DeepSeek и запрет Codex писать обычные
исправления отменены этим решением. DeepSeek не получает новые задания на
изменение файлов; независимые проверки остаются обязательными. Новые платные
DSH-проверки, если понадобятся, получают отдельный конечный потолок и
учитываются вместе с уже потраченным. Неполный учёт остаётся нижней границей.
Основное дерево, платный прогон 450, merge, push и deploy не входят в этот GO.

Статус: **обязателен для оставшейся части спринта**. Он определяет способ
исполнения; объём и продуктовые критерии остаются в
[`plan-hop-form-before-450.md`](plan-hop-form-before-450.md). Если документы
расходятся, матрица определяет **что** закрыть, этот контракт — **как** работать.

## 1. Неизменяемый результат

Спринт завершён только после приёмки всех 19 строк:

`M01–M04`, `S01–S02`, `E01–E07`, `C01–C06`.

Каждая строка получает ровно один терминальный статус:

- `ACCEPTED_FIX` — дефект воспроизведён, исправлен и независимо проверен;
- `ACCEPTED_NO_CHANGE` — проверка доказала, что изменение не требуется.

`PARTIAL`, `LOCAL_GREEN`, `CANDIDATE`, `OPEN`, `REJECTED` и `UNKNOWN` не
являются завершением. Перепрогон 450, merge, push и deploy не входят в GO
этого спринта и требуют отдельного решения владельца.

## 2. Владение работой: Codex пишет оставшийся код

Codex пишет и проверяет оставшиеся изменения. Уже созданный DeepSeek код
сохраняет своё фактическое авторство; число строк больше не служит критерием
приёмки. Авторский зелёный тест не заменяет независимую атаку и проверку diff.

| Роль | Делает |
|---|---|
| Codex | архитектура, границы пакета, критерии, чтение diff, локальная проверка, решение ACCEPT/REJECT |
| Codex implementer | RED-тесты, реализация, профильные тесты в audit worktree |
| Независимый проверяющий | контрпримеры и проверка контракта; не редактирует код |

Если исправление меняет архитектурную границу, Codex сначала проверяет её по
спецификации и буквальному RED, затем меняет код. Без независимой проверки
кандидат остаётся открытым, даже если его авторские тесты зелёные.

Для каждого задания сохраняется запись авторства:

- task/session id и роль;
- разрешённые файлы;
- снимок diff до и после;
- число добавленных/изменённых строк кода и тестов;
- стоимость с признаком `accountingComplete`.

Перед финальной приёмкой авторство и стоимость перечисляются фактически.
Неизвестное авторство и неполная стоимость обозначаются явно.

## 3. Два слота и конечный пакет

Если используются DeepSeek-проверяющие, одновременно работают максимум два
корневых агента без детей; они читают законченный пакет и не владеют файлами.

Каждое задание — **конечный пакет**, содержащий:

1. IDs и конкретные подпункты матрицы, которые оно покрывает;
2. один механизм или одну связанную поверхность кода;
3. буквальные RED и соседние отрицательные примеры;
4. разрешённые файлы;
5. команды профильных тестов;
6. критерий завершения, который можно проверить без мнения автора;
7. лимит времени и стоимости.

Задание без любого из семи полей не запускается. Выполнение части пакета не
закрывает весь ID: таблица покрытия отмечает конкретные подпункты.

## 4. Жёсткие лимиты против зацикливания

| Работа | Время | Потолок DSH, если он используется |
|---|---:|---:|
| Реализация Codex | 20 минут до проверки прогресса | — |
| Независимая проверка пакета | 12 минут | $0.10 |
| Один repair по подтверждённым замечаниям | 15 минут | — |
| Весь пакет до решения или явной остановки | 45 минут | не более $0.40 на DSH-проверки |

Сложный пакет может получить больший интервал только с записанной до начала
причиной. Ни один остановленный DSH-сеанс не продолжается автоматически.

У пакета один цикл возврата:

`implement → review → repair → re-check → ACCEPT/REJECT`.

После второго REJECT Codex не запускает ещё один repair. За 15 минут он обязан:

1. остановить пакет;
2. записать корневое противоречие и отбросить неудачную архитектуру;
3. сформировать новый пакет с другой границей/механизмом;
4. показать владельцу факт перезапуска в очередном статусе.

Если за 45 минут ни один пункт или законченный подпункт не получил терминальное
доказательство, это **hard pause пакета**: причина и новая граница публикуются,
а работа продолжается только по независимому готовому пункту.
Нельзя продолжать работу молча.

## 5. Пять этапов

Этапы закрываются по матрице, а не по времени и не по числу тестов.

### Этап 1 — честный измеритель

IDs: `M01–M04`, `S02`.

Два пакета:

- actual-event attribution: M01–M03;
- frozen oracle, mutants и payload canaries: M04 + S02.

Выход: versioned estimator; `ambiguous/unattributed/not_identifiable` видимы;
wrong-value, wrong-form, residual, passthrough и потеря действия ловятся
независимыми ошибочными gateways. Движок не является своим oracle.

### Этап 2 — общий механизм

IDs: `S01`, `E01`, `E02`; representative acceptance на PHONE, NAME и LOC.

Текущие S01 и CARD/noise подпункты должны закончиться, но CARD не закрывает
весь `C02`. После них один пакет проверяет общий контракт
identity → projection → rendering на трёх семействах.

Выход: privacy tool-result, форма текущего отправителя и conflict policy
принимаются одним набором контрактов; частные зелёные тесты не объявляются
закрытием всего этапа.

### Этап 3 — все типы и проекции

IDs: `E03–E06`, `C01`, `C02`, `C04`, `C05`.

Пакеты формируются по общей поверхности, а не по одному примеру:

- NAME + partial projections + gender/case;
- LOC + component ownership + corrections;
- DOB/EMAIL и цифровые типы SNILS/INN/CARD/PASSPORT/PLATE;
- speech/noise/Unicode + quote/summary/template + reproducibility.

Выход: матрица десяти типов × применимые четыре границы заполнена; каждый RED
исправлен или доказан как `ACCEPTED_NO_CHANGE`.

### Этап 4 — полный loop

IDs: `E07`, `C03`, `C06`.

Два пакета:

- chains, retries, corrections, memory и несколько сущностей;
- nested JSON, streaming choices/chunks, proxy/sidecar parity, isolation,
  persistence и согласованный performance threshold.

Выход: offline end-to-end regression на фиксированных входах. Порядок ходов
агента не фиксируется; наблюдение связывается с фактическими событиями.

### Этап 5 — приёмка спринта

Новые реализации запрещены, пока независимая панель не пройдёт все 19 строк.
Независимые проверяющие делят матрицу на два непересекающихся набора; Codex
сопоставляет доказательства с исходными критериями. Затем один полный
локальный regression gate, wiki check и diff review.

Выход: таблица `19/19`, фактическое авторство и стоимость, список
ограничений и локальное `before → after`. Это готовность запросить отдельный GO
на 450, а не утверждение о результате нового живого прогона.

## 6. Частота контроля

### Рабочий граф после возобновления (2026-09-27)

Это маршрутизация уже утверждённых 19 строк, а не новый объём. Узел может
закончиться доказанным `ACCEPTED_NO_CHANGE`; зелёный профильный тест сам по себе
не закрывает строку. Статусы и расходы записываются в `PROGRESS.md` и mission
плагина. Код пишет Codex; если нужны DeepSeek-сессии для независимой проверки,
одновременно их не более двух, без детей и без права редактировать файлы.

| Пакет | IDs | Владение изменениями | Зависимость / граница приёмки |
|---|---|---|---|
| OBS-EVENT | M01–M03 | `bench/agentpii5/{actual_hops,causal_hops,records,harness}.py` и их тесты; точные файлы выдаются по одному заданию | Фактические события, версия значения, causality и явные `ambiguous/unattributed/not_identifiable`; перенос хода не создаёт absent |
| OBS-ORACLE | M04, S02 | `bench/agentpii5/{frozen_oracle,payload_canaries,report}.py` и их тесты | Независимый oracle и мутанты; model-bound payload проверен отдельно от engine spans |
| ENG-BOUNDARY | S01, E01–E02 | `pseudex/{envelope,redact}.py`, профильные тесты | Связь call/result только из протокола; PHONE/NAME/LOC на IN и OUT; никакого угадывания чужой сущности |
| ENG-NAME | E03, C05 | `pseudex/morph_names.py`, NAME-тесты | Пол/падеж/часть/случайный mint; исходный сбой воспроизведён либо остаётся открытым |
| ENG-LOC | E04–E06 | `pseudex/{morph_places,vault}.py`, LOC-тесты | Один владелец составного адреса, проекции и версии; отрицательные два адреса/лица |
| ENG-FORMS | C01–C02, C04 | `pseudex/{date_form,spoken,ru_pii}.py`, типовые тесты | Все десять типов и метаязыковой контекст; неподдержанная форма не превращается в чужие данные |
| LOOP | E07, C03, C06 | после OBS-EVENT: harness/streaming и интеграционные тесты | Реальные цепочки, JSON/stream parity, isolation, performance; без фиксации номера хода |
| ACCEPT | все 19 | только независимое ревью и интеграционная регрессия | По каждой строке доказанный терминальный исход, авторство/расход, без новых утечек; затем отдельный G4-префлайт 450 |

Узкие атаки OBS-ORACLE (M04) и ENG-BOUNDARY (S01) завершились на лимите без
приёмки. Повторять их как поиск ещё одного контрпримера нельзя: две попытки
на каждый root-defect исчерпаны. Следующий пакет имеет другую границу —
производственный контракт повторно переданного tool-call и его результата,
совместно для S01/E01; M04 входит в полный пакет OBS-EVENT/OBS-ORACLE. Общие
`redact`/vault и интеграция сериализуются.

**Наблюдение для S01, не принятое исправление.** В proxy/sidecar ответ агента
проходит `unmask_response` / `/unmask_arguments`; следующий запрос клиента
может содержать восстановленное реальное значение в аргументах того же вызова.
`_Provenance.values_for` пока признаёт только модельную подмену, поэтому
свидетельства вызова не находит. Новый тест в `test_error_echo_privacy.py`
красный: 243/246. Проверка без изменения кода показала: для того же вызова
`raw_evidence=0`, после штатного `_mask_tool_calls` `masked_evidence=1`.
Это задаёт направление: связывать результат с **тем аргументом, который реально
увидит модель в текущем запросе**, сохраняя `tool_call_id`, conversation scope
и отрицательные контроли. Простое правило «любой реальный leaf — evidence»
неприемлемо: оно может приписать чужое значение и неверную форму. Три красных
assertion остаются кандидатом, пока независимая проверка не подтвердит тест и
широкая реализация не пройдёт регрессию.

**Наблюдение для M04, тоже не принятое исправление.** Публичный отчёт берёт
`frozen.lines` из `score_artifacts(corpus, arm_rows, repairs)`, где hops
строятся заново через `observe.observe`; срезы строятся из сохранённого
`<run>.hops.jsonl`. Если файл hops неполон, отчёт помечает себя `incomplete`,
но числители/знаменатели общих строк и срезов могут описывать разные
популяции. Текущий digest не включает hops. Следующий пакет должен связать
строки, срезы, неполноту и versioned digest с **одной** сохранённой популяцией,
не меняя старые числа на полноценном прогоне и не вызывая движок при оценке.
Это дефект измерителя, а не улучшение Pseudex.

Владелец разрешил продолжать новые ограниченные задания при неполном старом
учёте: прежние $0.251535048 остаются **нижней границей**, не обнуляются.
Каждый новый task получает собственный USD ceiling из §4; общий спринтовый
потолок $10 сохраняется до отдельного изменения. Перепрогон 450 здесь —
следующий шлюз после ACCEPT: предварительно фиксируем выборку, хеши,
конкуренцию, прогноз цены и условия остановки; без этого платный run не идёт.

Каждые 30 минут владелец получает ровно пять строк:

1. этап и `ACCEPTED / 19`;
2. что принято за интервал;
3. два активных агента и их время/стоимость;
4. что RED/REJECTED и почему;
5. следующий конечный пакет.

Статус без нового доказательства помечается `NO PROGRESS`. Два статуса подряд
`NO PROGRESS` запускают hard pause из §4.

## 7. Тестовая экономика

- Implementer запускает только профильный RED/GREEN и ближайшие regressions.
- Reviewer запускает профильные тесты и собственные контрпримеры.
- Широкая регрессия выполняется один раз на границе этапа.
- Полная регрессия выполняется один раз на этапе 5.
- Локальный fixture count не выдаётся за метрику 450.
- Один и тот же тест не перезапускается без изменения кода или новой гипотезы.

## 8. Бюджет

Общий потолок DeepSeek остаётся $10. Перед каждым запуском фиксируются
фактический reconciled spend, незавершённый upper bound и резерв.

- $2 сохраняются для этапа 5;
- при `accountingComplete=false` новые задачи не стартуют до сверки, кроме
  явно записанного разрешения владельца продолжать с сохранённой нижней
  оценкой и отдельным потолком каждого нового задания;
- пакет не запускается, если его ceiling плюс резерв превышают остаток;
- превышение task ceiling прерывает задачу и считается REJECT, а не основанием
  увеличить потолок задним числом.

## 9. Запрещённые подмены результата

- Нельзя закрыть ID одной частной формой или одним типом.
- Нельзя ослабить expected result, denominator или privacy negative ради GREEN.
- Нельзя переносить пункт после 450.
- Нельзя выдавать исправленный observer за улучшение движка.
- Нельзя выдавать локальную регрессию за живой результат.
- Нельзя считать исполнителя независимым reviewer собственной работы.

## 10. Следующее действие

1. Сохранить 5 уже принятых строк (`M01`, `M03`, `M04`, `S01`, `E01`) и их
   оговорённые пределы; не принимать их повторно по другой метрике.
2. Проверить кандидат M02 `m0-actual-out-v14` по буквальным досье, сохранённой
   когорте и новым отрицательным примерам. Если независимая атака находит
   ошибку, оставить M02 открытым и изменить границу пакета, а не ослабить тест.
3. Завершить S02: локальные capture/readback и отчёт проходят, но повтор
   соседнего значения пока может скрыть повреждение одного payload; нужна
   независимая атака на всю границу. Старые 450 остаются `NOT_MEASURED`.
4. После приёмки измерителя выполнить оставшиеся строки в порядке этапов 2–5
   исходной матрицы и остановиться перед отдельным GO на живой прогон 450.
