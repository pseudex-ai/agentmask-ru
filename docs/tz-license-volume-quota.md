# ТЗ: убрать инстанс-лимитер, доработать объёмный PAYG (замена слотов)

**Статус:** активное. Заменяет `docs/tz-license-slots-and-epochs.md`.

Решение владельца 24.09.2026: инстанс/слот-счёт как принудительный лимит удалён —
он не меряет продаваемое (весь трафик через один прокси обходит поштучный потолок)
и FLP-невозможен. **Объёмная модель (period-квота + PAYG-овередж + потолок +
буфер + уведомления) УЖЕ ПОСТРОЕНА в биллинге витрины и зрела** — её НЕ
переписываем. Единица — ЗАПРОС (сверяемо с логом шлюза клиента; значения
информационны).

## 1. Как это работает сегодня (не трогаем ядро)

- Движок метрит → лиц-сервер копит монотонный `capacity_billable`/`values`/`requests`
  (`prototype/licensing/store.py` usage, MAC, цепочка, `resets`).
- `storefront/billing/services.py::classify_zone(used, included, cap, buffer)` →
  зоны `included → metered → buffer → stopped`; `build_invoice` считает овередж
  = (metered_requests − included − floor)×`metered_per_1k`/1000 на `capacity_billable`.
- `run_billing_cycle` (ежечасно) детектит зону `stopped` → `set_status("suspended")`
  + `Subscription.volume_capped=True`; новый период двигает watermark → снятие.
- Тарифы: `Plan.included_requests`, `metered_per_1k`, `overage_cap_requests`,
  `buffer_requests`, `metered_floor` (`storefront/billing/models.py`).

## 2. Что добавить/изменить (это весь трек)

### A. Удалить инстанс/слот-лимитер
`store.py`/`server.py`: слоты/поколения/эпохи/фенсинг, `binding_of`,
`lease_generation`, `admit_generation`, `slots_view`, unbound-путь, `max_instances`/
`PLAN_INSTANCES`/`PROCESSES_PER_INSTANCE` как ПРИНУЖДЕНИЕ. `pseudex/license.py`:
слот-код (был +522 из PR #21). Экраны: слот/инстанс-внутренности из ЛК, админки,
операторской, `storefront/billing/slots.py`. Инстансы остаются лишь приблизительным
ПОКАЗОМ (различные `instance_id` в окне), без принуждения. Объёмное принуждение
(§B/§C) НЕ трогать удалением — оно независимо.

### B. Переключатель овереджа — дефолт ВЫКЛ
Новое поле `Subscription.overage_enabled` (default False). Читается в
`classify_zone`-вызовах (`run_billing_cycle` и `services.period_pricing`) и в
`build_invoice`: при ВЫКЛ эффективный потолок = `included` (зоны `metered`/`buffer`
пусты) → пробитие `included` → сразу `stopped`; овередж не начисляется. При ВКЛ —
как сейчас. Переключатель — настройка клиента в ЛК; менять можно в любой момент,
эффект со следующего тика/меры. НЕ выключать задним числом уже начисленный период.

### C. Стоп БЫСТРЕЕ (главное по деньгам)
Сегодня между пробитием потолка и реальным стопом до ~9ч: детект ежечасный
(`run_billing_cycle`) + движок узнаёт `suspended` только на продлении лизы (~TTL/3).
Владелец: раз предупреждаем — можно быстрее. Фикс: витрина передаёт лиц-серверу
АБСОЛЮТНЫЙ потолок запросов периода (`watermark + included + (cap+buffer или, при
overage выкл, 0)`) через connector (`storefront/billing/licensing.py`), лиц-сервер
хранит его на орге и на `/v1/meter` ОТКАЗЫВАЕТ в новой ёмкости сверх него —
движок упирается в исчерпание уже выданной полосы за минуты, а не за часы.
Код отказа — по образцу §3.4 slots ТЗ: ВНЕ `_ANSWER_CODES` выпущенного движка,
мягкий (доцеживает полосу), НЕ мгновенное гашение (урок Б30). Новый период →
витрина шлёт новый потолок. Это НЕ второй квота-движок: одно число + отказ на
готовом meter-пути.

### D. Уведомления в docker logs движка
Пороги (0.8·included, вход в овередж, потолок) уже шлются в ЛК/почту
(`NotifiedState`). Дотянуть их в docker logs движка через lease-notice/version-блок
(`pseudex/license.py`, существующая лестница D-055) — WARN-строки на каждом пороге.

## 3. Что НЕ делать
Не строить квота-движок на лиц-сервере (дубль биллинга). Не трогать монотонный
аккумулятор, MAC, цепочку, grace (grace только под наш сбой связи). Не менять
единицу счёта (запрос). `pseudex/` не импортирует `licensing/`, не `import sqlite3`.

## 4. Приёмка (гейты против РЕАЛЬНЫХ контейнеров + прод-тест)
- overage ВЫКЛ: пробитие `included` → стоп; счёт без строки овереджа;
- overage ВКЛ: сверх `included` служит и копит овередж по ставке; сверх `cap+buffer`
  → стоп; счёт с корректной строкой овереджа;
- стоп наступает за МИНУТЫ после пробития (не часы) — измерить;
- новый период/оплата → стоп снят, watermark сдвинут, следующий счёт корректен;
- удаление инстансов: слот/фенсинг-путей в коде нет (линт); объёмный счёт не задет;
- уведомления присутствуют в docker logs И в ЛК на каждом пороге;
- ПРОД-ТЕСТ на `igor.afonin316@gmail.com`: старт-тариф, прогон трафика к лимиту и
  за него при overage ВКЛ и ВЫКЛ; счёт и стоп верны; деньги считаются точно;
  обратимо (revoke/replan в конце).

## 5. Реализовано (24.09.2026) — модель принуждения потолка

`meter_if_allowed` считает «занятое остальными» РЕКЕНСИ-ЗАВИСИМО (store.py):
- сосед, приходивший за квантом в пределах `_CEILING_LIVE_WINDOW = 3×METER_TARGET_SECONDS`
  (900с), вносит `granted` → ограничивает одновременный холодный старт (нет переслужа);
- устаревший/мёртвый (в т.ч. легаси `last_seen_at=0`) вносит `billable` = реальный
  расход → замороженный резерв не крадёт квоту (нет дрейфа, нет 503 платящему).
`last_seen_at` штампуется на КАЖДОЙ выдаче кванта (и слепой, и acked). Колонка
добавлена в meter с идемпотентной миграцией.

**Допущение (INFO от скептика):** защита от переслужа опирается на однопроцессный
`RLock` лиц-сервера, сериализующий одновременные `/v1/meter`. При запуске сервера
в >1 uvicorn-воркер граница ослабнет (N холодных стартов прочли бы others<ceiling
до фиксации). Сейчас деплой однопроцессный (`deploy/compose.yml` без `--workers`).
Подстраховка — часовой цикл витрины (авторитетный кап). Если когда-нибудь
многопроцессный сервер — вынести потолок-счётчик в БД-транзакцию.
