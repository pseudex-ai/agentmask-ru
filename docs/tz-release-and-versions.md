# Релиз и жизненный цикл версий: движок клиенту, платформа нам

Статус: **ТЗ, принято 20.09.2026, реализуется этапами 1–7.** Решения D-051…D-064
в `wiki/STATE.md`; аргументы и первичные источники —
`research/2026-09-20-release-and-version-lifecycle.md`. По мере исполнения
этапов раздел §9 заполняется тем, чего план не предусмотрел.

## 1. Откуда взялась задача

Один тег `vX.Y.Z` собирал и публиковал пять образов: клиентский движок и
четыре наших сервиса. За последние двенадцать тегов движок менялся в двух.
Десять релизов пересобирали Nuitka-бинарник (~56 минут каждый) и выпускали
клиентам «новую версию» без единого изменения в движке. Проверка по реестру:
`0.3.12` и `0.3.13` — **один и тот же образ** (дайджест конфигурации совпал,
кэш сборки отдал те же байты). Проблема не в байтах, а в номере: два номера на
одном артефакте обесценивают changelog — когда половина версий пуста, никто не
читает ни одну.

Три смежных дефекта, найденные при этом:

- движок сообщал серверу лицензий и показывал в интерфейсе `ENGINE_VERSION =
  "1.0.0"` — константу из `license.py`, при образе `0.3.14`; сервер умел
  отказывать движкам ниже `PSEUDEX_MIN_ENGINE_VERSION`, но сравнивал с
  константой;
- хранилище мигрировало вперёд (`_migrate_*` в `vault.py`, `audit.py`), но без
  номера схемы: старый образ на новом томе не отказывался, снимка перед
  миграцией не было, откат не был описан ничем;
- клиенту негде было увидеть «есть версия новее» и нечем обновиться, сохранив
  том; сайт советовал тег, вписанный руками в `.env` (20.09.2026 — тег `1.0.0`,
  которого в реестре не существовало).

## 2. Как это будет выглядеть — четыре сценария

**Поменялась только витрина.** `git commit -m "fix(storefront): кнопка
поддержки"`. release-please видит файл под `storefront/` и открывает Release PR
«platform 0.4.1» с changelog из коммитов. PR движка не открывается — его файлы
не тронуты. Владелец вливает PR → тег `platform/v0.4.1` → четыре образа, ~10
минут, без Nuitka → подпись → агент выкатил. Клиенты: ничего не произошло.

**Починили детекцию.** `git commit -m "fix(detection): дата рождения «др» без
точек"` — файл под `prototype/pseudex/`. Release PR «engine 0.3.16» (`fix` →
patch). Владелец вливает → тег `v0.3.16` → тесты, Nuitka, гейты P1–P11 и
L1–L25, гейт D-060 «patch не добавил миграций» → push `pseudex:0.3.16` и алиасы
`0.3`, `0`, `latest` → подпись дайджеста. Последний шаг пайплайна — коммит
`chore(registry): pseudex 0.3.16` в `main` с дайджестом → агент на хосте в
течение минуты проверяет подпись дайджеста и подкладывает копию серверу
лицензий и витрине. Клиент на `0.3.15`
в ближайшие 24 часа при продлении аренды получает `version: {latest: "0.3.16",
running_latest: false}` → строка INFO в логе, «доступна 0.3.16» в интерфейсе,
`pseudexctl doctor` жёлтый. Обновление: `pseudexctl upgrade` (снимок тома →
`docker pull pseudex:0.3` → пересоздать с тем же томом → health) или
`docker compose pull && docker compose up -d`.

**Минор со схемой.** `git commit -m "feat(vault): индекс по транслиту"` с
футером `Release-As: 0.4.0` и новым шагом миграции №10. Release PR «engine
0.4.0». Гейт D-060: минор может менять схему, строка `0.4` в
`schema_lock.json` есть. Выпущено: сайт советует `pseudex:0.4`; цикл `0.3`
переходит в `maintenance` с `eol` через шесть месяцев; создаётся ветка
`release/0.3`. Клиент на `0.3` видит «доступна 0.4.0», но `docker pull
pseudex:0.3` её не подтянет — минор осознанный. `pseudexctl upgrade --to 0.4`:
снимок `vault.db.pre-9-10.db` → миграция → схема 10. Если после этого запустить
`0.3` — он откажется до старта воркеров: «схема тома 10, этот образ понимает до
9; образ ≥ 0.4.0 или снимок vault.db.pre-9-10.db». Молчаливой порчи нет.

**Уязвимость в старом миноре.** Коммит `security(assets): …` влит в `main`.
GitHub Action открывает backport-PR в каждую живую ветку `release/*`; владелец
вливает в `release/0.3` → Release PR «engine 0.3.17» с ветки → образ
`0.3.17`, алиас `0.3` сдвинут, `latest` — нет. Клиент на `0.3` получает фикс
через `docker pull pseudex:0.3` без миграции.

## 3. Два потока версий (D-051, D-052)

| компонент | пути | тег | образы | кто получает |
|---|---|---|---|---|
| `engine` | `prototype/` кроме `licensing/`, `bench/`, `e2e/`; бампает только то, что в образе | `vX.Y.Z` | `pseudex` | клиенты |
| `platform` | `prototype/licensing/`, `storefront/`, `deploy/` | `platform/vX.Y.Z` | `pseudex-licensing`, `pseudex-storefront`, `pseudex-backup`, `pseudex-supportbot` | наш хост, одним `compose up` |

Граница проведена по получателю, а не по сервису: у клиента и у нас разные
лестницы предупреждений, разные последствия ошибки и разный темп. Четыре
внутренних образа выкатываются одним агентом одной командой; независимые
версии внутри платформы заставили бы агента согласовывать четыре тега ради
ничего. Прецеденты: `grafana/loki` (`v3.8.0` и `operator/v0.11.0`),
`moby/buildkit` (`v*` и `dockerfile/*`).

`.github/workflows` не принадлежит ни одному потоку и версию не двигает.
`Dockerfile.nuitka` и `build_*.py` лежат под `prototype/` и двигают движок —
верно, потому что меняют артефакт.

**Инструмент — release-please в режиме манифеста.** Компонент получает версию
только если коммит тронул файлы под его путём (`commit-split.ts`: самый длинный
префикс; файл может попасть в несколько компонентов). Корневой пакет `"."` **не
заводится** — он получает все коммиты и вернул бы нас к статус-кво одним ключом
конфига. Инструмент заменим; конвенция — типы коммитов, «изменение = файл под
путём», `version.txt`, теги — навсегда, и при исчезновении инструмента её
воспроизводит скрипт в сто строк.

**Типы коммитов и их эффект:**

| тип | движок / платформа | комментарий |
|---|---|---|
| `feat` | patch, пока версия `0.x`; minor после `1.0` | новый минор до `1.0` — только футером `Release-As: 0.Y.0`: минор = цикл поддержки = ветка, его открывают осознанно |
| `fix`, `security`, `perf`, `build` | patch | `security` и `perf` **обязаны** быть видимыми в конфиге — по умолчанию release-please их скрывает, и security-фикс движка не уехал бы |
| `BREAKING CHANGE` / `!` | major (minor до `1.0`) | — |
| `chore`, `ci`, `docs`, `refactor`, `test`, `research`, `bench` | не двигают | скрытый тип с `BREAKING CHANGE` всё равно считается |

**Релиз = merge Release PR. Тег руками не создаётся.** Job `tag` в
`release-please.yml` ждёт зелёные проверки коммита, создаёт тег и вызывает
`release.yml` явно (`gh workflow run`): тег, созданный `GITHUB_TOKEN`, не
запускает `tags:`-триггер — та же причина, что была у прежнего «ship.yml». Ручной
fallback: `gh workflow run release.yml --ref <tag> -f publish=true`.

**«Изменился ли движок» решает набор файлов образа, а не путь пакета.**
`exclude-paths` у release-please матчит только каталоги, а плоские скрипты в
корне `prototype/` — тесты, генераторы, инструменты — под путём пакета, но в
образ не попадают: `fix(test): …` на `test_loop.py` чеканил бы номер для тех
же байтов. Поэтому набор файлов образа выводится из `COPY`-строк
`Dockerfile.nuitka` (`deploy/shipped_paths.sh`) — одно определение на три слоя:

1. `exclude-paths`: `prototype/licensing`, `prototype/bench`, `prototype/e2e`;
2. `deploy/lint_engine_commits.sh` в `checks.yml`: коммит видимого типа,
   тронувший `prototype/` и ничего из образа, — красный с подсказкой
   «типизируйте как `test:`/`bench:`/`chore:`»;
3. publish-джоба движка красная, если с прошлого тега `v*` в наборе образа не
   изменился ни один файл: номер солгал бы. Это и есть пин D-051.

## 4. Версия движка — один источник (D-053)

`prototype/version.txt` — единственное место. Оба `Dockerfile` записывают
`ENGINE_VERSION = "<version.txt>"` в `pseudex/_release.py` рядом с
`LICENSE_PUBKEY`; `license.py` читает оттуда, в dev-чекауте — из файла.
Публикуется в аренде (`engine_version`), в `/status` (`engine.version`), в
интерфейсе, в `pseudexctl doctor`. Publish-джоба красная, если `version.txt`
не равен тегу.

## 5. Реестр версий (D-054, D-056, D-057, D-061)

`deploy/releases.json`, схема по образцу endoflife.date (сам сайт не поднимаем —
это Jekyll на Ruby ради JSON в сорок строк; ценность в схеме):

```json
{
  "product": "pseudex", "schema": 1, "updated_at": "2026-09-21T10:00:00Z",
  "support": {"maintenance_months": 6, "eol_notice_days": 90},
  "cycles": [
    {"cycle": "0.4", "state": "current", "release_date": "2026-10-05",
     "eoas": null, "eol": null, "eol_announced": null,
     "latest": {"version": "0.4.0", "date": "2026-10-05", "digest": "sha256:…"},
     "aliases": ["0.4", "0", "latest"]},
    {"cycle": "0.3", "state": "maintenance", "release_date": "2026-09-14",
     "eoas": "2026-10-05", "eol": "2027-04-05", "eol_announced": "2026-10-05",
     "latest": {"version": "0.3.17", "date": "2026-10-12", "digest": "sha256:…"},
     "aliases": ["0.3"]}
  ],
  "notices": [
    {"id": "2026-10-sec-01", "severity": "warning", "applies_to": ">=0.3.0 <0.3.17",
     "text": "Уязвимость в …; обновитесь до 0.3.17", "url": "https://pseudex.ru/advisories/…"}
  ]
}
```

- **Пишет пайплайн** релиза движка: `python -m licensing.registry record
  --version --digest --date` → коммит `chore(registry): pseudex X.Y.Z` в `main`.
  Тип скрытый: Release PR платформы от него не открывается — реестр это
  данные, а не код, и релиз четырёх образов ради JSON был бы пустым релизом на
  нашей стороне. На хост копия попадает через агент (см. ниже) в течение
  минуты. Пол минимальной версии всё равно не меняется мимо ревью: `eol`
  руками — только PR-ом в `main`, а запись версии аддитивна и гейтится CI.
- **Руками правятся только** `eol`, `eol_announced`, `notices` — через PR.
  `latest` и `digest` руками не трогаются никогда.
- **Состояния цикла:** `current` (фиксы и фичи) → при выходе следующего минора
  `maintenance` (только `security` из ветки `release/X.Y`, шесть месяцев,
  `eoas` = дата следующего минора, `eol` = +6 месяцев, `eol_announced` =
  сегодня) → `eol`. Числа живут в `support` и меняются данными, не кодом.
- **Алиасы:** `X.Y.Z`, `X.Y` у каждого цикла; `X` и `latest` — только у
  новейшего. Maintenance-патч двигает только `X.Y`. Сайт и кабинет советуют
  `pseudex:X.Y` — клиент получает патчи одним `docker pull`, а шаг на минор
  остаётся осознанным. Подпись — по дайджесту, как и сейчас.
- **Пол:** `min_supported` = `latest` старейшего цикла, у которого `eol` ещё не
  наступил. Сервер отвечает 426 только если `eol ≤ now` **и** `eol −
  eol_announced ≥ 90 д` **и** `now − eol_announced ≥ 90 д`; иначе логирует
  «реестр ставит eol без 90-дневного уведомления — не принуждаю» и
  обслуживает. CI-гейт отвергает PR, где `eol` появился или сдвинут раньше без
  `eol_announced ≤ today` и `eol ≥ eol_announced + 90 д`. Урок Docker 29.0:
  минимум API подняли с 1.24 до 1.44, сломали Traefik и GitLab Runner, откатили
  до 1.40 в 29.3. Гистограмма флота (`/admin/versions`) — условие движения пола.
- **Как реестр попадает на хост:** `deploy/agent.sh` каждый тик делает `git
  show origin/main:deploy/releases.json`, проверяет JSON, делает `cosign verify`
  дайджеста `cycles[0].latest` той же identity, что у образов, и только тогда
  атомарно подменяет `deploy/.registry/releases.json`. Сервер лицензий и
  витрина читают этот файл (монтирован каталогом, чтобы `mv` был виден).

## 6. Вердикт контейнеру — в ответе на аренду (D-055, D-063, D-064)

Каждый контейнер раз в сутки продлевает аренду по аутентифицированному каналу
и уже шлёт `engine_version`. Отдельный update-check (как у Grafana, Nextcloud,
Sentry) добавил бы новый исходящий поток и спор об opt-out; здесь информация
идёт **от сервера к клиенту**, обратный поток не растёт.

Сервер кладёт в ответ **до подписи** (`sign_lease` покрывает все верхнеуровневые
ключи, кроме `bundle` и `signature`; клиент проверяет подпись по тому, что
получил, поэтому развёрнутые `0.3.14` принимают новые поля и игнорируют их):

```json
"version": {
  "running_latest": false,
  "latest": "0.4.0", "latest_in_cycle": "0.3.17", "min_supported": "0.3.17",
  "deprecated_at": "@1759622400", "sunset_at": "Mon, 05 Apr 2027 00:00:00 GMT",
  "notice": {"id": "2026-10-sec-01", "severity": "warning", "text": "…", "url": "…"}
},
"bundle_format": 2,
"lease_contract": 3
```

Формы дат — RFC 9745 (`Deprecation`, `@unix`) и RFC 8594 (`Sunset`, HTTP-date);
`sunset_at` не раньше `deprecated_at`. Уведомление отзывается **отсутствием** в
следующем ответе (образец — Sentry beacon), так что «как снять баннер» не
требует второго механизма. Версия `1.0.0` и любая версия вне циклов трактуется
как старейший цикл.

**Лестница на клиенте:**

| условие | лог | `/status`, интерфейс | `pseudexctl doctor` | обслуживание |
|---|---|---|---|---|
| `running_latest = false` | INFO раз на версию | «доступна X» | жёлтый | полное |
| `deprecated_at` в прошлом | WARN на каждом продлении | баннер «версия устаревает, поддержка до <sunset>» | жёлтый | полное — RFC 9745: deprecation не меняет поведение |
| `notice` | по `severity`, раз на `id` | баннер | — | полное |
| `sunset_at` в прошлом | сервер: 426 `unsupported_client` | «версия больше не обслуживается: обновитесь до ≥ X — `pseudexctl upgrade`» | красный | вердикт вне grace, как 402/403 |

`lease_contract` уже существует (сервер — 3, отдаёт в `/v1/pubkey` и в ответе);
клиент начинает слать его явно, сервер записывает. Несовместимое изменение
формы ответа — контракт 4; старым клиентам сервер отдаёт старый формат, пока
контракт 3 поддерживается. `bundle_format` — целое число формата бандла (2 =
секционный фрейм); клиент с меньшим максимумом получает
`bundle_format_unsupported` «обновите движок», а не «бандл повреждён».

**Порядок выкатки:** сервер раньше клиента (`docs/operations.md` §2bis).
Клиент, получивший ответ без блока (старый сервер), работает как раньше.

## 7. Схема тома (D-058, D-059, D-060)

SQLite резервирует в заголовке файла два целых под приложение —
`application_id` (смещение 68) и `user_version` (смещение 60) — и сама их не
использует. `schema_version` — печенье SQLite, меняется на любой DDL и на
`VACUUM`; запись в него документирована как риск порчи. SQLCipher шифрует
заголовок целиком, поэтому оба числа читаются только после `PRAGMA key` — у
нас это роль `probe`, она уже разрешает ключ до старта воркеров.

- **Штамп:** `application_id` — своя константа на стор (`vault.db`, `audit.db`,
  `tenants.db`); `user_version` — монотонный номер, который ставит только
  миграция. Существующие тома имеют `0` — «до-версионный»: все идемпотентные
  шаги выполняются, затем штамп.
- **Шаги:** нумерованы, лежат рядом со своим стором
  (`vault.VAULT_MIGRATIONS`, `audit.AUDIT_MIGRATIONS`,
  `tenants.TENANTS_MIGRATIONS`), исполняются `pseudex/schema.py::ensure` в
  историческом порядке; после каждого — `PRAGMA user_version = n` и commit.
  `CREATE TABLE IF NOT EXISTS` остаётся базой, не версионируется.
- **Один раз, до фан-аута:** новая одноразовая роль `migrate` в
  `entrypoint.sh` между `probe` и запуском воркеров; под `flock`
  (`vault_migrate._Lock`); воркеры попадают на быстрый путь «`user_version` ==
  max». Сегодня миграции бегут в каждом воркере при `Vault.__init__`.
- **Отказ от тома из будущего:** `user_version > max` образа → `probe` печатает
  «`vault.db`: схема user_version 12, этот образ понимает до 10. Нужен образ ≥
  0.6.0 либо восстановите снимок `vault.db.pre-10-12.db`» и выходит кодом 2;
  `entrypoint.sh` — кодом 6. Так делают Gitea («Gitea will exit to keep your
  database safe»), Signal Desktop (тоже SQLCipher), Home Assistant.
  `user_version < min` → «сначала образ Y».
- **Снимок перед подъёмом:** `os.statvfs` — свободно ≥ 2× (стор + `-wal`),
  иначе отказ до касания; `PRAGMA wal_checkpoint(TRUNCATE)`; `VACUUM INTO
  '<store>.pre-<from>-<to>.db'` на той же связке — SQLCipher сохраняет ключ
  (тест `sqlcipher-compatibility.test`); fsync файла и каталога. Снимок
  открывается тем же ключом; `pseudexctl doctor` перечисляет `.pre-*.db` и
  советует удалить после успешной работы на новой версии.
- **Контракт номера** (словами Gitea): patch — та же `user_version`, откат на
  предыдущий patch свободен; minor — может поднять, в одну сторону; major —
  может потребовать роль оператора, названную в release notes. Пин:
  `prototype/schema_lock.json` `{"0.4": {"vault": 9, "audit": 1, "tenants":
  1}}`; `test_schema.py` красный, если `max_version(store)` ≠ строке минора из
  `version.txt`. Добавил шаг — подними минор, добавь строку.
- **Откат, словами документации:** «Старый образ откажется открыть
  мигрированный том. Чтобы вернуться: остановить контейнер, заменить
  `<store>.db` (и удалить `-wal`/`-shm`) снимком `.pre-*.db`, запустить старый
  образ. `user_version` руками не править никогда».
- **Гейты:** L24 — том из будущего отказан в наших словах (штамп `999` →
  пересоздание → лог «новее образа», exit 6 → штамп назад → обслуживает); L25 —
  до-версионный том: снимок существует, `unmask` прежнего текста совпадает.

## 8. Нативное обновление (D-062)

Для compose: `docker compose pull && docker compose up -d` — Compose «picks up
the changes by stopping and recreating the containers (preserving mounted
volumes)»; том переживает `down`, `rm`, `rm -v`; уничтожает его только `down
-v`. Для `docker run`-клиентов — `pseudexctl upgrade`:

1. `docker pull <образ>` — по умолчанию тот же репозиторий и тег, что у
   работающего контейнера (плавающий `0.3` даёт новейший патч; `--to 0.4` —
   минор); тот же ID образа → «обновлять нечего».
2. `docker stop`.
3. Снимок тома (`backup` tar, `--snapshot PATH`, `--no-snapshot`).
4. `probe` старым образом, только чтение — запоминает `user_version` сторов.
5. `docker rename <name> <name>-old`; `docker run` с теми же томом, портами,
   переменными (по именам, значения — в окружение процесса, не в argv),
   `--memory`, `--restart`, сетью — из `docker inspect` старого.
6. Ожидание health. Здоров → `docker rm <name>-old`. Нездоров и `user_version`
   не двинулся → назад на старый образ. Двинулся → ничего не удаляется,
   печатается `pseudexctl restore <снимок> --yes` и инструкция.

Watchtower не рекомендуется: архивирован в декабре 2025, «не для продакшена» в
собственном README, при отказе оставляет без контейнера. Для уведомлений —
Diun; для compose в git — Renovate с пином дайджеста.
