# ТЗ: лицензионный слой и упаковка

Полное техническое задание на два этапа, после которых Pseudex можно продавать
незнакомому клиенту в его контур.

Продуктовые решения зафиксированы в `spec.md` §2 — этот документ их **реализует**,
а не пересматривает. Все расхождения со `spec.md` отмечены явно.

**Правило приёмки, общее для обоих этапов: закрывающий gate — только end-to-end
на реальном локальном стенде.** Ни один пункт не считается выполненным по факту
прохождения юнит-теста, чтения кода или ручной проверки в консоли. См. §4.

---

## 0. Область и словарь

| Термин | Значение |
|---|---|
| **сайдкар** | образ Pseudex, работающий в контуре клиента (`pseudex/service.py`) |
| **лицензионный сервер** | наш сервис, единственное, что крутится на нашем железе |
| **ключ** | непрозрачная строка `ps_live_…`, выдаётся клиенту, срока не содержит |
| **бандл** | сериализованные активы детекции, зашифрованные под конкретный процесс |
| **аренда (lease)** | подписанный нами ответ: бандл + срок + grace + лимиты |
| **инстанс** | один контейнер сайдкара; содержит N рабочих процессов |
| **процесс** | один рабочий процесс внутри инстанса; арендует бандл самостоятельно |

Вне области этого ТЗ: приём платежей, лендинг, личный кабинет, тарифная логика
сверх лимитов. Лицензионный сервер отдаёт счётчики наружу — биллинг строится
поверх них отдельно.

## 1. Технологический выбор

Раздел отвечает на требование «не писать from scratch». Для каждого выбора —
что взято, почему, и что отвергнуто.

### 1.1 Шифрование бандла — `pyrage` (age)

**Взято:** [pyrage](https://pypi.org/project/pyrage/) 1.3.0 — Python-биндинги к
`rage`, Rust-реализации формата [age](https://github.com/FiloSottile/awesome-age).
Есть manylinux x86_64 wheel, вся криптография остаётся в Rust.

**Почему:** age — специфицированный формат файлового шифрования, где на каждый
примитив выбран ровно один вариант (X25519 + HKDF + ChaCha20-Poly1305), а смена
примитива требует новой версии спецификации. Мы вызываем `encrypt(data,
[recipient])` / `decrypt(data, [identity])` и не собираем схему из примитивов
сами.

**Отвергнуто:**
- `cryptography` (PyCA) в роли шифровальщика бандла — она даёт примитивы
  (X25519, HKDF, AESGCM), но композицию sealed-box пришлось бы писать нам. Это и
  есть «крипта from scratch», просто из безопасных кирпичей.
- Симметричный ключ, переданный в том же TLS-ответе, что и шифротекст — не даёт
  ничего сверх TLS. Смысл появляется только при шифровании **под ключ конкретного
  процесса** (см. §2.4).
- Fernet — AES-CBC+HMAC, формат без внятной эволюции, ключ симметричный.

### 1.2 Подписи — `cryptography` (PyCA), Ed25519

**Взято:** `cryptography` для Ed25519: подпись аренды и манифеста бандла на
сервере, проверка в клиенте публичным ключом, вкомпилированным в бинарник.

**Почему:** подпись и шифрование решают разные задачи. age в режиме X25519 **не
аутентифицирует отправителя** — обладатель публичного ключа процесса может
зашифровать ему что угодно. Для продукта, у которого детекция и есть весь актив,
подмена бандла — это тихая утечка ПД. Ed25519 поверх — 15 строк.

### 1.3 Лицензионный сервер — свой, на нашем же стеке

**Взято:** FastAPI + SQLite (тот же `pseudex/sqlite_setup.py` с WAL и
`busy_timeout`), деплой одним контейнером.

**Отвергнуто: [Keygen](https://keygen.sh/docs/self-hosting/) Community Edition.**
Разбирался всерьёз — это самый зрелый self-hosted вариант, покрывает выдачу,
отзыв, expiry, heartbeat. Не берём по трём причинам:
1. Раздача артефактов (OCI/Docker distribution) — фича **Enterprise**, а не CE.
   Ровно то, ради чего его стоило бы брать, в бесплатной версии отсутствует.
2. Эксплуатация: Rails + Postgres 13+ + Redis 6.2+ + Sidekiq. Для ИП это второй
   продакшн, который надо мониторить и обновлять, ради ~400 строк CRUD.
3. Аренда бандла — наш собственный протокол (ключ процесса, шифрование под него,
   memory-only). Keygen пришлось бы всё равно обвешивать своим сервисом.

Правило «не писать from scratch» относится к криптографии и парсерам, а не к
четырём HTTP-ручкам над таблицей.

### 1.4 Компиляция — Nuitka standalone

**Взято:** [Nuitka](https://nuitka.net/doc/commercial.html) `--standalone`.
Транслирует Python в C и дальше в нативный код — не байткод, декомпиляторы
неприменимы.

**Nuitka Commercial (€250/год, плагин `data-hiding`) — НЕ НУЖНА. Решено замером,
а не рассуждением.** Тюнинг едет в ЛИЗЕ (см. docs/tz-tuning-in-lease.md), а в
образе его нет ВООБЩЕ — ни блоба, ни открытых констант; `grep -a` по образу не
находит ни исходник адресного регэкспа, ни `контактныйтелефон`, ни
`появил на свет`, потому что этих строк там просто нет — плагин `data-hiding` покупал бы ровно
это, а у нас оно уже сделано своим пассом сборки. Bulk-словари (маркерная фамилия
и прочее) по-прежнему лизятся, так что их в образе нет вовсе. Gate P2 проверяет
обе половины: блоб остаётся сжатым, bulk отсутствует. Покупать плагин имело бы
смысл, только если бы P2 упал. Это расхождение со `spec.md` §2.4 в пользу более
дешёвого пути, и оно оплачено измерением.

**Отвергнуто:**
- **PyArmor вторым слоем** (как записано в `spec.md` §2.4). PyArmor шифрует
  байткод и расшифровывает его в рантайме — значит расшифрованный байткод
  обязан оказаться в памяти интерпретатора, откуда его снимают. Nuitka такого
  места не создаёт вовсе. Совмещение двух инструментов документировано только
  для старых веток PyArmor (6/7) с ослабляющими флагами; на 9.x это лишняя
  хрупкость сборки без выигрыша.
- `--onefile`. Распаковывает себя во временный каталог при старте — то есть сам
  создаёт на диске ровно то, чего мы избегаем, плюс замедляет холодный старт.
  Берём `--standalone` (каталог внутри образа).

### 1.5 Registry — Yandex Container Registry + cosign

**Взято:** [Yandex Container Registry](https://yandex.cloud/en/docs/container-registry/pricing)
(оплата только за хранение образов, входящий трафик бесплатен) + подпись образов
[cosign](https://yandex.cloud/en/docs/tutorials/container-infrastructure/sign-cr-with-cosign).

**Почему:** клиенты — российский средний бизнес; тянуть образ из GHCR у части из
них не выйдет по политике или по сети. Подпись cosign нужна не «для галочки»:
клиент обязан уметь проверить, что PII-шлюз, который он ставит внутрь периметра,
собран нами.

### 1.6 Часы деградации — монотонные, без защиты от перевода времени

**Взято:** отсчёт grace — `time.monotonic()` от момента последней успешной
аренды.

**Почему это закрывает откат часов целиком, без сложных схем:** монотонные часы
не зависят от системного времени, а при рестарте процесса память обнуляется —
и рестарт **требует новой аренды** (бандла на диске нет). То есть у клиента нет
состояния, которое можно было бы откатить: ни файла с датой, ни кэша. Схемы с
high-water mark и монотонными счётчиками в TPM решают задачу, которой у нас
структурно не возникает.

Разделение двух часов (доступность против отзыва) взято из
[«Two-Clock Fail-Closed Entitlement Engine»](https://www.tdcommons.org/dpubs_series/10874/):
grace покрывает **нашу** недоступность, но не покрывает отзыв. См. §2.5.

## 2. Этап 1 — лицензионный слой

### 2.1 Поток

```
старт процесса
  ├─ генерирует X25519-пару В ПАМЯТИ (на диск не пишет никогда)
  ├─ POST {license_url}/v1/lease  {key, instance_id, process_id, pubkey, usage?}
  │     ├─ 200 → бандл, зашифрованный под pubkey этого процесса
  │     ├─ 402/403 → процесс не поднимается (exit != 0)
  │     └─ сеть/5xx → процесс не поднимается (холодный старт grace НЕ имеет)
  ├─ decrypt → verify Ed25519 → построить Detector → слушать порт
  └─ каждые renew_after (= TTL/3) → повторить, приложив агрегатные счётчики
```

Направление данных — только от нас к клиенту. Обратно уходят ключ, публичный
ключ процесса и агрегаты. ПД не пересекают периметр клиента ни в каком виде,
поэтому схема не делает нас обработчиком (`spec.md` §1).

### 2.2 Что уезжает в бандл, а что остаётся в бинарнике

> **ЗАМЕНЕНО 2026-09-14 — актуальный дизайн в `docs/tz-tuning-in-lease.md`.**
> Красная команда показала (A2, `research/2026-09-14-security-redteam.md`), что
> вкомпилированный блоб тюнинга со статическим ключом строго ХУЖЕ: дамп памяти
> доставал ключ за ~1 с и расшифровывал блоб офлайн, навсегда, вне отзыва.
> Тюнинг ТЕПЕРЬ едет в лизе целиком (как bulk), в бинаре ничего ценного нет,
> статического ключа не существует. Свойство «патч → нет тюнинга» сохранено и
> усилено. Абзацы ниже описывают СТАРЫЙ дизайн — оставлены как запись решения.


Правило разделения, по которому решается каждый спорный случай:

> **В ЛИЗ-БАНДЛ — только полупубличный BULK, который ротируется (списки имён, улицы
> ГАР — открытые данные). В БИНАРНИК — каждый алгоритм И ВЕСЬ авторский тюнинг
> (cue-слова, адресные регэкспы, таблица приоритетов, look-alike, ключ→тип).**

Это **инверсия против первой редакции**, и причина в угрозе, а не в удобстве.
Тюнинг раньше лизился, а лиз-бандл клиент с root расшифровывает СВОИМ ключом
процесса в один шаг — то есть весь «выстраданный на ложных срабатываниях» набор
cue-слов и адресных регэкспов читался тривиально. Теперь он не путешествует в
аренде: `licensing/pack.py::emit_tuning_module` собирает его в блоб
(`pseudex/_tuning_blob.py`), который компилируется В движок и склеивается с bulk
при загрузке (`pseudex/assets.py::_merge_payload`). Достать его теперь — значит
РЕВЕРСИТЬ бинарник, а не дампить бандл. Защита подобрана по скорости изменения:
bulk дрейфует (аренда + ротация ГАР), тюнинг стабилен (статический барьер).
Формат СНИЛС и его контрольная сумма опубликованы — красть нечего; списки имён
полупубличны и лизятся.

**Блоб ЗАПЕЧАТАН, и это несущий рубеж против патча.** Он лежит в бинарнике не
`zlib+hex`, а `ChaCha20-Poly1305`-шифротекстом (`pseudex/bundle.py::seal_tuning`):
32-байтный ключ, который его открывает, приходит ТОЛЬКО внутри валидной (значит
оплаченной) аренды и живёт в env лицензионного сервера (`PSEUDEX_TUNING_KEY`;
в движок тот же ключ входит при сборке secret-mount'ом, не build-arg'ом — ARG
остаётся в `docker history` каждого слоя после него, гейт P11 это стережёт). Поэтому проверка лицензии становится
**load-bearing, а не булевой веткой на один NOP**: движок, который обошёл
аренду, — пропатченный или пересобравший полупубличный bulk из открытых данных —
ключа не получает, и его СОБСТВЕННЫЙ тюнинг остаётся шифротекстом. Снять проверку
не значит освободить тюнинг — значит уморить его голодом. Остаток честный:
одноразовый плательщик извлечёт ключ из своей аренды и запечёт в фейк-сервер до
следующего релиза (ротация `PSEUDEX_TUNING_KEY` = пересборка), что ограничено
тем же окном дрейфа §3.5.

**В ЛИЗ-БАНДЛ уезжает ТОЛЬКО bulk (плюс штампы `version`/`tuning_version`):**

| Модуль | Активы |
|---|---|
| `names.py` | `data/first_names.txt` (28 412), `data/surnames.txt` (196 799) |
| `address.py` | `street_names` (одиночные ГАР), `street_phrases` (составные ГАР) |
| — | `attribution` (строка лицензии ФНС из того же дампа ГАР) |

**Вкомпилировано В движок как блоб тюнинга** (было в бандле, теперь нет):
`_SEED_FIRST_NAMES`, `_DIMINUTIVES`, `_TRANSLIT`, `_NAME_CUES`, `_STOPWORDS`,
суффиксы имён/отчеств; `_STREET_GAZ`, `_CORE_PART`, типы улиц, **исходные строки
всех адресных регэкспов**; `_BIRTH_CTX`, `_MONTHS`, `_MEDICAL_RE`; `_DENY`,
`_PHONE_TRIGGER`, `_REGIONS`, `_ADDR_INTENT`, `_PLACE_REF`, `_VERSION_CTX`;
`_KEY_TYPE`, `_PRIORITY`, `_LOOKALIKE`, `_CTX_TYPES`, `_INN_CONTEXT`,
`_NUMERAL_TYPOS`. Gate P2 проверяет, что ни одна из этих строк не находится в
образе `grep`-ом — блоб остаётся сжатым, а не отдаётся в открытую.

**Остаётся в бинарнике как КОД:** `validate_snils/inn/luhn/ogrn`, регэкспы
публичных форматов (СНИЛС, ИНН, карта, паспорт, IPv4, ГРЗ, свидетельство о
рождении), `normalize()`, `_resolve()`, `trim_person_span()`, `Vault`, `envelope`,
весь транспорт.

**Штамп связывает половины.** Лиз-бандл несёт `tuning_version` (хеш тюнинга),
движок сверяет его с `VERSION` своего вкомпилированного блоба и отказывается
детектить при расхождении: bulk одного релиза против тюнинга другого — это
неверный деплой, и fail-closed единственный безопасный ответ.

**Обязательное изменение семантики.** Сейчас `names.py:_load_dictionary`
документирует пустой словарь как штатное состояние («empty is a supported state,
not an error»). Это **инвертируется**: отсутствие бандла — не деградация, а
отказ. PII-шлюз с частичной детекцией течёт молча, а молчаливая утечка хуже
остановки. Соответствует правилу fail-closed из `CLAUDE.md`.

**Новый модуль `pseudex/assets.py`:**

```python
class Assets:          # connector к внешнему состоянию -> класс, по конвенции репо
    def load(self, plaintext: bytes) -> None: ...   # msgpack -> скомпилированные структуры
    def unload(self) -> None: ...                   # обнуляет, переводит детекцию в отказ
    def names(self) -> NameAssets: ...
    def address(self) -> AddressAssets: ...
    ...
```

Регэкспы компилируются **один раз при загрузке бандла**, а не на запрос —
иначе аренда станет узким местом на горячем пути. Доступ к активам при
незагруженном бандле поднимает `BundleNotLeased`, которую транспорт превращает в
503 (§2.9).

**Новый модуль `licensing/pack.py`** собирает бандл из рабочего дерева: тот же
самый набор данных, что сейчас в коде, вытащенный в один msgpack + zstd. Это же
гарантирует, что источник правды один и бандл не разъедется с кодом.

### 2.3 Протокол

**`POST /v1/lease`** — единственная ручка, которую дёргает сайдкар.

```jsonc
// запрос
{
  "key": "ps_live_…",
  "instance_id": "8f3c…",          // на контейнер, из entrypoint
  "process_id": "8f3c…-3",         // на процесс
  "pubkey": "age1…",               // X25519, живёт только в памяти процесса
  "engine_version": "1.4.0",
  "usage": {                        // агрегаты с прошлой аренды; при первой — null
    "since_lease_id": "ls_…",
    "requests": 184203,
    "entities": {"PHONE": 12043, "NAME": 8871}
  }
}

// ответ 200
{
  "lease_id": "ls_…",
  "org_id": "acme",
  "issued_at": 1786000000,
  "ttl_seconds": 86400,
  "grace_seconds": 172800,
  "renew_after_seconds": 28800,     // TTL/3
  "bundle_version": "2026-08-13.1",
  "bundle_sha256": "…",             // от ОТКРЫТОГО бандла
  "bundle": "base64(age(…))",
  "signature": "base64(ed25519)"    // над канонической формой всего, кроме bundle
}
```

Коды ответа и реакция клиента:

| Код | Причина | Реакция процесса |
|---|---|---|
| 200 | всё в порядке | загрузить бандл, сбросить часы grace |
| 402 | подписка не оплачена | **grace не применяется**, немедленно 503 |
| 403 | ключ отозван / неизвестен | **grace не применяется**, немедленно 503 |
| 409 | несовместимая версия движка | grace применяется, WARNING с требуемой версией |
| 5xx, таймаут, DNS | наша недоступность | grace применяется |
| 400 | тело или отчёт не разобраны | ответ, не сбой: чинится у клиента |
| 413 | тело сверх предела | то же |
| 429 | слишком часто (метр, бюджет освобождений) | ответ, grace не применяется |

Отдельно: **409 с `error: instance_limit` grace НЕ даёт.** Код 409 в списке
ради «движок слишком стар», и это верно, но им же отказывает потолок инстансов
— из-за чего контейнер, превысивший тариф, уходил в STALE и обслуживал
безлимитно семьдесят два часа. Различается по полю `error`, которое клиент и
так разбирает.

Разделение принципиальное: grace существует, чтобы **наш** сбой не уронил бизнес
клиента. Отзыв ключа — не наш сбой, а решение, и растягивать его на 48 часов
означает подарить клиенту двое суток работы после расторжения.

**`POST /v1/meter`** — покупка кванта ёмкости. Лёгкая и частая: около
килобайта, без бандла. Тело несёт нонс и подписанный отчёт о расходе, ответ —
подписанный абсолютный потолок, размер кванта, резерв и порог предвыборки.
Разъезд с арендой обязателен арифметически: бандл — около двух мегабайт после
шифрования, и покупать этим ценой квант в несколько сотен запросов значило бы
устроить себе DoS.

**`POST /v1/usage`** — счётчики вне цикла аренды. Вызывающих в дереве нет;
описанной здесь идемпотентности по `lease_id` в коде тоже нет и не было. Ручка
подлежит удалению вместе с мостом контракта 2.

**Админские ручки** (отдельный порт, не публикуется наружу) — их десять, и у
каждой объявлена аудитория в `licensing/server.py::ADMIN_ACTIONS`. Витрине
доступны девять; `list` — каталог всех абонентов — только оператору. Совпадение
объявленного со смонтированным проверяется на импорте и роняет старт при
расхождении.

### 2.4 Криптография

**Ключ процесса.** При старте — `pyrage.x25519.Identity.generate()`. Приватная
часть не покидает память процесса и никуда не записывается. Публичная уходит в
запрос аренды.

Что это даёт: перехваченный ответ аренды бесполезен где-либо ещё — расшифровать
может только тот процесс, что сгенерировал пару. Рестарт → новая пара → новая
аренда. Скопировать «рабочий» бандл на другую машину нельзя, потому что он не
существует в переносимой форме.

**Подпись.** Сервер подписывает Ed25519 каноническую JSON-форму ответа (все поля
кроме `bundle`, включая `bundle_sha256`). Клиент: расшифровал → посчитал sha256
→ сверил с подписанным значением → только потом загрузил. Публичный ключ
вкомпилирован в бинарник. Ротация — через `key_id` в ответе и два принимаемых
ключа в клиенте.

**Ключ клиента** на стороне клиента не проверяется вообще — он предъявляется нам
(`spec.md` §2.2). Локально проверять нечего, значит нечего и патчить.

### 2.5 Лестница деградации

Состояния процесса и переходы:

```
BOOT ──арендовал──▶ LEASED ──не продлил──▶ STALE ──grace истёк──▶ EXPIRED
 │                     ▲                     │                       │
 │                     └──── продлил ────────┴───────────────────────┘
 └── не арендовал ──▶ exit(non-zero)         (402/403: сразу в EXPIRED)
```

| Состояние | `/mask` | `/health` | Лог |
|---|---|---|---|
| `LEASED` | работает | `200 {"status":"ok","license":"active"}` | — |
| `STALE` | работает | `200 {"status":"ok","license":"stale","grace_left_s":N}` | `WARNING` при входе и далее раз в 15 мин с остатком grace |
| `EXPIRED` | `503` | `503 {"status":"degraded","license":"expired"}` | `ERROR` раз в 5 мин |

При входе в `EXPIRED` — `Assets.unload()`: бандл вычищается из памяти, а не просто
поднимается флаг. Иначе «отключить проверку» — это патч одного `if`.

**Под 503 уходят только ручки детекции** — `/mask` и `/spans`. `/unmask`,
`/unmask_chunk` и `/reveal` продолжают работать даже в `EXPIRED`: они читают
собственный волт клиента, то есть его же данные по его же токенам. Держать их в
заложниках не нужно и вредно при продаже, а рычаг от этого не слабеет: без
`/mask` fail-closed шлюз клиента вообще не может отправить запрос в модель, и
агенты встают в любом случае.

Отсчёт grace — `time.monotonic()` (§1.6). Величины `ttl_seconds` и
`grace_seconds` приходят **внутри подписанной аренды** и не читаются из
окружения контейнера: иначе клиент выставит `PSEUDEX_GRACE=999999` и лестница
перестанет существовать. На стенде e2e они сжимаются конфигом **сервера**.

Холодный старт grace не имеет: без успешной аренды процесс не поднимается.
Это то самое место, где схема держится — сломанный бинарник детектить нечем.

**Из `EXPIRED` по отзыву есть выход без рестарта.** Отзыв и неоплата
останавливают обслуживание немедленно (в этом весь смысл), но процесс продолжает
спрашивать сервер — реже, раз в минуту, — и восстанавливается сам, как только
статус ключа снова `active`. Иначе оплата счёта превращалась бы в тикет в
поддержку «перезапустите все контейнеры»: рубильник должен останавливать сервис
сейчас, а не делать возврат ручной операцией.

⚠️ Риск из `spec.md` §2.3 остаётся в силе: 503 делает нас single point of failure.
Компромисс для юриста крупного клиента — режим «работает на последнем бандле без
обновлений». В этом ТЗ он **не реализуется**, но состояние `EXPIRED` вынесено в
одну функцию, чтобы такой режим добавлялся правкой в одном месте.

### 2.6 Счётчики

Источник — существующий `AuditLog.counts(org_id)`, уже агрегированный по типам.
В теле — только `org_id`, период, число запросов и разбивка по типам сущностей.
Ни превью, ни токенов, ни значений: gate L10 это проверяет грепом по телу запроса.

**Отчёт КУМУЛЯТИВНЫЙ** — называет итог, а не приращение. Поэтому потерянная
отправка исправляется следующей, задвоить начисление нельзя, и частые отправки
дёшевы. Из этого же следует, что выдернутый кабель не даёт бесплатного сервиса:
потраченное отчитается при первом контакте и попадёт в счёт.

#### 2.6.1 Отчёт уходит своим таймером, а не с продлением — СДЕЛАНО

Было: счётчики ехали ВНУТРИ `/v1/lease`, то есть ровно тогда, когда наступало
продление, а продление считается от TTL:

```
renew_after_seconds = max(1, TTL // 3)      # TTL 86400 → 28800 = 8 часов
```

Измерено на бою, а не выведено из кода: движок поднят с реальным ключом, семь
запросов через `/mask` прошли (подмена стабильная, аудит пишется, аренда выдана,
ёмкость 200 выдана), а `usage` осталась пустой. С укороченным TTL до 90 с тот же
опыт дал `{"requests": 7, "trust": "signed"}` — семь отправлено, семь в отчёте.

Два следствия, оба про деньги: кабинет отставал на восемь часов, а контейнер,
проживший меньше восьми, не отчитывался ВООБЩЕ — и клиент платил по ВЫДАННОЙ
ёмкости (200), а не по факту (семь).

Стало: `_report_usage()` → `/v1/usage` своим таймером
(`PSEUDEX_USAGE_REPORT_SECONDS`, по умолчанию 120 с). Продление аренды не
тронуто — восемь часов там уместны, это про срок лицензии. Эндпоинт `/v1/usage`
существовал с самого начала, и его же докстринг описывает этот случай:
«Normally counters ride on /v1/lease; this exists for a client that wants to
report before its renewal is due».

**Подпись идёт ДО отправки, и это нарочно:** `seq` растёт и цепляется за
предыдущий отчёт до сетевого вызова, поэтому недошедший отчёт оставляет РАЗРЫВ
ЦЕПИ на нашей стороне — признак потери, а не молчание.

#### 2.6.2 Ёмкость УЖЕ считается от темпа — проверить, а не переписывать

**ЗАПИСАНО ПОСЛЕ ПРОВЕРКИ КОДА, И ПЕРВАЯ РЕДАКЦИЯ ЭТОГО ПУНКТА БЫЛА НЕВЕРНА.**
Он утверждал, что порция — константа 200 с предзапросом на 150-м, и требовал
считать её от темпа. На деле `issue_quantum` делает именно это:

```python
elapsed = now - row["acked_at"]
gained  = max(0, consumed - row["acked"])
rate    = gained / elapsed if elapsed > 1.0 else 0.0
quantum = min(max(int(rate * METER_TARGET_SECONDS), low), high)   # темп × 300 с
granted = max(granted, consumed + Q + R)                          # ЦЕЛЬ, а не прибавка
```

`METER_TARGET_SECONDS = 300` (пять минут между покупками), `PREFETCH_FRACTION =
0.25`, границы `quantum_min/quantum_max` — на тариф. 200 и 150, которые я принял
за константы, — это РЕЗУЛЬТАТ вычисления при нулевом трафике, а не политика.

**И `granted` — цель, а не прибавка, и это записано в докстринге как урок:**
«`granted += Q` — это учёт по числу ОБРАЩЕНИЙ, то есть по времени: ровно тот
дефект, из-за которого простаивающий воркер накапливал 45 000 выданных за
полторы минуты и тринадцать запросов». Прирост равен расходу, а разрыв
`granted − consumed` — КОНСТАНТА на процесс.

**Слепой шаг тоже уже продуман:** без отчёта (`acked is None`) считается, что
предыдущий квант выбран целиком. «Слепой шаг не может быть выгоднее честного —
он завышает», и это делает молчание невыгодным без единого механизма
принуждения.

**Вывод: в этой части менять нечего.** Пункт закрыт проверкой, а не правкой.

#### 2.6.3 Автономия тоже уже во времени — расходится только ОБЕЩАНИЕ

Вторая редакция этого пункта тоже была неверна: я писал, что резерв измеряется в
запросах. Он измеряется во времени:

```python
RESERVE_SECONDS = int(os.environ.get("PSEUDEX_RESERVE_SECONDS", str(6 * 3600)))
RESERVE_MAX = {"start": 20_000, "work": 100_000, ...}
```

**Резерв — шесть часов хода** (темп × 6 ч, с потолком на тариф). То есть
автономия по трафику уже временная, и «обслуживает без потолка по запросам, пока
связи нет меньше N часов» — это и есть текущее поведение с `N = 6`.

**Что действительно расходится — числа.** На лендинге написано **«48 часов
автономии»**, а ёмкостного хода у клиента **6 часов**; 48 — это срок аренды с
grace (`PSEUDEX_GRACE_SECONDS = 172800`), то есть про лицензию, а не про
способность обслуживать.

**Поэтому настоящий вопрос не «переписать механику», а «выбрать N»** —
величина деловая:

- **6 часов** (сейчас) — при нашей аварии клиент с трафиком встанет через шесть
  часов;
- **48 часов** — тогда обещание на лендинге становится правдой, но и «кабель на
  два дня» становится возможным. Кумулятивный отчёт (§2.6) при этом оставляет
  потраченное в счёте: кабель даёт отсрочку, а не прощение.

Решать это надо вместе, и менять — одну константу.

**Отдельно проверить:** что происходит, когда резерв исчерпан и связи нет.
Терминальный ответ роняет `_expire()`, а сетевой сбой только предупреждает —
значит после шести часов хода контейнер упрётся в потолок `granted`. Это и есть
настоящий предел автономии, и его надо проверить на живом стенде, а не вывести из
чтения.

### 2.6.4 Нагрузочное тестирование — ОБЯЗАТЕЛЬНО ДО РЕКЛАМЫ

Два разных страха, и одним стендом их не проверить:

- **сервер лицензий не bottleneck** — он общий, и его торможение тормозит чужие
  прод-агенты;
- **контейнер не съедает ресурсы клиента** — вольт и аудит растут, а это ЕГО прод,
  и сломать его мы не имеем права.

Стенд локально, не на проде: **10 000 клиентов × 1–5 инстансов = 10–50 тыс.
процессов**, темпы разные (от 1 до 10 000 запросов/час) — равномерная нагрузка о
разной не говорит ничего.

**На сервере:** RPS и p50/p99 `/v1/lease`, `/v1/meter`, `/v1/usage`; **размер БД
и скорость роста** на 10–50 тыс. процессов (`meter` и `usage` пишутся на
процесс); память; поведение при отказе.

**На контейнере:** рост `vault.db` на длинном трафике (сколько занимает одно
реальное значение, что будет на 100 тыс. и на 1 млн); рост `audit.db` — он
пишется на КАЖДЫЙ запрос и может перерасти вольт; RSS воркера при растущем
вольте.

**Порог приёмки назвать ДО прогона.** Без него получим графики и никакого вывода.

### 2.9 Ошибки

Fail-closed, без исключений. Любая ошибка аренды, расшифровки, проверки подписи
или обращения к незагруженным активам приводит к отказу обслуживания, никогда —
к обработке без маскирования.

```jsonc
// 503
{"error": "license_expired", "detail": "lease expired 2026-08-13T04:11:00Z, grace exhausted",
 "license": {"state": "expired", "last_lease_at": …, "last_error": "connect timeout"}}
```

Коды: `license_missing`, `license_invalid`, `license_revoked`, `license_expired`,
`bundle_unavailable`, `bundle_corrupt`, `engine_incompatible`. В сообщение
кладётся то, что нужно для разбора инцидента: адрес сервера, код последнего
ответа, время последней успешной аренды.

## 3. Этап 2 — упаковка

### 3.1 Сборка

Многостадийный `Dockerfile`:

```
stage build:  python:3.12-slim + gcc + nuitka
              nuitka --standalone --include-package=pseudex …
stage runtime: debian:12-slim + скомпилированный каталог
```

Флаги:

```
--standalone
--include-package=pseudex
--include-package=uvicorn --include-package=fastapi
--include-package-data=pymorphy3_dicts_ru
--include-package-data=natasha --include-package-data=navec --include-package-data=slovnet
--python-flag=no_docstrings --python-flag=no_asserts
--output-filename=pseudex-serve
serve_main.py
```

Словари pymorphy3 и модели natasha/navec/slovnet **остаются в образе** — это
чужие открытые артефакты, не наш моат, и тянуть их в аренду бессмысленно.
Наше — в бандле.

**`--include-module=_json` обязателен.** Плагин anti-bloat включён по умолчанию и
молча выбрасывает C-ускоритель JSON, сообщая об этом одной проходной строкой в
логе сборки: `Not including '_json' ... may slow down by using fallback
implementation`. Сервис разбирает и пересобирает JSON-тело на каждом запросе, так
что это обменивает немного размера образа на постоянный налог к латентности на
горячем пути. Тем же порядком возвращается `_bisect`.

`--python-flag=no_docstrings` вырезает docstring'и; FastAPI использует их для
описаний в OpenAPI. Функционально не несущее, но проверяется в P3.

### 3.2 Проблема `uvicorn --workers` и её решение

**Это главный технический риск этапа, его надо решить до всего остального.**

Сейчас `entrypoint.sh` запускает `uvicorn --workers N`, и это несущая
конструкция: pymorphy3 держит GIL, реальный параллелизм даёт только процессы.

Менеджер воркеров uvicorn несовместим с замороженными бинарниками: у
frozen-исполняемых файлов на Unix недоступны методы старта `spawn`/`forkserver`,
и `uvicorn --workers > 1` под Nuitka падает на умирающем `semaphore_tracker`
([Nuitka #1063](https://github.com/Nuitka/Nuitka/issues/1063),
[#1581](https://github.com/Nuitka/Nuitka/issues/1581)). Штатная рекомендация —
запускать скомпилированное FastAPI-приложение одним процессом, что для нас
означает потерю всего CPU-параллелизма.

**Решение: `SO_REUSEPORT`.** Python-мультипроцессинга не остаётся вовсе.

```
entrypoint.sh (обычный shell, IP не содержит)
  └─ for i in 1..N: ./pseudex-serve &      # N независимых процессов
                     └─ создаёт свой сокет с SO_REUSEPORT на :8000
                     └─ uvicorn.Config(app, fd=sock.fileno())   # --fd есть в uvicorn 0.52
```

Балансировку между процессами делает ядро. Общий Vault и audit — уже общие через
SQLite на смонтированном томе, то есть токены остаются согласованными между
процессами ровно как сейчас.

**Замерено, не предположено.** 4 процесса uvicorn 0.52.1, каждый со своим
`SO_REUSEPORT`-сокетом на одном порту, 60 свежих соединений в `python:3.12-slim`:
распределение 18 / 18 / 13 / 11 по четырём PID. Схема работает.

⚠️ **На macOS это не воспроизводится и воспроизводиться не будет.** Там
BSD-семантика `SO_REUSEPORT`: биндиться разрешено, но все соединения уходят в один
процесс (замер на darwin — 40 из 40 в один PID). Разработка идёт на macOS,
поэтому локальная проверка параллелизма **обязана** идти в Linux-контейнере,
иначе схема выглядит сломанной там, где она исправна.

Известное свойство (не регрессия): распределение идёт **по соединениям**, а
клиент с пулом keep-alive может осесть на одном процессе. С сегодняшним
`--workers` картина та же — воркеры так же конкурируют на `accept()` по одному
сокету. Требование к интеграции: пул соединений хоста ≥ 2N. Проверяется в P5
измерением фактического распределения.

Запасной вариант, если `SO_REUSEPORT` не даст равномерности: N однопроцессных
контейнеров за nginx. Дороже по эксплуатации, поэтому только как запасной.

### 3.3 Registry и подпись

- Приватный репозиторий в Yandex Container Registry, отдельный сервисный аккаунт
  на клиента (отзыв доступа = отзыв доступа к обновлениям).
- Подпись `cosign sign`; в quickstart клиента — команда `cosign verify` с нашим
  публичным ключом.
- Тег: `pseudex:<engine_version>`; `latest` не используется — клиент должен
  знать, что именно у него внутри периметра.

### 3.4 Модель угроз: что прячем, а что нет — РЕШЕНО

> **Обновление 2026-09-14 (`docs/tz-tuning-in-lease.md`).** Граница «заказчик
> может прочитать свою лизу» осталась (её аппаратно не закрыть на любом железе).
> Но раньше это означало extract-once-run-**forever** офлайн вне отзыва —
> красная команда это воспроизвела (A2). Теперь тюнинг в лизе, статического
> ключа нет: извлечение даёт ОДНО окно активной лизы, отзыв работает. Остаток
> (тюнинг активной лизы в RAM у root) сужается коротким TTL и водяным знаком.


Требование сформулировано владельцем продукта явно, и оно уже, чем казалось:

> **Бандл клиент увидеть может — это приемлемо. Исходный код увидеть не должен.**

Отсюда два следствия, и оба экономят много работы.

**Confidential computing отвергнут.** AMD SEV-SNP / Intel TDX + remote attestation
— единственный технически честный способ спрятать данные от root'а на чужой
машине, и мы его не берём. Он требует конкретных поколений железа (EPYC
Milan+/Xeon Sapphire Rapids+), которых у среднего российского бизнеса на своём
контуре нет и в обозримом будущем не появится. А защищал бы он ровно то, чем мы
готовы рискнуть — бандл.

**Планка — коммерческий десктопный софт и игры.** Игры едут нативным кодом, их
реверсят и взламывают, но исходников с именами, структурой и комментариями
никто не получает. Это ровно то, что даёт Nuitka: машинный код, а не байткод,
и никакого инструмента вида `uncompyle6`, который вернул бы Python одной
командой.

**Остаточный риск, который эта формулировка не покрывала.** «Бандл клиент увидеть
может» написано про угол А — про то, что мы не прячем данные от чужого root'а.
Про угол Б — про оплату — из этого не следует ничего, и разрыв стоит проговорить.

Снимок памяти процесса, который прямо сейчас **законно арендует**, даёт плоскую
копию бандла. Эта копия **не подчинена лестнице TTL → grace → EXPIRED**: лестница
живёт в цикле `LicenseClient` того самого процесса и не имеет власти над копией,
скормленной отдельной программе, которая наш цикл не вызывает вообще. Гейт L14
меряет выгрузку активов **после** истечения аренды; снимок **до** истечения не
меряет никто, и это не оплошность, а не обсуждённый до сих пор случай.

Барьер остаётся, но он не запретительный: чтобы копия стала полезной, нужно
отдельно воспроизвести порядок слияния, приоритеты и контекстные фильтры
`detect_all.py` вне нашего бинарника — а это ровно то, что таблица ниже относит
к «алгоритм, не секрет». То есть цена обхода — не «скопировать файл», а
«написать половину движка заново, имея словари».

Принимаем это как осознанный остаточный риск. Эфемерный ключ процесса всё равно
делает главное: захваченный артефакт бесполезен **на другой машине** — age-текст
привязан к паре ключей, которая рождается и умирает с процессом. Мы честно
защищаемся от перераспространения, а не от самого лицензиата, и заявлять стоит
именно это.

**УГОЛ В: ЦЕЛОСТНОСТЬ УЧЁТА ПРОТИВ САМОГО ЛИЦЕНЗИАТА.** Формулировка выше
(«защищаемся от перераспространения, а не от самого лицензиата») верна для
угла А и была молча перенесена на биллинг, где она неверна. С переходом на
тарификацию объёма это надо сказать отдельно.

Что достижимо и достигнуто: движок не обслуживает без ёмкости, а ёмкость
выдаём только мы. Отсюда `granted` — наша запись, и она нижняя граница счёта:
клиент может её только не попросить, перестав обслуживать. Отчёт о расходе
работает в обратную сторону, уменьшая начисление до фактического, поэтому
занижать его невыгодно, а снимать — значит отказываться от скидки. Ни одного
входа, который считает клиент, в нижней границе нет.

Что НЕ достижимо и не заявляется: подпись отчёта не доказывает правдивость
чисел. Секрет запечатывается на ключ, который генерирует сам клиент, — владелец
ключа подписывает что угодно, и проверено, что тридцать строк на одном ключе
лицензии дают отчёты со статусом `signed`. Полностью разобрано в
`pseudex/bundle.py::mac_report`; там же сказано, почему это не мешает счёту
быть верным.

Остаточный риск тот же, что и в угле А: патч релизного бинарника. Окно
бесплатной работы патча равно TTL аренды и повторяется на каждой версии. Мера
исполняемой сборки едет внутри подписанного отчёта — это датированный факт, а
не невозможность, и заявлять стоит именно это.

**Что реально осталось в бинарнике — замерено, а не предположено:**

| | В образе | Почему |
|---|---|---|
| `.py` / `.pyc` | нет | компиляция в машинный код |
| текст кода | нет | проверено грепом по 4 характерным конструкциям |
| комментарии | нет | Python отбрасывает их при разборе, до компиляции |
| **докстринги** | **были — вырезаны** | см. ниже |
| имена символов, пути модулей | **есть** | нужны для трейсбеков; имя — не строка кода |

**Докстринги — единственная дыра, и она была настоящей.**
`--python-flag=no_docstrings` мы передавали с самого начала, и он не помог: флаг
запрещает компилированному модулю выставлять `__doc__`, но сами литералы
остаются в блобе констант Nuitka, где `grep -a` находит их дословно. Замерено на
собранном образе — «Connector to the leased asset state» и соседние нашлись.

Это хуже утечки кода. Докстринги в этом репозитории и есть проектный журнал: чем
обоснован выбор, какая альтернатива отвергнута и почему, что измерено. Отдать их,
удержав синтаксис, — отдать самое ценное.

Решение: `build_strip_docstrings.py` вырезает их из наших исходников **до**
Nuitka. Содержимое заменяется на `""` по точному диапазону, с добивкой переводами
строк — файл сохраняет число строк, поэтому трейсбек из проданного бинарника
по-прежнему указывает на верную строку настоящего исходника. Применяется только к
нашему дереву: у сторонних пакетов `__doc__` бывает функциональным (argparse,
FastAPI OpenAPI), и ломать их ради чужой прозы — плохой размен.

⚠️ Грабли, на которые наступили: `ast` отдаёт `col_offset` в **байтах UTF-8**, а
не в символах. Резать `str` по этим смещениям нельзя — на любой строке с
кириллицей или тире срез уезжает, и правка съедает следующую строку. У нас
докстринги русскоязычные, так что ломалось сразу и громко.

### 3.5 Что упаковка НЕ даёт

Nuitka не делает восстановление исходников невозможным — она делает его дорогим.
Планка из `spec.md` §2.4 («прочитать `.py` — минуты, разобрать нативный бинарник —
недели») остаётся честной формулировкой. Настоящая защита — аренда бандла:
украденный сегодня бандл завтра не продлится, а устаревший детектор на
PII-шлюзе начинает течь. Упаковка нужна, чтобы бандл нельзя было выковырять из
памяти тривиально, а не вместо аренды.

**Дрейф бандла — ГЛАВНЫЙ долговечный рычаг, и он зафиксирован политикой, а не
настройкой.** Все статические ходы (нативная компиляция, вырезанные докстринги,
скрытые строки-маяки, вкомпилированный блоб тюнинга §2.2) поднимают стоимость
ОДНОКРАТНОЙ атаки; дрейф поднимает её НА КАЖДОМ релизе и потому держится годами.
Механизм — одно неравенство: захваченный bulk-бандл обслуживает не дольше
`TTL + grace`, а его содержимое (улицы ГАР) ротируется дважды в неделю. Пока окно
аренды меньше окна ротации, украденная копия протухает внутри своего же срока
годности — детектор течёт, и пиратство становится гонкой, а не разовой кражей
(тот же принцип, что ре-версии Denuvo; `research/2026-09-01-antitamper-nuitka.md`
§7 ход №4).

Единственный враг этого рычага за годы сопровождения — тихое «поставим TTL на
месяц, чтобы реже дёргать сервер»: это снимает защиту, а выглядит как удобство.
Поэтому потолок объявляется КОДОМ: `licensing/server.py` громко предупреждает на
старте, если `TTL + grace` превышает `_DRIFT_TTL_CEILING_SECONDS` (7 суток) — за
порогом захваченный бандл переживает ротацию и рычаг обнуляется. Дефолт
(TTL 24 ч + grace 48 ч = 3 суток) лежит под порогом с запасом; сокращение TTL
усиливает рычаг ценой нагрузки на `/v1/lease` (см. `metering-integrity.md`),
увеличение сверх недели — осознанное ослабление защиты, а не операционная мелочь.

## 4. Gate закрытия — только e2e на реальном локальном инстансе

### 4.1 Что не считается прохождением

Явный список, чтобы не было толкований:

1. **Юнит-тест вместо сценария.** Проверка `LicenseClient` с подменённым
   `httpx` не закрывает ни одного пункта. Каждый gate работает против реально
   запущенного контейнера по сети.
2. **Мок лицензионного сервера.** На стенде поднимается тот самый
   `licensing/` образ, который поедет в прод, — с укороченными TTL/grace, но с
   тем же кодом. Отдельная тестовая реализация сервера запрещена.
3. **Подмена времени внутри приложения.** Никаких тестовых хуков в
   `license.py`, ускоряющих часы. Время сжимается конфигом сервера; откат часов
   проверяется реальным переводом часов в контейнере.
4. **Ручной шаг.** `e2e/gates.py` запускается одной командой от чистого
   состояния и сам возвращает код выхода.
5. **Зелёный результат при неподнявшемся контейнере.** Каждый сценарий обязан
   сначала доказать, что нужное состояние достигнуто, и только потом
   проверять следствие.
6. **Прохождение на исходниках вместо образа.** Все gate этапа 2 гоняются по
   скомпилированному образу.

### 4.2 Стенд

```
e2e/
  compose.yml    license (TTL=60s, GRACE=120s, TLS self-signed) + sidecar
  gates.py       все сценарии, таблица PASS/FAIL, exit code
  fixtures.py    полезная нагрузка с ПД
```

Запуск: `docker compose -f e2e/compose.yml down -v && python3 e2e/gates.py`.

Сжатие времени (TTL 60 с, grace 120 с) — конфиг **сервера**, поэтому проверяется
ровно тот код, что работает на суточной аренде. Полный прогон ≈ 25 минут.

**Стенд не имеет права ломать машину, на которой запущен.** Первая версия L11
переводила часы через `cap_add: SYS_TIME` и `date -s`. Ядро не изолирует часы по
контейнерам: это сдвинуло часы всей Docker-VM и вместе с ними каждого чужого
контейнера на машине. Заменено на `libfaketime`, подмонтированный снаружи и
подключённый через `LD_PRELOAD`, — врёт только целевому процессу. Побочный
эффект: сценарий стал честнее, потому что моделирует враждебного клиента (тот,
кто хочет бесплатный grace, управляет окружением контейнера, а не нашим
Dockerfile), а `FAKETIME_DONT_FAKE_MONOTONIC=1` удерживает модель угрозы в
реальности — живое ядро не двигает `CLOCK_MONOTONIC` назад.

`fixtures.py` берёт **редкую фамилию, которой нет в seed-списке**, прямо из
исходника бандла — она служит маркером: если она найдена на диске контейнера,
значит активы утекли на диск.

### 4.3 Сценарии этапа 1 (лицензия)

| # | Сценарий | Как достигается | Что должно быть |
|---|---|---|---|
| **L1** | Без ключа не поднимается | `docker run` без `PSEUDEX_LICENSE_KEY` | exit code ≠ 0 в течение 30 с; в логе `license_missing`; порт 8000 не слушается |
| **L2** | С неизвестным ключом не поднимается | ключ, которого нет в БД сервера → 403 | exit ≠ 0, `license_invalid`, ни одного успешного `/mask` |
| **L2b** | Ключ проверки нельзя подменить снаружи | валидный ключ + `PSEUDEX_LICENSE_PUBKEY` = мусор | контейнер поднимается и арендует **как обычно** — переменная игнорируется, потому что ключ вкомпилирован. Если бы её читали, клиент поднял бы свой сервер, подписал свой бандл и жил бы с отменённой подпиской вечно |
| **L3** | Холодный старт при недоступном сервере | `compose stop license`, затем старт сайдкара | exit ≠ 0. Grace на холодном старте не применяется |
| **L4** | Happy path | валидный ключ | `/health` = `license: active`; `/mask` маскирует ФИО, телефон, СНИЛС, карту, адрес; `/unmask` возвращает исходную форму; tool-call round-trip проходит |
| **L5** | Бандла нет на диске | 200 вызовов `/mask` | `docker diff` не показывает новых файлов вне `/data`; `grep -rF "<маркерная фамилия>" /` → 0 совпадений; `ls /app/pseudex/data` → нет каталога; грепом покрыт и смонтированный том |
| **L6** | Продление не рвёт обслуживание | 5 минут нагрузки при TTL=60 с | ≥3 продления в логе; 0 ошибок `/mask`; **тот же вход даёт тот же токен до и после продления** (доказывает, что бандл не подменился) |
| **L7** | Grace: работа при нашей недоступности | `compose stop license` под нагрузкой | `/mask` работает; `/health` = `stale` с убывающим `grace_left_s`; WARNING в логе |
| **L8** | Grace истёк → 503 | ждём 120 с после L7 | `/mask` → 503 `license_expired`; `/health` → 503; в теле ответа нет ПД |
| **L9** | Восстановление без рестарта | `compose start license` после L8 | в течение одного интервала продления `/mask` снова 200, тот же контейнер, тот же PID |
| **L10** | Отзыв бьёт мимо grace | `POST /admin/revoke` под нагрузкой | на первом же продлении → `license_revoked`; **немедленно** 503, без 120 с grace |
| **L11** | Откат часов не продлевает grace | `libfaketime` через `LD_PRELOAD`, подсунутый монтированием; в состоянии `STALE` файл смещения переписывается на `-72h` | процесс видит время на 72 ч назад (проверяется отдельно), но grace истекает по монотонным часам в срок |
| **L12** | Счётчики совпадают и не содержат ПД | известное число `/mask` с известными сущностями | агрегаты на сервере = `audit.counts()` сайдкара; грепом по телу запроса (сервер пишет сырое тело на стенде) нет ни одного значения из `fixtures.py` |
| **L13** | Порча бандла = отказ, не деградация | флаг сервера «испортить один байт шифротекста» | `bundle_corrupt`, процесс не обслуживает; ни одного ответа `/mask` с немаскированным текстом |
| **L14a** | Сканер памяти вообще работает | под действующей арендой | маркерная фамилия **находится** в памяти воркера. Без этого L14b бессмыслен: сканер, который не умеет находить, объявит чистым любой процесс |
| **L14b** | Активы отданы **живым** процессом | после L8 | тот же PID продолжает работать, `/license` показывает `assets_loaded=false`, `/mask` и `/spans` отдают 503, а `/unmask` — 200. Это и есть отличие «отдал активы» от «упал» и от «поднял флаг»: упавший процесс тоже перестал бы детектить |

**Чего L14b не утверждает — и почему.** Обе проверки были написаны до замера и
замером опровергнуты:
- **байтов нет в памяти** — `free()` не затирает, освобождённые страницы хранят
  содержимое до переиспользования. Затирание строк CPython недостижимо, поэтому
  обещать его нельзя ни в тесте, ни клиенту;
- **RSS падает на объём газеттиров** — аллокатор CPython возвращает арену ОС
  только когда она пуста целиком, а 225 тыс. коротких строк размазаны по аренам
  с живыми объектами.

Обе величины замерены на **одном и том же образе в двух прогонах**: «освобождено
2 МБ, 3 региона с маркером» и «освобождено 76 МБ, 0 регионов». Разброс задаёт
посторонний трафик, перетасовавший кучу, — то есть утверждение на любом из этих
чисел мерило бы везение, а не поведение продукта. Оба остаются в выводе гейта как
наблюдения, но ни одно ничего не решает.
| **L15** | В логах нет ПД | после всех сценариев | `docker logs` грепом по всем значениям `fixtures.py` → 0 |

### 4.4 Сценарии этапа 2 (упаковка)

| # | Сценарий | Как достигается | Что должно быть |
|---|---|---|---|
| **P1** | Ни исходников, ни прозы | `find` по образу + `grep -a` по бинарнику на 2 докстринга и 2 конструкции кода | нет наших `.py`/`.pyc`, нет каталога `pseudex/`, и ни одна из проб не находится в бинарнике. Имена символов и пути модулей — остаются, это принято (§3.4) |
| **P2** | Константы не вынимаются | `grep -a` по всему `/app` (не `strings`: в debian-slim нет binutils, а `strings` читает однобайтовые кодировки и на кириллице объявил бы чистым любой бинарник) | ни одна **однозначно наша** строка не найдена. Пробы — только авторские: исходник адресного регэкспа, составной ключ `контактныйтелефон`, cue-фраза `появил на свет`, маркерная фамилия из бандла. Общие слова пробами быть не могут: «саша» нашлась в `natasha/data/dict/first.txt` — это собственный словарь natasha, чужой открытый артефакт, — а «мира» ловилась как подстрока обычных слов. Провал → покупаем Nuitka Commercial с `data-hiding` |
| **P3** | Функциональный паритет | весь набор (`test_loop`, `test_product`, `test_coverage_152fz`, `vault_test`, `eval_dirty`) прогоняется **по HTTP против скомпилированного контейнера** | результаты совпадают с прогоном на исходниках до последней цифры: 23/23 типа, 0 из 7 ложных, 0 утечек, метрики dirty без изменений |
| **P4** | Паритет производительности | 60 замеров `/mask` на каждый образ, разбитые на два блока | p50 не хуже границы, **выведенной из шума этого же прогона**: два блока одного образа дают собственный разброс, граница = `max(1.25x, шум × 2)`. p95 — только наблюдение |

**Почему порог не фиксированный.** Первая версия требовала «не хуже 10% по p50 и
p95». Три прогона на неизменённом коде дали отношения p50 **0.82x, 0.94x,
1.16x** — знак меняется от запуска к запуску, потому что на машине крутится
десяток чужих контейнеров, а один прогон шёл сразу после девятиядерной сборки.
Порог 10% лежит ниже этого разброса, то есть гейт проходил или падал по везению,
а не по свойствам бинарника. Теперь шум измеряется в самом прогоне и задаёт
границу; на практике это ~2.5x, то есть гейт ловит крупную регрессию и честно не
претендует различать мелкую. p95 по 60 замерам — это три точки, он сдвигается от
одного затыка и утверждение нести не может. Та же дисциплина, что с L14b: не
утверждать на числе, разброс которого не измерен.
| **P5** | N процессов реально работают | `SO_REUSEPORT`, N=8, нагрузка в 16 соединений | 0 таймаутов; `/health` отвечает < 100 мс под нагрузкой; работа распределена минимум по 6 из 8 процессов (считается по логам/метрикам на процесс) |
| **P6** | Registry и подпись | локальный `registry:2` с htpasswd на порту **5555** (не 5000 — на macOS он занят ControlCenter/AirPlay); cosign из официального образа | анонимный push отклонён, push с кредами проходит, образ подписан, `cosign verify` своим ключом проходит, чужим — отвергается. Креды передаются cosign **флагами**, а не монтированием `~/.docker`: на macOS там лежит только `credsStore: desktop`, а секрет в keychain, до которого Linux-контейнер не дотянется |
| **P7** | Все сценарии L1–L15 на скомпилированном образе | повтор §4.3 | без исключений; отдельно проверяется L14 (выгрузка активов из памяти скомпилированного процесса) |
| **P8** | Бюджет старта и размера | замер | холодный старт до первого успешного `/mask` < 20 с; размер образа < 1.5 ГБ |

### 4.4b Что эти сценарии уже нашли

Список ведётся не для отчётности, а потому что каждая строка — довод в пользу
того, что гейт должен быть e2e, а не юнит-тестом. Ни один из этих дефектов не
виден в коде при чтении.

| Нашёл | Дефект |
|---|---|
| L1/L2 | `entrypoint.sh` возвращал **0**, когда единственный воркер умирал от лицензионной ошибки. Для оркестратора это выглядит как штатное завершение — контейнер «успешно» не работал |
| L6 | аренда продлевалась исправно и **молча**: `service.py` вообще не настраивал logging, поэтому все INFO-строки терялись. Единственный способ клиента увидеть живую подписку — этот лог |
| L14a | сканер памяти искал UTF-8 там, где CPython держит строку как UCS-2, и не мог найти ничего никогда. Без L14a гейт L14b «проходил» бы всегда |
| L5 | два воркера на пустом томе гонялись за `PRAGMA journal_mode=WAL`; `busy_timeout` этот случай не покрывает |
| — | счётчики: клиент шлёт **накопительный** итог на каждое продление, а сервер их суммировал. На суточной аренде это завысило бы месячный счёт в 30 раз; N воркеров одного контейнера умножали бы его ещё на N |
| — | `engine_version` сравнивался как строка: `"1.10.0" < "1.9.0"`, то есть первый же релиз с двузначным minor был бы объявлен устаревшим |
| P1 | **докстринги ехали в бинарнике** несмотря на `--python-flag=no_docstrings` — а в них весь проектный журнал (§3.4) |
| P1 | `grep -c` печатает `0` **и** возвращает код 1, поэтому `\|\| echo 0` дописывал второй ноль отдельной строкой — гейт «находил» утечку на чистом бинарнике. Проверено контрольной пробой: гейт обязан уметь падать |
| P4 | порог был задан вкусом (10%), а не измерением — ниже собственного шума машины |

### 4.4c Что нашло ревью, а гейты — нет

Все гейты были зелёными, когда код-ревью нашло восемь дефектов, три из них
серьёзные. Это не упрёк гейтам, а описание границы их применимости, и её стоит
держать в голове при добавлении новых сценариев.

**Гейт проверяет наблюдаемое поведение. Ревью читает механизм.** Отсюда весь
список:

| Дефект | Почему гейт молчал |
|---|---|
| `_TERMINAL_RETRY_SECONDS` не определена — `NameError` убивал поток лицензии при первом отзыве | L10 проверял, что сервис встал. Он вставал: `_terminal_code` выставляется до падения, а состояние читается из него. Мёртвый поток снаружи неотличим от живого |
| Пул LOC — 33 значения, IP — 254; 34-й адрес клиента давал вечный 5xx | тест на исчерпание пула был написан только для NAME, где пул комбинаторный. Гейты гоняют один и тот же адрес |
| Неизвестный статус ключа → `KeyError` → 500 → **grace на 48 часов**, рубильник отказывает открыто | у гейта нет сценария с повреждённой строкой в БД |
| `trim_person_span` схлопывал пробелы, маска съезжала, в модель уходил хвост настоящей фамилии | в тестовых данных нет двойных пробелов и переносов внутри имени |
| Шесть типов документов не попали в `_NUMERIC_TYPES` — переформатированный номер не восстанавливался | round-trip проверялся на телефоне |
| `billing_totals()` читал общее соединение без блокировки из потока лицензии | видно только под гонкой |
| Токены-эхо тарифицировались повторно | счётчики никто не сверял с ожидаемым числом |
| Дубликат в таблице глифов — греческая омикрон отсутствовала | обфускация проверялась кириллицей |

**И два дефекта нашлись уже после ревью, при перепроверке.**

Первый — **`database is locked` под нагрузкой**, 46 отказов из 64 при четырёх
воркерах на свежем томе. P5 показывал это и раньше, но выводил только счётчик
неудач, и легко было списать на занятость машины. Как только гейт стал писать
ПРИЧИНУ, стало видно `HTTP 500`, а не таймаут — то есть отказ сервера, а не
контеншен. Корень: аудит делал `INSERT`+`commit` на каждый найденный спан
(комментарий в коде отмечал это как будущую оптимизацию), и восемь сущностей на
сообщение при четырёх процессах превращались в шторм записи. Исправлено тремя
изменениями: одна транзакция на сообщение вместо одной на сущность,
`PRAGMA synchronous=NORMAL` (штатный режим для WAL), `busy_timeout` 5 → 15 с.
После — 128 из 128 успешны.

Отдельный урок: **счётчик отказов без причины провоцирует догадку.** Формулировка
«наверное, контеншен» звучит правдоподобно и закрывает вопрос, поэтому гейт
обязан отличать «машина занята» от «сервис ответил 500».

Второй — **около 1%
фейковых телефонов проходят контрольную сумму СНИЛС. Тогда при повторной встрече
СНИЛС выигрывает по приоритету, страж повторного маскирования промахивается
(детекция отдаёт цифры без `+`, а в токене он есть), и номер человека меняется
посреди диалога. Правило «токен обязан быть невалидным экземпляром своего типа»
существовало и применялось к СНИЛС, ИНН и картам — но не к телефону, у которого
та же длина. Правило переформулировано: **токен не должен быть валидным
экземпляром НИКАКОГО типа.**

Вывод для практики: каждый закрытый дефект получил тест, а L10 расширен до
проверки возврата после оплаты — половины сценария, которой не было и которая
только и могла поймать мёртвый поток.

## 5. Порядок работ

### Этап 1 (5–7 рабочих дней)

1. `licensing/pack.py` + `pseudex/bundle.py` — формат и сборка бандла (0.5 дня)
2. `pseudex/assets.py` + перенос констант из 8 модулей; регрессия по всему
   набору тестов и evals после каждого модуля (2 дня — самая рискованная часть)
3. `licensing/` сервер: аренда, отзыв, счётчики, админка (1 день)
4. `pseudex/license.py`: ключ процесса, цикл продления, машина состояний (1 день)
5. Интеграция в `service.py`/`proxy.py`, коды ошибок, `/license` (0.5 дня)
6. `e2e/` стенд и сценарии L1–L15 (1–2 дня)

### Этап 2 (4–5 рабочих дней)

1. `SO_REUSEPORT`-лаунчер и проверка N процессов **на исходниках** — сначала
   убедиться, что схема работает, и только потом компилировать (0.5 дня)
2. Сборка Nuitka, вычистка того, что не собралось (1–2 дня — здесь всегда
   всплывает неожиданное с natasha/pymorphy3)
3. Многостадийный Dockerfile, бюджет размера и старта (0.5 дня)
4. Registry, cosign, инструкция клиенту (0.5 дня)
5. Прогон P1–P8 плюс полный повтор L1–L15 на скомпилированном образе (1 день)

**Порядок между этапами не переставляется.** Компилировать до того, как активы
уехали в бандл, — значит компилировать то, что после переноса придётся
компилировать заново, и отлаживать сборку и рефакторинг одновременно.

### Что оказалось дороже и дешевле оценки

- **Перенос активов (2 дня по оценке)** — риск оправдался, но не там, где ждали:
  сам перенос механический, а стоила времени одна деталь — единый `re.IGNORECASE`
  на все адресные паттерны. Метрики не «немного просели», а потеряли 12 упоминаний
  PERSON, причём через LOC: раздутые адресные спаны перекрывали имена по
  приоритету. Ловится только полной регрессией, не чтением диффа.
- **Сборка Nuitka (1–2 дня по оценке)** — заняла часы, но выдала три отдельных
  дефекта подряд (glibc между стадиями, динамически импортируемый
  `pymorphy3_dicts_ru`, вырезанный anti-bloat'ом `_json`). Каждый проявляется
  только при запуске собранного образа, ни один не виден в конфиге сборки.
- **Гейты** — половина найденных дефектов оказалась в самих гейтах, а не в
  продукте. Это не потеря: гейт, который не может упасть, хуже отсутствующего,
  и все четыре таких случая (UTF-8 против UCS-2, порог RSS взятый с потолка,
  ожидание первого отчёта вместо отчёта с данными, общие слова как пробы) были
  найдены именно потому, что каждый сценарий обязан доказать предусловие.

## 6. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Перенос констант в бандл сдвинет метрики детекции | средняя | после каждого модуля — полный прогон evals; расхождение = откат этого модуля, а не «уточнение» |
| Nuitka не соберёт natasha/slovnet | **не реализовался** | `--include-package-data` хватило; бинарник собрался за ~290 с из 1040 C-файлов |
| Пакет, импортируемый динамически, приедет без кода | **реализовался** | pymorphy3 находит `pymorphy3_dicts_ru` через entry point, статический анализ этого не видит. С одним `--include-package-data` пакет приезжает без `__init__.py`, и бинарник умирает на старте: `module 'pymorphy3_dicts_ru' has no attribute 'get_path'`. Нужны **оба** флага — и на код, и на данные |
| Разъехавшийся glibc между стадиями сборки | **реализовался** | `python:3.12-slim` уехал на trixie (glibc 2.41), а runtime был прибит к `debian:12-slim` (bookworm, 2.36) — бинарник не стартовал: `version GLIBC_2.38 not found`. Плавающий тег молча изменился под прибитым. Обе стадии теперь указывают релиз явно |
| `SO_REUSEPORT` даст неравномерность на пуле keep-alive | средняя | балансировка ядра уже подтверждена замером на Linux (§3.2); открытым остаётся только поведение на длинных keep-alive-соединениях — измеряется в P5, запасной вариант nginx |
| `pyrage` (Rust-расширение) плохо ляжет в standalone | низкая | падаем на `cryptography` с X25519+HKDF+AESGCM, ценой того, что композицию пишем сами |
| 503 как рычаг отпугнёт крупного клиента | высокая при продаже | режим «последний бандл без обновлений» вынесен в одну функцию; включается как коммерческая уступка |
| Клиент занижает счётчики | средняя | признаём открыто: рычаг — аренда, а не подпись счётчиков |
| Стенд ломает машину разработчика | **реализовался** | `cap_add: SYS_TIME` сдвинул часы всей Docker-VM; заменено на `libfaketime` (§4.2). Правило: сценарий не имеет права менять состояние, разделяемое с чужими контейнерами |
| Гонка N воркеров на пустой БД | **реализовался** | `PRAGMA journal_mode=WAL` возвращает `SQLITE_BUSY` сразу, не вызывая busy handler, — `busy_timeout` его не покрывает. Переключение ретраится вручную (`pseudex/sqlite_setup.py`) |
| Гейт «зелёный», потому что ничего не проверил | **реализовался дважды** | сканер памяти искал UTF-8 там, где CPython держит UCS-2, и не мог найти ничего никогда; entrypoint возвращал 0 при упавшем воркере. Отсюда правило §4.1: каждый сценарий сначала доказывает предусловие |
