## 1. Модель поставки

**Obscura ставится в контур клиента как сайдкар. На нашем железе не крутится
ничего, кроме платформы лицензий и приёма счётчиков.**

Это решение одновременно техническое и юридическое. Как только ПД пойдут через
наш сервер, мы становимся обработчиком по поручению (ст. 6 ч. 3 152-ФЗ) со всей
ст. 19: модель угроз, аттестация, уведомление РКН, ответственность перед
оператором. Для ИП это неподъёмно. В сайдкар-схеме мы **не участник обработки**:
ПД к нам не поступают ни в каком виде.

Модель LLM выбирает клиент (OpenAI, OpenRouter, свой GPU) — мы модель-нейтральны.
Модели детекции (Natasha NER + pymorphy3) едут внутри нашего образа.

## 2. Защита и лицензирование

Две независимые линии. Ни одна не самодостаточна, вместе — работают.

### 2.1 Аренда detection-бандла (первая линия, делать первой)

Образ содержит **только движок**. Активы детекции — газеттиры, правила, regex-паки,
таблица приоритетов, веса NER — на диск клиента не попадают никогда.

```
старт контейнера
  → POST /bundle с API-ключом
  → получает зашифрованный detection bundle (аренда ~24 ч)
  → расшифровывает В ПАМЯТЬ, на диск не пишет
  → работает
каждые 24 ч → продлевает аренду
```

Направление потока — **от нас к клиенту**. Никакие ПД в обратную сторону не идут,
поэтому схема не делает нас обработчиком.

Почему это сильнее обычной проверки лицензии: локальную проверку ломает патч
одного условия. Здесь ломать нечего — недостающая часть физически отсутствует на
диске. Взломанный бинарник детектит нечем.

### 2.2 Ключ — API-ключ, НЕ JWT

**Решение: непрозрачный API-ключ без вшитого срока.**

JWT отвергнут сознательно: это локально проверяемое утверждение, и кто владеет
валидатором — подделает подпись, вписав себе вечный `exp`. Публичный ключ,
вкомпиленный в образ, патчится.

API-ключ на стороне клиента **не проверяется вообще** — он предъявляется нам, чтобы
получить бандл. Срок живёт не в ключе, а в аренде, которую выдаём мы. Подделывать
нечего.

### 2.3 Лестница деградации

```
аренда активна            работает
не продлилась, 0–48 ч     работает на бандле в памяти, WARNING в лог
не продлилась, 48 ч+      бандл выгружается → /mask отдаёт 503
рестарт без валидного ключа   не поднимается
```

Grace 48 ч — чтобы не уронить клиента из-за задержки платежа в пятницу.

`503` работает как рычаг именно потому, что система **fail-closed**: без
маскирования шлюз клиента обязан не пропускать запрос, иначе он льёт ПД в модель.
Остановка сайдкара останавливает агентов клиента.

⚠️ Риск, который надо держать в голове при продаже: это делает нас single point of
failure для бизнеса клиента. Юрист крупного клиента потребует escrow или
perpetual fallback. Готовый компромисс — деградация до «работает на последнем
бандле без обновлений» вместо полной остановки.

### 2.4 Нечитаемость кода (вторая линия)

- **Nuitka** — компиляция Python в C, дальше в нативный бинарник. Не байткод.
  `--standalone --onefile`, символы снять.
- **PyArmor** вторым слоем — шифрование байткода, анти-отладка.
- Вырезать docstring'и, отключить `__pycache__`. Cython на горячие модули (после
  профилирования, см. §4).

Планка: прочитать `.py` — минуты; разобрать нативный бинарник — недели.

**Почему нужны обе линии.** Обфускация — это секрет: держится, пока держится, а
при утечке исходников пропадает навсегда и сразу для всех проданных копий. Аренда
бандла такого обрыва не имеет: украли сегодняшний бандл — завтрашнего не получат,
копия протухает, а устаревший детектор на PII-шлюзе начинает течь.

**Rust — отвергнут.** Актив продукта не в коде, а в качестве детекции, которое живёт
в правилах, газеттирах и в Natasha/pymorphy3 — питоновских по природе.
Переписывание = пересборка всего NER-стека с нуля, полгода, и выбрасывает ровно то,
что составляет моат. Nuitka даёт нативный бинарник без этой цены.

### 2.5 Монетизация

Подписка, не разовая продажа. Аренда бандла — 24 ч, ключ живёт до отзыва.

Счётчики уже есть (`audit.counts()`). Вместе с продлением аренды уходят **только
агрегаты**:

```json
{"org_id": "acme", "period": "2026-08", "requests": 184203,
 "entities": {"PHONE": 12043, "NAME": 8871, "LOC": 3310}}
```

Ни байта ПД. Подписано ключом инстанса, чтобы не занизили. Тариф: база + переплата
за объём сверх лимита. Не доходит телеметрия N дней — деградация как при неоплате.

Расчёты с юрлицами безналом на р/с ККТ не требуют — касса не нужна, пока не идём в
физлиц.

Образ раздаётся из приватного registry с выданными клиенту кредами.

## 3. Бенчмарк

Задача — измерить не «ловим ли ПД» (это меряют `eval_detect`/`eval_dirty`), а
**«не ломаем ли агента»**. Отвечает только парный прогон: один сценарий, один seed,
одна модель — с Obscura и без. Главное число: **Δtask-success ≈ 0 при leak = 0**.

Модель для прогонов — **`deepseek-v4-flash`**. Выбор модели оказался не деталью, а
условием работоспособности замера: нужна такая, которая решает ЧАСТЬ задач сама.
Слишком слабая (`gpt-4o-mini` — 21% на `multi_turn_base`) даёт сплошной both-fail и
мерить нечего; слишком сильная упирается в потолок бенчмарка и Δ размазывается в шум.
DeepSeek даёт 58–62% — это рабочий диапазон. Плюс он дёшев и умеет префиксный кеш,
на котором проверяется стабильность токенов (§3.3b).

### 3.1 Выбор харнесса

| | роль | почему |
|---|---|---|
| **BFCL v3 multi-turn** | основной | Apache-2.0. **Нет симулированного пользователя** — реплики скриптованы, значит единственный источник случайности — модель агента, и Δ атрибутируется middleware. Сравнение — сырое `!=` по атрибутам с машиночитаемым диффом: видно, какое поле испорчено. Прокси — одна переменная `OPENAI_BASE_URL`. Категория `memory` (155 задач, эталон — имя человека) — готовый зонд на round-trip |
| **τ³-bench telecom** | вторичный | MIT. Единственный с мульти-тёрном, где пользователь держит ПД и выдаёт по частям — там маскирование должно ломаться сильнее всего. И единственный, где прокси вешается на агента, **не задевая симулятор** (`--agent-llm-args` отдельно от `--user-llm-args`). Домен telecom: оценка 100% детерминированная, БД — 4 клиента в TOML |
| WorkBench | опционально | MIT, 690 бизнес-сценариев. Перекрывается с BFCL |

**Отвергнуты:** CRMArena (LLM-судья + CC BY-NC, некоммерческая), ToolSandbox
(репозиторий из одного коммита, лицензия Apple без патентного гранта, ROUGE-L
возвращает 0.0 на кириллице → русская локализация обнуляет оценку), API-Bank
(teacher-forced, БД пересоздаётся перед каждой проверкой — траектория не может
разойтись), τ1 tau-bench (объявлен устаревшими авторами, ~38% задач проходит агент,
который ничего не делает).

Исключить внутри выбранных: BFCL `web_search` (платный SerpAPI + живой интернет →
непарные прогоны), τ³ airline (~46% задач «ничего не делай и выиграй») и τ³ retail
(98% оценки на англоязычном LLM-судье, который сам среагирует на маскированные имена).

### 3.2 Метрики

**Безопасность.** `leak@wire` — обязан быть 0. Считать по канонизированному значению
во всех форматах, не substring по сырому. Проверять все ноги: system, messages,
схемы тулов, `role:tool`, SSE-чанки.

**Достоверность петли.** `arg_exact`; round-trip при перефразировании; cross-session;
multi-entity. Отдельно — **`wrong_entity_rate`**: тул вызван с валидным, но **чужим**
значением (списали с чужой карты, отменили чужой заказ). Для бизнеса это страшнее
утечки, и обычный `arg_exact` это маскирует. Прямой кандидат в источники —
digit-signature реиндекс в `vault.resolve_digit_signatures()`.

**Полезность.** Δtask-success; over-mask на негативах; **`reasoning_damage`** — набор,
где модели нужно содержимое ПД («мобильный или городской», «в каком городе адрес»).
Эти кейсы обязаны провалиться — измеряем размер дыры честно, а не прячем. Плюс
Δturns, Δtokens, Δlatency p50/p95.

### 3.3 Первый парный прогон — результат и выводы

Сделано: BFCL склонирован (Apache-2.0), зарегистрированы две модели-близнеца
`obscura-control-FC` / `obscura-masked-FC` — различаются ТОЛЬКО тем, куда смотрит
`OPENAI_BASE_URL`, поэтому пишутся в разные деревья результатов. Модель
`gpt-4o-mini` через OpenRouter, категория `multi_turn_base`, 19 парных задач.

| | |
|---|---|
| control | 21.1% (4/19) |
| masked | 26.3% (5/19) |
| Δ task sensitivity | −5.3% |
| both pass / DAMAGED / recovered / both fail | 3 / 1 / 2 / **13** |

**Эти цифры НИЧЕГО не измеряют, и это главный вывод.** Три задачи поменяли исход
в обе стороны, чистая Δ — одна задача, то есть внутри шума (`compare_arms.py` сам
это и написал). Единственная DAMAGED упала с `multi_turn:inference_error` — сбой
инфраструктуры, не смысловая поломка маскирования.

Что нужно поправить в дизайне замера:

1. **13 из 19 — both fail.** gpt-4o-mini слишком слаб для `multi_turn_base`, и 68%
   выборки не несут сигнала вообще; эффективное n ≈ 6. Нужна либо модель посильнее
   (gpt-4o — ожидаемо 40–50%, плотность сигнала выше при сохранении запаса), либо
   более лёгкая категория, либо и то и другое. Не «просто больше задач».
2. **n=19 мало в любом случае.** Полный `multi_turn_base` — 200, с
   `multi_turn_miss_param` — 400.
3. **Английские данные BFCL почти не триггерят детектор** — 8 срабатываний на 1927
   вызовов. То есть эта Δ измеряет накладные расходы прокси-хопа, а НЕ маскирование.
   Подстановка русских ПД в `initial_config` + `question` + `possible_answer` — не
   опция, а условие осмысленности замера.
4. Исключить `web_search` (платный SerpAPI + живой интернет → непарные прогоны).

**Что прогон дал сразу — два реальных бага** (см. §3.4). Ради этого его и делали:
внешний бенчмарк бьёт по местам, которых наши собственные наборы не покрывают.

### 3.3b Второй прогон — DeepSeek v4-flash, n=29 парных

Модель `deepseek-v4-flash` (`https://api.deepseek.com`), 40 задач запущено, 29
доехало в обеих руках.

| | |
|---|---|
| control | 58.6% (17/29) |
| masked | 62.1% (18/29) |
| Δ task sensitivity | −3.4% |
| both pass / DAMAGED / recovered / both fail | **15** / 2 / 3 / 9 |
| кеш префикса через Obscura | **97.8%** (699 008 hit / 15 991 miss) |
| накладные расходы Obscura | **1.7%** времени запроса |

**Смена модели починила замер.** Было 13 из 19 both-fail на gpt-4o-mini — теперь 15
задач проходят в контроле, то есть появилось где увидеть ущерб. Δ по-прежнему
нестабильна (5 задач поменяли исход в обе стороны при чистой дельте в одну), так что
для вывода нужен больший n и несколько сидов — но плотность сигнала уже рабочая.

DAMAGED сломались осмысленно, а не по таймауту: `instance_state_mismatch` и
`execution_response_mismatch` — то есть расхождение конечного состояния и ответа
инструмента. Это то, что можно вскрывать.

**Кеш префикса — отдельный продающий результат.** У DeepSeek вход по кешу стоит
$0.0028/M против $0.14/M мимо кеша (в 50 раз). Кеш требует ПОБАЙТОВОГО совпадения
префикса, то есть нестабильный маскировщик отнял бы у клиента весь выигрыш. Мы
сохраняем 97.8%. Учёт встроен в прокси (`_record_prefix_cache`), видно в `/profile`.
Метрика двойного назначения: падение hit-rate = токены перестали быть стабильными,
то есть это ещё и сигнал корректности.

Особенность DeepSeek: reasoning-модель **не принимает `tool_choice="required"`**.
BFCL его не шлёт, но в своих харнессах учитывать.

### 3.3c ПЕРВЫЙ ВАЛИДНЫЙ ЗАМЕР — русские ПД в петле, n=50

`deepseek-v4-flash`, BFCL `multi_turn_base` ids 150-199 (TravelAPI), русские ПД
подставлены согласованно в вопрос + начальное состояние + эталон
(`bench/inject_ru_pii.py`), так что значения ОБЯЗАНЫ пройти через вызовы
инструментов дословно.

| метрика | значение |
|---|---|
| control | 54.0% (27/50) |
| masked | 46.0% (23/50) |
| **Δ task sensitivity** | **+8.0 п.п.** |
| both pass / DAMAGED / recovered / both fail | 19 / 8 / 4 / 19 |
| **leak@wire** | **0** из 180 значений на 10 526 сообщениях |
| **кеш префикса** | **96.9%** сохранён |
| накладные расходы | **1.5%** времени запроса |
| таймауты | 0 |

Почему этому замеру можно верить, а предыдущим — нет: все восемь DAMAGED упали
СЕМАНТИЧЕСКИ (`execution_response_mismatch`, `instance_state_mismatch`), ни одного
`inference_error`. В прошлом прогоне было ровно наоборот — 19 из 19 инфраструктурных,
то есть мерялись таймауты, а не маскирование.

Δ пока не стабильна: 12 задач поменяли исход при чистой дельте в 4, харнесс это сам
и пишет. Нужен больший n и несколько сидов. Но порядок величины — единицы процентов,
а не десятки, и это принципиально: **у Presidio в PrivScope было −14…−26 п.п.**

Утечка — главный результат. 0 на 10 526 сообщениях при каноническом сравнении
(переформатированный номер тоже поймался бы), при этом покрытие полное: значения
реально ездили по проводу, а не лежали без дела.

Кеш префикса 96.9% означает, что токены побайтово стабильны между ходами — иначе
префикс бы не совпадал. Это одновременно и экономика клиента (вход по кешу в 50 раз
дешевле), и датчик корректности.

### 3.4 Баги, найденные первым прогоном

**(а) Имена файлов маскировались как ФИО — ИСПРАВЛЕНО.** Слой structured-KV
типизирует значение по ключу, а `name` в английском JSON значит «имя вещи»:

```
'log.txt' -> 'Полина Жукова'   'ideas.txt' -> 'Вера Котова'
'TeamNotes.txt' -> 'Артур Лебедев'   'test' -> 'Роман Тихонов'
```

Агенту переписывали его же аргументы, ломая задачи без всякого отношения к ПД.
Фикс НАРОЧНО узкий: отбрасывается только значение, похожее на имя файла или путь —
там ошибка невозможна, цена по recall нулевая. Более широкий вариант («значение
должно выглядеть как имя человека») был отвергнут: существующий тест поймал, что
он перестаёт маскировать `{"name":"johnsecret"}`, то есть меняет утечку на
точность — задом наперёд для fail-closed. Неоднозначные слова (`test`, `config`)
остаются замаскированными сознательно. Закреплено
`test_perf_masking.py::test_generic_name_key_does_not_over_mask`.

**(в) Маскирование СОБСТВЕННОГО токена — ИСПРАВЛЕНО. Самый опасный из трёх.**

Фейковое NAME/LOC по построению является корректным именем или местом, поэтому
когда мульти-тёрн агент возвращает токен внутри НОВОГО текста, детектор находит его
снова:

```
Иван Петров   → Глеб Сорокин
Глеб Сорокин  → Полина Жукова      ← маскируем свою же подмену
детокенизация → Глеб Сорокин       ← вернулся ТОКЕН, не реальное значение
```

Последствия по убыванию тяжести: инструмент исполняется на правдоподобном, но
**чужом** значении (ровно `wrong_entity`); личность человека меняется каждый ход;
префиксный кеш провайдера умирает, потому что префикс перестаёт быть стабильным.

Числовые типы от этого защищены невалидной контрольной суммой — имена и места нет.
Утверждение в `maskcache.py`, что токены «никогда не ретриггерят детекцию», было
верно только для числовых.

Почему не ловили тесты: тест на идемпотентность маскирует один и тот же СЫРОЙ текст
и попадает в кэш контента. Баг проявляется только когда токен приходит внутри
другого окружения — то есть ровно то, что делает настоящий агент.

Фикс: `Vault.is_minted_token()` — спан, значение которого уже является выданным нами
токеном, не маскируется повторно. Закреплено
`test_product.py::test_masking_own_token_is_stable`.

⚠️ Известное ограничение: реальный человек, чьё имя в точности совпадёт с выданным
фейковым именем, пройдёт без маскирования. Нужен пул фейковых имён на порядки
больше нынешнего seed-списка — та же production-замена словарей, что уже
запланирована в `names.py`.

**(б) Прокси зависает на 97% CPU под реальным агентным трафиком — ИСПРАВЛЕНО.**

Причина: SQLite. При конкурентном доступе он отдавал `database is locked`, а
python-sqlite3 в это время не ждёт пассивно, а **опрашивает в цикле** до таймаута —
чистый CPU без полезной работы. Отсюда 97% загрузки, кадры `pysqlite` в стеке и
полная остановка прогона.

Фикс: общий `obscura/sqlite_setup.py` — WAL (читатели не блокируют писателя) плюс
явный `busy_timeout`, применяется ко всем трём хранилищам.

Исторически (диагностика, которая к этому привела):
Воспроизводится на длинных multi-turn транскриптах. Установлено замерами:

- это НЕ детекция и НЕ маскирование: `mask.one` замирает, суммарно 455 мс на 8885
  вызовов, кэш даёт 92% попаданий
- это НЕ детокенизация: `unmask.total` — 2 мс на 130 вызовов
- это НЕ upstream: ноль открытых соединений к провайдеру, лог не растёт
- стек: чистый Python (`_PyEval_EvalFrameDefault`), остальные треды ждут лока
- гипотеза о катастрофическом бэктрекинге `_NUM_RUN` **проверена и опровергнута**

Весь путь прокси теперь размечен стадиями (`proxy.tenant`, `proxy.parse_body`,
`proxy.log_upstream`, `proxy.upstream_call`, `proxy.unmask_response`,
`proxy.serialize`), поэтому следующий затык диагностируется своими цифрами, а не
внешним сэмплером. На прогоне DeepSeek: 308 с в `proxy.upstream_call` (ожидание
модели) против 5.2 с во всём маскировании.

### 3.5 Что строим сами

**Детектор утечки на проводе.** Подтверждено независимо: WorkBench не оценивает
read-операции вообще, BFCL сравнивает состояние и ответы, τ³ инструментирует утечку
симулятора пользователя, а не агента. Готового нет ни в одном харнессе.

**Примитив minefield** (идея из ToolSandbox, сам харнесс не берём): если в траектории
случилось запрещённое — вся траектория обнуляется независимо от результата. Ровно
форма нашего требования «сырые ПД пересекли провод → задача не засчитана, даже если
выполнена».

### 3.6 Формат значения, отдаваемого инструменту — РЕШЕНО

**Инструмент получает значение ровно в той форме, в какой его написал
пользователь.** Канонизация остаётся, но только как ключ дедупликации.

Довод: без Obscura в цепочке инструмент получил бы собственную строку
пользователя. Возвращать переформатированную — это наблюдаемое изменение
поведения, которое навязываем мы. CRM, сверяющая телефон точным сравнением строк,
просто не найдёт запись.

Плюс это ломало бы сам бенчмарк: все детерминированные верификаторы сравнивают
значения точно (BFCL — сырое `!=` по атрибутам, τ³ — равенство хеша БД, их же баг
`25` vs `25.0`, WorkBench — равенство DataFrame), то есть любой показал бы ложные
провалы и Obscura выглядела бы хуже, чем есть.

Реализация: колонка `original` в `tokens`, `detokenize()` и обратный маппинг
возвращают её. Первая встреченная форма побеждает — что инструмент получает,
стабильно между ходами, а не скачет вслед за формулировкой. Обе формы одного
значения по-прежнему дают ОДИН токен, поэтому модель видит одну сущность.
Закреплено `test_product.py::test_tool_receives_original_surface_form`.

## 3.7 Покрытие типов ПД — внешняя проверка и чек-лист

**Recall на чужих данных: NAME 72.0%** (NEREL, 1908 упоминаний, 187 документов,
размечено не нами; 72.3% на кириллическом подмножестве). Собственные наборы дают
100% — разрыв в 28 пунктов и есть цена того, что мы проверяли себя на данных,
которые сами и сгенерировали. Харнесс: `bench/eval_external_ner.py`.

Промахи почти целиком — имена вне seed-газеттира (Обама, Бейонсе, Месси,
Рокуццо). Лекарство известно и записано в `names.py`: подставить полный словарь
(RussianNameVariants / russiannames, 32k). Эффект измеряется тем же харнессом.

CITY/LOCATION 2-3% и AGE 7% — низко **ПО ЗАМЫСЛУ**: голый топоним без привязки к
человеку не ПД (правило гранулярности HIPAA/GDPR), возраст маскируем от 90 лет.
Замер помечает эти строки отдельно, чтобы решение не выглядело дефектом.

DATE 0% на NEREL — тоже в основном по замыслу: даты доставки и встреч маскировать
нельзя, иначе ломаются те самые вызовы инструментов. Настоящая дыра была уже: в
контексте рождения брался только ГОД, а число с месяцем утекало
(`Родился 12 марта 1985` → маскировалось только `1985`). Закрыто; контекст
ограничен границей клаузы, чтобы `Заказ приедет 1 сентября, а я родился 7 июля`
маскировал только вторую дату.

### Чек-лист 152-ФЗ — `test_coverage_152fz.py`

Было закрыто: телефон, email, ФИО, адрес, СНИЛС, ИНН, карта, паспорт, дата, ДР,
возраст, медицина.

**Добавлено:** полис ОМС, водительское удостоверение, СТС/ПТС, госномер,
банковский счёт, ОГРН/ОГРНИП (с проверкой контрольного разряда), загранпаспорт,
IP, свидетельство о рождении. Итого 23 типа, проверяются в обе стороны.

Два дефекта, найденных самим чек-листом:

- **Водительское и СТС определялись как ТЕЛЕФОН** — та же форма `NN NN NNNNNN`,
  что у паспорта. Тип не косметика: токен рендерится по типу, поэтому номер прав
  заменялся фейковым телефоном. Разведены по слову-подсказке, приоритет выше
  телефона.
- **Госномера ломала наша же нормализация.** Она схлопывает буквы-двойники в
  цифры, чтобы ловить обфусцированные телефоны, и `О123ОО777` превращался в
  `012300777`. Номера теперь ищутся по СЫРОМУ тексту — это безопасно, потому что
  нормализация строго 1:1 по длине и офсеты совпадают.

Всем новым типам сделаны **формат-сохраняющие** токены. Без этого они падали в
`REDACTED…`, и номер счёта, заменённый на `REDACTEDab12cd`, провалил бы
валидацию в форме клиента — ровно тот вред, против которого продукт и делается.
Фейковый ОГРН намеренно с неверной контрольной суммой, IP — из диапазона
RFC 5737, зарезервированного под документацию.

## 4. Производительность

**Принцип: не оптимизировать вслепую.** Сначала профилировщик показывает, где
время; оптимизируем измеренное.

### 4.1 Профилировщик (`obscura/profiling.py`)

Трёхуровневая лестница:

1. **Стадийные таймеры, всегда доступны.** `OBSCURA_PROFILE=1` включает замер по
   стадиям (normalize / regex / structured / NER / address / gazetteer / kv / quasi /
   resolve / tokenize / audit / splice). `GET /profile` отдаёт count, total, p50,
   p95, p99, max. Кольцевой буфер на стадию — память ограничена. Выключено —
   накладные расходы нулевые.
2. **Функциональный профиль по требованию.** `profile_deep.py --mode=function` —
   `yappi` (умеет треды, в отличие от `cProfile`; наша детекция уходит в threadpool).
3. **Построчно.** `profile_deep.py --mode=line` — `line_profiler` по горячим
   функциям, найденным на шаге 2.

Прогон бенчмарка выполнять с `OBSCURA_PROFILE=1`, чтобы узкое место всплыло на
реальной нагрузке, а не на синтетике.

### 4.2 Первый результат профилирования — узкое место найдено

Прогон `profile_deep.py --mode stage` (120 сообщений, смешанная нагрузка):

| стадия | доля | мс/сообщение |
|---|---|---|
| **`detect.address`** | **84.3%** | 10.47 |
| `detect.ner` | 5.8% | 0.72 |
| `mask.tokenize_and_audit` | 4.3% | 0.53 |
| `detect.gazetteer` | 4.1% | 0.51 |
| `audit.record` | 3.8% | 0.25 |
| `vault.tokenize` | 0.6% | 0.02 |
| остальное | <1% | — |

`--mode line` локализует это в одной строке `address.py:207` — внутри
`_natasha_candidates`, то есть в Yargy-грамматике `AddrExtractor`. Регексная ветка
рядом стоит копейки.

**Хранилище узким местом НЕ является** (аудит 3.8%, vault 0.6%) — то есть замену
SQLite и очередь записи делать рано, это не там.

**Абляция AddrExtractor** (три независимых свежих сида адресного бенчмарка,
712 адресов, плюс dirty-набор с жёсткими негативами):

| | recall | мс/кейс |
|---|---|---|
| с AddrExtractor | 100% (227/227, 242/242, 243/243) | 7.85 / 8.38 / 9.88 |
| только регексы | 100% (227/227, 242/242, 243/243) | 1.01 / 1.15 / 1.14 |

На dirty-наборе — полностью идентичные recall, precision, утечки и ложные
срабатывания. То есть **AddrExtractor не добавляет ни одной пойманной сущности и
стоит 7–8× латентности**.

⚠️ **Решение не принято.** Все три набора синтетические и порождены скриптами этого
же репозитория, поэтому могут разделять слепые пятна с регексной веткой. Убирать
источник recall из fail-closed шлюза — односторонняя дверь: цена ошибки здесь тихая
утечка. Перед удалением проверить на реальном русском тексте.

### 4.3 Хранилище и доступ — после профилирования

Известные кандидаты, решение принимать **по данным профиля**:

- SQLite с одним соединением и `threading.Lock` на `Vault`/`AuditLog` сериализует
  все обращения. Кандидаты: WAL-режим, пул соединений, отдельное соединение на тред.
- `AUDIT.record()` делает `commit()` на **каждый** span — то есть fsync на каждую
  найденную сущность. Кандидат: батчинг записи через очередь с фоновым писателем.
  Аудит не на критическом пути ответа, его можно писать асинхронно.
- Замена SQLite (Redis / Postgres) — только если профиль покажет, что упирается
  именно в него. Добавляет зависимость в контур клиента, поэтому не по умолчанию.

### 4.4 Уже сделано

- Детокенизация: поиск по форме токена + индексированные точечные запросы вместо
  скана всего хранилища. **56 мс → 0.06 мс при 50k токенов (×955).** Инвариант
  форм токенов закреплён тестом `test_product.py::test_token_shapes`.
- Content-cache на маскирование убирает O(n²) на растущем транскрипте.
- Детекция уходит с event loop в threadpool под `CapacityLimiter`.
- Воркеры-процессы: pymorphy3 держит GIL, параллелизм даёт только процессы.

## 6. Что литература говорит против нас — и наш ответ

Две независимые работы показывают, что privacy-промпт обыгрывает
middleware-маскирование по обеим осям сразу: **AgentDAM** (Meta FAIR) — pre-filter
0.390 utility / 0.841 privacy против privacy-CoT 0.398 / 0.919, pre-filter закопан
в приложение как неэффективный; **PrivScope** — Presidio как middleware стоит
−14 п.п. task success на GPT-4o-mini и −26 п.п. на Gemini, candidate recall падает
до 7.5%.

Ответ, который надо доказать цифрами, а не риторикой: **обе работы меряют системы,
которые ТЕРЯЮТ информацию.** Presidio редактирует безвозвратно, AgentDAM
минимизирует данные до запуска агента. Obscura не теряет — подменяет и возвращает
обратно на границе инструмента. Если наш Δ выйдет около нуля там, где у Presidio
−14…−26 — это и есть продающий результат. Если нет — узнаем рано.

Планка низкая: у Presidio нет ни одного замера downstream-полезности, у Skyflow —
ноль публичных замеров вообще.

Метрики берём из литературы, не изобретаем: `task sensitivity` (Δ = U_orig − U_priv,
Tau-Eval, EMNLP 2025), `TSR`, `Candidate Recall`, и обязательно **`Q&A true`** —
точность на подмножестве задач, где ответ зависит от ПД (общая точность прячет
ущерб). Незанятая земля, которая может стать нашим вкладом: никто не измерял,
переживает ли токен переписывание ответа моделью.
