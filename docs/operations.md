# Эксплуатация: что работает без нас и что требует человека

Цель этого документа одна: чтобы продукт продавался, выдавал ключи, тарифицировал
и останавливал неплательщиков без нашего участия — а список того, где человек
всё-таки нужен, был коротким, явным и осознанным.

---

## 1. Что где крутится

**У клиента** (мы туда не ходим никогда):

> Том `pseudex-data` — единственный носитель соответствия «подмена → настоящее
> значение». Подмены уже лежат в СИСТЕМАХ клиента (CRM, заказы, журналы), и без
> тома они становятся строками без обратного пути: восстановить их не можем ни
> мы, ни он. Инструкция по резервной копии выдаётся при подключении (шаг 7
> в `billing/onboarding.py`), потому что это единственное место, которое клиент
> читает. Мы туда не ходим и копию не делаем — это его контур и его данные.
>
> **Том зашифрован (SQLCipher, AES-256), и ключ такой же невосстановимый, как
> сам том.** По умолчанию контейнер создаёт ключ рядом с данными
> (`/data/pseudex-vault.key`) и говорит об этом в логе при каждом старте: это
> защищает скопированный файл базы и НЕ защищает украденный том, потому что
> ключ лежит в нём же. Клиент выносит ключ наружу через `PSEUDEX_VAULT_KEY`,
> `PSEUDEX_VAULT_KEY_FILE` или `PSEUDEX_VAULT_KEY_CMD` (вывод любой команды —
> его KMS), а `PSEUDEX_VAULT_ENCRYPTION=required` запрещает старт, если внешний
> ключ не разрешился. Ключа у нас нет ни в каком виде, и это не позиция, а
> отсутствие механизма: мы его не выдаём и не получаем.
>
> Шаг 8 онбординга говорит про ключ ту же фразу, что шаг 7 говорит про том.

```
их сеть → :8000 движок (N воркеров)      ← зовёт их шлюз
          :8081 локальный интерфейс      ← открывает их администратор
          volume /data                   ← волт, журнал, статистика — шифротекст
                                            + pseudex-vault.key, если ключ свой
```

Что открывается текущим ключом, показывает отдельная роль — она нужна потому,
что SQLCipher отвечает `file is not a database` одинаково на неверный ключ, на
испорченный файл и на незашифрованную базу:

```bash
# КАЖДАЯ из этих команд должна получить ТЕ ЖЕ переменные ключа, с которыми
# работает движок на этом томе (PSEUDEX_VAULT_KEY / _FILE / _CMD). Без них
# probe ничего не создаёт и честно печатает «ключ: none» — и тогда каждый
# файл покажет «НЕ ОТКРЫВАЕТСЯ», хотя том исправен.
docker run --rm -v pseudex-data:/data -e PSEUDEX_ROLE=probe \
  -e PSEUDEX_VAULT_KEY_CMD="$PSEUDEX_VAULT_KEY_CMD" pseudex:<версия>

# decrypt и rekey ПИШУТ: движок на этом томе должен быть ОСТАНОВЛЕН. Обе
# заканчиваются подменой файла, и живые воркеры продолжают писать в отвязанный
# inode — всё, что выдано после этого момента, теряется, в том числе из той
# открытой копии, которую уходящий клиент забирает с собой.
docker run --rm -v pseudex-data:/data -e PSEUDEX_ROLE=decrypt \
  -e PSEUDEX_VAULT_KEY_CMD="$PSEUDEX_VAULT_KEY_CMD" pseudex:<версия>

docker run --rm -v pseudex-data:/data -e PSEUDEX_ROLE=rekey \
  -e PSEUDEX_VAULT_KEY=<текущий> -e PSEUDEX_VAULT_KEY_NEW=<новый> pseudex:<версия>
```

**Те же шесть команд — одним входом.** `prototype/pseudexctl` — один файл на
stdlib (у клиента есть docker и python3, нашего venv у него нет), который
собирает их сам. Возможностей он не добавляет; он убирает способы промахнуться —
том, смонтированный не туда, ключ, переданный не той переменной, роль с
опечаткой, из-за которой контейнер молча стартует движком вместо диагностики:

```bash
pseudexctl doctor          # что сломано и ЧТО ДЕЛАТЬ, а не трейсбек
pseudexctl probe           # открывается ли том текущим ключом
pseudexctl preflight --memory 2g   # сколько воркеров влезет, не трогая контейнер
pseudexctl rekey --verify  # ротация И доказательство, что детокенизация выжила
pseudexctl backup vault.tgz
pseudexctl --dry-run …     # напечатать команду, не выполняя
```

**`--verify` закрывает дыру, которую не видел никто.** `vault_migrate.rekey_store`
доказывает ровно одно: файл открывается новым ключом. Что подстановки, УЖЕ
ЛЕЖАЩИЕ В CRM КЛИЕНТА, по-прежнему разворачиваются в настоящие значения, не
проверял ни один гейт и ни один тест — а это единственное, ради чего волт
существует. `--verify` берёт подстановки из `/selfcheck` ДО ротации (настоящие
`/mask` и `/unmask` на канонической фразе, под организацией, которую биллинг
исключает) и требует ТЕХ ЖЕ после. Разошлись — значит строки не пережили смену
ключа и отчеканены заново, то есть у половины людей в чужой системе теперь по
два псевдонима; тогда команда говорит это прямо и советует восстановить том из
копии. Если сравнить не с чем (движок не отвечает ДО ротации), том не трогается
вовсе: смена ключа плюс «проверить не смогли» — худший из двух исходов.

`decrypt` оставляет открытую копию на диске, а зашифрованный файл ОТВЯЗЫВАЕТ, а
не затирает: `os.replace` удаляет запись в каталоге, блоки остаются. То же верно
и в обратную сторону — том, на котором когда-либо лежал открытый текст, следует
считать всё ещё содержащим его. Затирать байты мы не будем: на overlay2, на CoW и
на SSD это не работает, и обещание, которого продукт не держит, хуже названного
пробела.

Ротация — `PRAGMA rekey`: страницы перешифровываются, строки не трогаются, 50 000
строк за 0.15 с. Хранилище переезжает целиком или никак, а **том — нет**: файлы
идут по одному, и обрыв оставляет часть на старом ключе, часть на новом. Сделать
это атомарным нечем, поэтому роль печатает, какие файлы переехали, и отказывается
говорить «старый ключ можно отзывать», пока не переехали все.

`decrypt` — обратная миграция, тем же `sqlcipher_export`. Она существует, чтобы
дверь не была односторонней: клиент, уходящий от продукта, забирает данные в
виде, который читает любой инструмент.

**У нас** (`deploy/compose.yml`):

```
:443   Caddy                 → TLS для ОБОИХ имён, сертификаты сам (Let's Encrypt)
         pseudex.ru          → витрина: лендинг, регистрация, кабинет
         license.pseudex.ru  → лицензионный сервер: аренда, счётчики
       license :8443/:9443   → только внутренняя сеть; :9443 — админ, наружу никогда
       storefront-migrate    → миграции и тарифы перед первым запросом, на каждой выкатке
       postgres              → аккаунты, тарифы, счета
       backup                → обе базы, ежедневно
       billing               → цикл биллинга раз в час, сводка утром
       watch                 → сторож, раз в минуту, тревоги в Telegram
```

До сентября 2026 лицензионный сервер сам слушал :443 со своим сертификатом из
`./certs`, а Caddy с витриной был вытеснен на :8443 — то есть `https://pseudex.ru`
отвечал бы лицензионным сервером. Обнаружено первым подъёмом боевого compose.

Вне compose, таймерами systemd — потому что обе единицы управляют самим стендом
и внутри него жить не могут:

```
pseudex-agent.timer          → раз в минуту: новый тег? подпись сошлась? выкатить
pseudex-restore-drill.timer  → раз в неделю: развернуть вчерашний бэкап
```

Вне нашей инфраструктуры вообще:

```
.github/workflows/uptime.yml → раз в 10 минут снаружи: витрина и лицензии живы?
```

Связь **односторонняя**: контейнер клиента звонит нам. Обратного канала нет, и
это не удобство, а то, что делает нас необработчиком — у нас физически нет
способа дотянуться до их данных.

## 2. Что ломается и что происходит само

| отказ | что видит клиент | требуется человек? |
|---|---|---|
| упал наш лицензионный сервер | ничего, пока хватает предоплаченного резерва (~6 ч трафика), потом ещё до 24 ч аренды и 48 ч grace с предупреждениями — что кончится первым, зависит от нагрузки | **нет**, если поднимется в пределах резерва |
| витрина не может дозвониться до лицензий при оплате | счёт остаётся ОПЛАЧЕННЫМ, обслуживание возобновится повторной доставкой уведомления; в кабинете `service_resumed_at` пуст | **да, если висит дольше десяти минут** — сторож алармит |
| клиент упёрся в остывание слота | до 5 минут отказа новому контейнеру; переразвёртывание на том же томе не задето | нет, отказ называет работающий путь |
| упала витрина | не может зарегистрироваться или открыть кабинет; работающие клиенты не замечают | нет |
| упал postgres | витрина отдаёт 500; лицензии и маскирование не затронуты | нет, `restart: unless-stopped` |
| у клиента упал воркер движка | контейнер останавливается целиком (это верно: полулицензированный контейнер хуже остановленного) | нет, их оркестратор перезапускает |
| клиент дал контейнеру мало памяти | контейнер НЕ СТАРТУЕТ и печатает, сколько дать или сколько просить | нет, отказ называет обе цифры |
| у клиента упал локальный интерфейс | маскирование продолжается, интерфейс перезапускается сам через 3 с | нет |
| клиент не оплатил | 48 ч предупреждений, потом fail-closed | **нет** — это и есть автоматика |
| истёк TLS-сертификат | — | нет, Caddy продлевает сам |
| кончилось место на диске | лицензионный сервер встанет → все клиенты через 3 суток | **да, следить** |

**ЁМКОСТЬ КОНЕЧНА, И ЭТО ОСОЗНАННО.** Раньше наш простой давал клиенту
безлимитное обслуживание на весь TTL плюс grace, и это было не милосердие, а
дыра: одна строка в фаерволе превращала две трети месяца в бесплатный трафик.
Теперь в контейнере лежит предоплаченный резерв примерно на шесть часов его
обычного трафика — наш сбой покрыт, а блэкхол даёт ровно оплаченное. Обратная
сторона названа честно: простой ДЛИННЕЕ резерва останавливает клиента, и это
наша ответственность по SLA, а не его по договору.

**ПАМЯТЬ СЧИТАЕТСЯ ДО ФАН-АУТА, А НЕ OOM-KILLER'ОМ ПОСЛЕ.** Воркер держит ~350 МБ
резидентной памяти (измерено: 7 МБ голый интерпретатор, 117 после бандла, 252
после импорта движка, 351 после сборки морфологии — дальше плоско), интерфейс —
ещё ~50, плюс 128 МБ запаса. `PSEUDEX_ROLE=preflight` считает это перед стартом и
либо **отказывает** (когда число воркеров назвал оператор — тихо запустить
четверть от заказанного значит сделать развёртывание вчетверо слабее, чем за него
заплатили, и никогда об этом не сказать), либо **понижает своё же число**,
выведенное из `nproc`, громкой строкой в лог. Ручки: `PSEUDEX_WORKER_MB`,
`PSEUDEX_HEADROOM_MB`, `PSEUDEX_MEMORY_LIMIT_MB` (последняя — когда cgroup виден
неправильно, например во вложенном рантайме, который показывает память хозяина).

Пока контейнер работает, ту же арифметику отдают `/status` и `/diagnostics` рядом
с ФАКТИЧЕСКИМ размером самого крупного воркера. Интересна строчка, где эти два
числа разошлись: это контейнер, который остановит OOM-killer сегодня к вечеру, и
виден он до того, а не после.

Единственный отказ, который действительно останавливает бизнес, — **потеря
`license.db`**. В ней все выданные ключи; без неё ни один клиент не продлит
аренду, и починить это кодом нельзя. Отсюда бэкап в отдельном контейнере со
своей политикой перезапуска, а не в cron на хосте, который однажды пересоберут.

## 2bis. Порядок выката: лицензионный сервер ПЕРВЫМ

Движок и сервер связаны контрактом аренды, и связь несимметрична. Движок
контракта 2 требует в лизе `recipient`, `report_secret` и `issued_at`; сервер
контракта 1 их не шлёт. Отсутствие поля движок трактует как «сервер старше меня
или это повтор» и **не стартует** — по существу верно, а снаружи выглядит как
наш сбой.

Обратное направление безопасно: сервер контракта 2 шлёт лишние поля, старый
движок их игнорирует. Поэтому правило одно:

    сначала лицензионный сервер, потом образ движка

Проверяется одной командой, без токена:

    curl -s https://<лицензионный сервер>/v1/pubkey | jq -r .lease_contract

Если число меньше того, что требует выкатываемый образ, — сервер выкатывается
первым. `PSEUDEX_MIN_ENGINE_VERSION` закрывает противоположный случай (движок
слишком старый) и этот НЕ закрывает: он про версию движка, а не про контракт.

## 3. Где человек всё-таки нужен

Список сознательно короткий. Всё, что в нём есть, — одна кнопка в
`/admin/` (Django), а не shell на проде:

1. **Отметить счёт оплаченным.** Приходит банковский перевод — в списке счетов
   «отметить оплаченным». Действие само возобновляет обслуживание на
   лицензионном сервере; порядок именно такой, потому что клиент ждёт не запись
   в нашей базе, а работающий шлюз.
2. **Внести реквизиты.** ИНН и наименование не спрашиваются при регистрации
   намеренно — до покупки они не нужны и удлиняют путь до первого запроса.
3. **Enterprise-договор.** Тариф не продаётся на сайте.
4. **Ответить в поддержку.** Основной канал — Telegram, почта вторым;
   разбирает человек, автоответчика нет.

Всё остальное — выдача ключа, проба, счётчики, остановка за неоплату,
возобновление после оплаты — происходит без нас.

## 4. Секреты

| секрет | где | ротация |
|---|---|---|
| `PSEUDEX_SIGNING_KEY` | только в окружении лицензионного сервера | **не ротируется автоматически** — публичная часть вкомпилирована в каждый выпущенный бинарник, смена ключа делает недействительными все развёрнутые образы |
| `PSEUDEX_SECRET_KEY` | витрина | при подозрении; разлогинивает всех |
| `POSTGRES_PASSWORD` | compose | обычная |
| ключи ЮKassa | витрина | по правилам провайдера |
| `PSEUDEX_ADMIN_TOKEN` | генерируется в `entrypoint.sh` у клиента | каждый рестарт контейнера |
| ключ шифрования волта | **только у клиента**: env, файл или вывод его команды; по умолчанию генерируется в его же том | `PRAGMA rekey`, но см. ниже |

**Ключа от волта у нас нет, и это не хранение с ограничениями, а отсутствие
механизма.** Выдачу ключа лицензионным сервером мы отвергли: механизм есть
(`bundle.py` уже запечатывает под процессный X25519), но он делает нас стороной,
способной расшифровать персональные данные граждан РФ у клиента, превращает наш
простой в его неоткрываемый волт и юридически переводит нас в обработку по
поручению.

**Своя база лицензий НЕ шифруется** (`PSEUDEX_VAULT_ENCRYPTION=off` в
`licensing/Dockerfile`), и это решение, а не упущение: персональных данных там
нет — ключи лежат как SHA-256, остальное это org id, тарифы и счётчики, — зато
шифрование сломало бы `backup.sh` (хостовый `sqlite3 .backup` не откроет
SQLCipher и молча свалится в `cp` живой WAL-базы) и еженедельные учения, которые
считают строки в копии. Единственная база, которую нельзя пересобрать из кода,
осталась бы без обеих проверок ради нуля персональных данных.

Ключ подписи — единственный, у которого нет автоматической ротации, и это
осознанно: смена требует перевыпуска образа и согласованного обновления у всех
клиентов. Если он скомпрометирован, это инцидент с планом, а не операция.

## 5. За чем смотрит сторож

**Раньше это был список для человека, и человек не смотрел.** Теперь каждый
пункт — проверка в `deploy/watch.sh`, раз в минуту, с тревогой в Telegram.

Главное свойство: **тревога на СМЕНУ состояния, а не на каждый обход.** Сторож,
раз в минуту повторяющий «диск заполнен», за час обучает замьютить канал — и
следующая, настоящая тревога придёт в замьюченный канал. Поэтому каждая проверка
помнит свой прошлый вердикт и говорит дважды: когда сломалось и когда починилось.
Отбой не менее важен, чем тревога: без него человек гадает, чинилось ли оно.

В тревогу не попадают логи и тела ответов — там персональные данные клиентов.
Сообщается ФАКТ и место, смотреть человек идёт сам. То же правило, по которому
журнал раскрытий не хранит значение.

Метрик немного, потому что смотреть должны за тем, что действительно ведёт к
отказу:

- **место на диске** лицензионного сервера и postgres — единственный отказ из
  таблицы §2, который останавливает всех;
- **свежесть бэкапа**: файл в `deploy/backups/` не старше 25 часов. Бэкап,
  который никто не проверял, — это отсутствующий бэкап;
- **`/admin/list` отвечает 200** — лицензионный сервер жив;
- **доля 402/403 в ответах на `/v1/lease`** — рост означает либо волну
  неоплат, либо нашу ошибку в статусах. **Реализовано**: исходы считает
  middleware в `licensing/server.py` — в одном месте, а не в двенадцати ветках
  обработчика, поэтому в счётчик попадают и пятисотки, которых в тексте
  обработчика нет вовсе. Метрика `pseudex_license_responses_total{path,code}`,
  тревога `PseudexLeaseRefusalsHigh` на 20% за полчаса. Различать волну неоплат
  и нашу ошибку помогает второй вопрос: у ОДНОЙ организации это биллинг, у всех
  сразу — мы. Пятисотки на аренде вынесены в отдельную тревогу, потому что
  клиент трактует 5xx как НАШ сбой и берёт полный grace: рубильник неоплаты на
  это время не работает;
- **экземпляры, не продлевавшие аренду > 24 ч** — клиент, который вот-вот
  встанет и ещё не знает об этом. Проверка ЧИТАЛА поле, которого `/admin/list`
  не отдавал, и была всегда пустой; поле добавлено, и теперь это ещё и сигнал о
  блэкхоле лицензионного сервера — отсюда «клиент перестал продлеваться» и
  «клиент уронил связь нарочно» выглядят одинаково, и разбираться стоит в обоих
  случаях;
- **оплаченные счета с пустым `service_resumed_at` старше десяти минут** —
  деньги записаны, обслуживание не возобновлено. Повтор доставки чинит это сам,
  но если счёт висит — не починил.

Последний пункт — единственный, который стоит превращать в письмо клиенту до
того, как он позвонит.

Чего сторож видеть НЕ МОЖЕТ — собственной смерти. Если машина выключилась или
провайдер увёл сеть, он молчит вместе с ней, и молчание неотличимо от «всё
хорошо». Для этого есть `.github/workflows/uptime.yml`: проверка раз в десять
минут из облака GitHub, в тот же канал. Две проверки намеренно разные — эта
видит «процесс жив», та видит «машина жива», и совпадать они не обязаны.

### Скрейп, дашборд и тревоги

Сторож остаётся тем, что БУДИТ: он ходит раз в минуту, шлёт в телеграм и
переживает падение чего угодно, включая Prometheus. Наблюдаемость даёт другое —
историю и ответ на вопрос «когда это началось», на который сторож ответить не
может по устройству. Поэтому это **отдельный профиль**, который по умолчанию не
поднимается:

```bash
# Полный админский токен кладётся ФАЙЛОМ, а не переменной: подстановку ${...}
# в compose делает сам Compose, и токен оказался бы в `docker inspect`.
mkdir -p secrets && printf %s "$PSEUDEX_LICENSE_ADMIN_TOKEN" > secrets/license-admin-token
chmod 600 secrets/license-admin-token
echo 'COMPOSE_PROFILES=observability,support' >> .env   # не флагом: агент делает up -d без флагов
docker compose up -d                              # prometheus + grafana + alertmanager + бот
ssh -L 3000:127.0.0.1:3000 <хост>                 # Grafana смотрят через туннель
```

- `GET /admin/metrics` на лицензионном сервере — сводка по флоту: исходы аренд,
  сколько контейнеров обслуживает, разрывы цепи (и поимённо — только у тех, у
  кого они есть), неподтверждённые и неразобранные отчёты.
- `GET /metrics` на движке КЛИЕНТА — лестница лицензии, память против бюджета
  предполёта, что защищено сегодня по типам. **Мы это не скрейпим**: трафик у
  продукта односторонний, от клиента к `/v1/lease`, и другого быть не должно.
  Блок для клиентского Prometheus лежит закомментированным в
  `deploy/prometheus.yml` как образец.
- Обе цели — **за токеном**. Числа говорят, сколько людей клиент защитил сегодня
  и в каких категориях: это описание его бизнеса, а на малом масштабе и его
  трафика. Полный токен кладётся Prometheus'у **файлом**, а не переменной
  окружения: переменная видна в `docker inspect` всякому, кто на этой машине
  есть.
- Grafana публикуется только на `127.0.0.1` — смотреть через ssh-туннель.
  Панель показывает, кто наши клиенты и у кого из них проблемы.
- Дашборд лежит в `deploy/grafana-dashboard.json` и версионируется вместе с
  правилами: панель, нарисованная руками в UI, живёт в базе одной машины и
  исчезает вместе с ней.

Тревог намеренно мало, и правило то же, по которому написан сторож: смотреть
надо за тем, что действительно ведёт к отказу. У каждой есть `for:` — скрейп раз
в тридцать секунд ловит любое мгновенное состояние, а перезапуск контейнера это
мгновенное состояние всего перечисленного.

## 6. Выпуск

```bash
git tag v1.0.1 && git push --tags
```

**И всё.** Дальше без человека.

`.github/workflows/release.yml`:

1. тесты движка и витрины;
2. **гейты против настоящих контейнеров** — P1–P8 и L1–L20;
3. только после зелёных гейтов образы пушатся и подписываются `cosign` — все
   три: клиентский, лицензионный и витрина.

Наши собственные два образа собираются **здесь, а не на хосте**. Сборка на боевой
машине означала, что ничто нигде не доказывает: то, что крутится, — это то, что
прошло гейты.

`pseudex-agent.timer` на хосте, раз в минуту:

1. новый тег `v*` в git?
2. **`cosign verify` каждого образа** — до того, как что-либо остановлено. Не
   сошлась подпись — не выкатываем и кричим. Реестр не доверенная сторона, и
   подпись существует ровно затем, чтобы его не приходилось считать таковой;
3. `compose pull` + `up -d`;
4. **ждём здоровья и откатываемся сами**, если не поднялось. Обновление, после
   которого сервис не встал, чинится за сорок секунд без человека — в этом и
   разница между «автономно» и «автоматически»: автоматическое умеет только
   ломать быстрее.

Откат вручную: `PSEUDEX_PIN=v1.0.0` в `deploy/.env` закрепляет версию и выключает
автовыкатку. Нужен ровно тогда, когда что-то пошло не так и нужно время подумать,
не воюя с агентом, который упорно возвращает «правильную» версию.

Порядок обратный обычному специально: подпись означает «этот образ доказан», а
не «этот коммит собрался». Подписывается **дайджест, не тег** — тег изменяем, и
подпись над ним ничего не говорит о байтах, которые клиент в итоге скачает.

Клиент проверяет — **с нашей личностью, не с `.*`**. Регексп `.*` принимает
подпись любого аккаунта GitHub и не доказывает о нас ничего (по коду cosign
проверка личности при `.*` — тавтология; см. `research/2026-09-14-devops-audit.md`).
Личность публикуется здесь, и менять её могут только мы:

```bash
cosign verify cr.yandex/crpkutn2el1knpsbrs2d/pseudex:0.1.0 \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  --certificate-identity-regexp '^https://github\.com/Isk4R1oT/Obscura/\.github/workflows/release\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+$'
```

Проверено на `v0.1.0`: этот шаблон проходит, а `@refs/heads/main`, чужой
репозиторий и чужой issuer — отказ. Сертификат несёт
`…/release.yml@refs/tags/v0.1.0` даже при ручном `workflow_dispatch` на тег:
Fulcio кладёт в SAN `job_workflow_ref`, а он равен ref запуска.

Ставит обновления безопасности без автоперезагрузки, закрывает всё кроме 22/80/443,

## 6ter. Копии вне хоста

`./backups` лежит на том же диске, что и базы: это защита от «уронили таблицу» и
не защита ни от чего, что случается с машиной. Ночной цикл после локальных копий
вывозит их **restic**-ом в Yandex Object Storage.

| свойство | как обеспечено |
|---|---|
| Шифрование | встроено в restic, пароль в `RESTIC_PASSWORD` |
| Дедупликация | измерено: вторая ночь на 1,05 МБ добавила **823 байта** |
| Хост не может стереть историю | `DeleteObject` запрещён политикой бакета; `prune` идёт из GitHub Actions другим ключом |
| Проверка — вне зоны поражения | воркфлоу `backup-audit`, ежедневно |
| Это восстановление, а не листинг | база лицензий выкачивается, `PRAGMA integrity_check`, считаются ключи клиентов |

Локальные копии остаются **незашифрованными** намеренно: обычное восстановление
не должно зависеть от пароля репозитория. Пароль нужен только после пожара.

Заведено 13.09.2026, и форма политики — результат измерения, а не чтения документации:

| что | как |
|---|---|
| Бакет `pseudex-backups` | стандартное хранилище (холодное штрафует restic за мелкие объекты), версионирование включено, лимит 50 ГБ |
| Жизненный цикл | неактуальные версии — 14 дней; оборванные multipart-загрузки — 2 дня |
| `pseudex-backup` | `storage.editor`, статический ключ → `deploy/.env` хоста |
| `pseudex-backup-audit` | `storage.editor`, статический ключ → секреты GitHub |

**Политика бакета — три правила, и порядок появления важен.** Первая версия была
одним запретом, и она заперла ОБА ключа целиком: политика Яндекса — «всё, что явно не
разрешено, запрещено», роли IAM это не обходят. Вторая версия запрещала хосту
`DeleteObject` на `pseudex-backups/*` — и хост перестал снимать **собственный
замок**: restic ставит файл в `locks/` на каждую операцию, а `prune` со стороны
проверки отказался с «repo already locked».

1. `deny-delete-host` — **Запретить** `s3:DeleteObject`, `s3:DeleteObjectVersion`
   для `pseudex-backup` на **пяти** ресурсах: `data/*`, `snapshots/*`, `index/*`,
   `keys/*`, `config`. Каталог `locks/` намеренно не назван.
2. `allow-backup-accounts` — **Разрешить** все действия обоим аккаунтам на
   `pseudex-backups/*` **и** на `pseudex-backups` (без `/*`: `ListBucket` — операция
   над бакетом, и без неё restic не видит свой индекс).
3. Правило доступа из консоли — кнопка в интерфейсе, иначе владелец теряет
   веб-доступ к собственному бакету.

Явный запрет сильнее разрешения, поэтому хост получает всё, кроме удаления.
Измерено: хост пишет и оставляет 0 замков; `restic forget` хостом — `Access
Denied`, снапшоты целы; проверка удаляет. Аудит перед работой снимает
ПРОТУХШИЕ замки (`restic unlock` без `--remove-all`) — контейнер, убитый посреди
бэкапа, замок не снимает.

В `deploy/.env`: `RESTIC_REPOSITORY`, `RESTIC_PASSWORD`, `OFFSITE_KEY_ID`,
`OFFSITE_KEY_SECRET`. В секретах GitHub — те же плюс `OFFSITE_ADMIN_KEY_ID` /
`OFFSITE_ADMIN_KEY_SECRET` (с правом удаления).

**Потеря `RESTIC_PASSWORD` = потеря всех вывезенных копий.** Он обязан лежать в
менеджере паролей владельца, а не только в `.env` машины, которую он защищает.

## 6quater. Тревоги доходят до человека

В `alerts.yml` десять правил, и до сентября 2026 они срабатывали **в никуда**:
в `prometheus.yml` стояло `targets: []`. Теперь есть Alertmanager, тот же
телеграм-канал, что у сторожа (одно место, куда смотреть в три ночи), с двумя
решениями: падение лицензионного сервера, разрыв цепи отчётов и истёкшая лиза
идут **без задержки** и повторяются чаще; следствия упавшего лицензионного
сервера **подавляются**, чтобы не топить причину в симптомах.

`chat_id` подставляется одноразовым сервисом `alertmanager-config` из `.env`, и
Alertmanager не стартует, пока рендер не завершился успешно: Alertmanager не
раскрывает переменные окружения, а вторая копия значения в гите однажды
разойдётся — и выяснится это в аварии.

**Сторож теперь сторожит и себя.** `while :; do watch.sh || true; done` крутится
вечно, чем бы ни кончался обход, поэтому сломанный `watch.sh` выглядел исправным
сервисом. Отметка ставится только дошедшим до конца обходом; её возраст читают и
сам сторож, и healthcheck контейнера.

## 7. Восстановление

```bash
# витрина
docker compose exec -T postgres pg_restore -U pseudex -d pseudex --clean \
  < deploy/backups/storefront-<stamp>.dump

# лицензии — тот отказ, ради которого всё это существует
docker compose stop license
docker cp deploy/backups/license-<stamp>.db pseudex-license-1:/data/license.db
docker compose start license
```

**Учения идут сами, раз в неделю** (`pseudex-restore-drill.timer`): вчерашний
бэкап разворачивается во временную базу, и проверяется не «файл читается», а
«таблицы непустые». Дамп, оборванный на середине, читается прекрасно и
восстанавливается в пустоту — а проверку свежести проходит.

**Восстановление у клиента — это том И ключ.** Если ключ генерировался
контейнером, он лежит в томе и едет вместе с ним; если он вынесен наружу,
восстановленный том без него не открывается ничем. Порядок проверки один:

```bash
docker run --rm -v pseudex-data:/data -e PSEUDEX_ROLE=probe \
  -e PSEUDEX_VAULT_KEY_CMD="$PSEUDEX_VAULT_KEY_CMD" pseudex:<версия>
```

Переменные ключа обязательны и здесь: `probe` ничего не создаёт, поэтому без них
он печатает `ключ: none`, и все три файла честно показывают `НЕ ОТКРЫВАЕТСЯ` — на
исправном томе. Раньше он в этом месте ЗАВОДИЛ новый ключ рядом с данными и
докладывал ту же катастрофу, уже своими руками.

`НЕ ОТКРЫВАЕТСЯ` здесь — это про ключ, а не про порчу файла: заголовок уже
прочитан и говорит «зашифровано». Дальше либо находится верный ключ, либо
соответствия «подмена → значение» не восстановит никто, включая нас.

После восстановления лицензий проверить, что живой клиентский ключ продлевается:
`/admin/list` показывает организации, а не пустой список. Клиенты внутри своих
72 часов этого не заметят вовсе — в этом и был смысл суточной аренды с двумя
сутками grace.
