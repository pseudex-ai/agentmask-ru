## 3. Corpus — 500 synthetic messages, own scope, never the holdout

Generated by [gen_corpus.py](gen_corpus.py) with `random.Random(20260930)`, from
templates and vocabulary contained in that file. **No real-speech utterance, no
transcript, no `prototype/*.json` dataset, no holdout and no paid-run file was
read or copied.** Registers: `kv` 125, `prose` 150 (40 of them carry no
person-like PII), `chat` 125, `sloppy` 100. Lengths: min 37 / p50 124 / mean
119.8 / max 261 chars. Deterministic order; each line is
`{id, register, text}`.

The fabricated identifiers are real to the *checksums*: `--verify` re-checked 200
freshly generated values per type against the engine's own validators —
СНИЛС 200/200, ИНН-10 200/200, ИНН-12 200/200, card (Luhn) 200/200, ОГРН
200/200 ([corpus.meta.json](corpus.meta.json)). That cross-check caught a real
generator defect: the first Luhn writer appended a checksum computed over the
15-digit body, which flips doubling parity, and only 20/200 cards passed. It is
fixed by searching the check digit with the validator itself.

This corpus is a **cost** input. It carries no gold labels and no quality claim
is made from it anywhere.

## 4. The two arms

| arm | what it is |
|---|---|
| `FULL` | current `Detector.detect` — the whole shipped pipeline, in process. Not the container: no HTTP, no uvicorn, no worker fan-out. |
| `NER_ONLY` | **diagnostic ablation, not a production candidate**: only the Natasha PER/LOC layer, `Detector._ner_spans(normalize(text))`. |

`NER_ONLY` **keeps** Layer 0 `normalize()`, the natasha Segmenter + NewsNERTagger,
and the in-layer gates `keep_person`, `keep_location`, `location_is_pii`,
`trim_person_span`. It **disables** `detect_address`, `detect_pii` (phone/email),
`detect_structured`, `detect_structured_kv`, `detect_spoken_ids/_email/_plate`,
`detect_credentials`, `detect_vehicle_ids`, `detect_plates`, `gazetteer_names`,
`detect_quasi`, `context.suppress`, `_resolve`/`_PRIORITY` and the
`_guess_inside_person` cross-check. Disabling `_resolve` means spans may overlap
and no priority winner is chosen — irrelevant to cost, and no quality claim is
made. No engine file was patched: the ablation is a subclass defined inside
[perf_one_arm.py](perf_one_arm.py).

| `Detector()` (natasha weights) | 214.6 / 206.4 / 213.3 | 219.0 / 215.2 / 203.8 |
| cold start = spawn → first `detect()` return | 1330.4 / 1285.1 / 1269.5 | 1290.8 / 1317.7 / 1281.8 |
| **time to fully warm** = spawn → end of 50-call warm-up | 3655.8 / 3616.3 / 3573.6 | 1341.7 / 1366.9 / 1332.0 |

Cold start is measured across process boundaries: the script re-executes itself so
the parent can stamp `time.time()` immediately before `subprocess.run`, and the
child reports `first_detect_wall - spawn_wall`. The in-process part of the first
call is only 30.8 ms (FULL) / 2.2 ms (NER_ONLY).

**`load_dev_bundle()` dominates cold start (~0.86 s), and it is a development-only
path** — it calls `licensing.pack.build_plaintext()` and packs the bundle in
process. The shipped image receives a lease instead. This number therefore has no
production equivalent and must not be quoted as a container cold start.

## 8. The headline finding: the rules layer has a ~1.5 s one-time lazy cost

| | FULL | NER_ONLY |
|---|---:|---:|
| warm-up max single call (ms) | **1437.3 / 1465.2 / 1457.2** | 1.76 / 1.54 / 1.70 |
| time to fully warm (ms) | 3573–3656 | 1332–1367 |

The first call that reaches a marker-less street builds a deletion index over the
whole leased ГАР street vocabulary (`address.py::_street_index`,
`build_index(ASSETS.get().address.street_names)`, lazily `lru_cache`d), and a
second index build costs ~0.5 s more. `Detector()` does not pay either, and the
natasha layer pays ~1.7 ms at worst. The two costs reproduce in all three matrix
runs — the two slowest warm-up calls per run are **1437.3 / 510.3 ms**,
**1465.2 / 500.9 ms**, **1457.2 / 497.1 ms** — ≈1.95 s of the ≈2.3 s gap between
cold start and fully warm. So per process:

* ~1.29 s to the first answer,
* ~3.6 s to a fully warm detector — i.e. **~2.3 s of one-time work that the first
  address-bearing input triggers**, not process start and not model load.

This changed the harness. The first version warmed on the first 50 contiguous
messages; the index build then landed inside the timed window and p99 became a
setup cost (smoke pass: p99 514 ms). The shipped warm-up now takes every
50/LEN-th message ("spread"), so every register is touched before timing — and the
discarded cost is still printed as `warmup_max_ms` and `warmup_sum_ms` in every
`raw/*.meta.json`, not hidden by the choice. Whether a production worker's first
request is better served by this warm-up is not decided here; RUNBOOK-PERF §1's
<20 s cold-start contract (P8) is a container figure this run does not measure.

## 9. RSS

Every run records four checkpoints, each as **peak** (`ru_maxrss`, monotonic by
definition) and **current** (`ps -o rss=`) — peak alone would have read as "flat"
between load and after-N even where allocation happened:

| | import (peak/cur) | after load (peak/cur) | after warm-up (peak/cur) | after N (peak/cur) |
|---|---|---|---|---|
| FULL 1 | 208.6 / 208.6 | 445.2 / 418.2 | 445.2 / 359.6 | 445.2 / **111.3** |
| FULL 2 | 208.6 / 208.6 | 463.7 / 436.7 | 463.7 / 347.3 | 463.7 / **111.9** |
| FULL 3 | 207.4 / 207.4 | 461.6 / 434.6 | 461.6 / 356.4 | 461.6 / **223.9** |
| NER_ONLY 1 | 215.8 / 215.8 | 437.7 / 410.7 | 437.7 / 411.9 | 437.7 / 390.8 |
| NER_ONLY 2 | 207.0 / 207.0 | 438.2 / 411.2 | 438.2 / 412.0 | 438.2 / 413.3 |
| NER_ONLY 3 | 205.4 / 205.4 | 456.9 / 429.9 | 456.9 / 430.7 | 456.9 / 431.0 |

Peak RSS is the stable figure: **FULL 445–464 MiB (median 461.6), NER_ONLY
438–457 MiB (median 438.2)**, i.e. the natasha model + leased assets dominate and
the two arms differ by ~5 %. The kernel's own peak agrees **exactly** with the
in-process `ru_maxrss` on all six runs (max disagreement 0.0 MB,
`/usr/bin/time -l`).

The **current** column is not stable and should not be quoted as a per-worker
resident: FULL ranged 111.3–223.9 MiB (2.0× spread) across three identical runs.
A bounded probe ([logs/06-rss-probe.log](logs/06-rss-probe.log)) shows why: after
2000 calls a `FULL` process holds 235 MiB, then 165 MiB two seconds later and
**76.5 MiB after seven idle seconds** — the resident set keeps falling after the
loop ends. The sample time decides the number; only a fixed sampling protocol
makes it comparable, and this experiment does not have one.

Two consequences, both offered as observations, not verdicts:
* the ~350 MB/worker figure `preflight.py` uses is a **Linux container**
  measurement on the service path; this run's **macOS peak of 438–464 MiB is
  above it**, but that is a cross-host, cross-path comparison and is not evidence
  of a production regression;
* the claim there that RSS is "flat across sixty detections" is contradicted on
  this host by the probe above — page reclamation, a different allocator, or a
  different sampling point. This run does not isolate the cause and does not
  revise that document.

## 11. Caveats — read these before quoting any number

1. **Contended host.** Another repo benchmark job held one full core throughout
   (§1). All values are exploratory and barred from an admission budget.
2. **3 repeats, not 5.** The runbook asks k=5; this preliminary pass ran k=3.
   Median-across-runs is therefore a weak centrality estimate: with 3 samples the
   median is the middle run.
3. **In-process only.** `Detector.detect` in a plain process. No HTTP, no
   `uvicorn`, no `to_thread`/`CapacityLimiter`, no multi-worker fan-out, no
   vault/audit. Not a container or production measurement.
4. **The corpus is a cost fixture, not a workload model.** 500 synthetic messages
   (mean 119.8 chars) with a fixed 1:1:1.2:0.8 register mix. A different length or
   register mix moves every percentile, and nothing here bounds product traffic.
5. **The current-RSS column is unstable by construction** (§9): the sampler's
   timing sets the value (111–224 MiB for the same arm). Use the peak column.
6. **`load_dev_bundle()` is ~2/3 of cold start and has no production equivalent**
   (§7). Do not quote 1.29 s as a container start.
7. **One-time lazy costs are real but excluded from the timed N** by a spread
   warm-up, and reported separately. A deployment that does not warm up will see
   a ~1.5 s first-address call.
8. **`max` spread is 1.9× across runs for FULL** (29.28 / 52.51 / 27.55 ms) while
   the percentile spread is ≤2 %. The tail beyond p99 is not characterised by
   3 runs.
9. **p99 is threshold-sensitive at n=1000**: nearest-rank puts p99 at sample 990,
   so `max` and `p99` answer different questions; both are reported.
10. **Two pymorphy versions are installed** (`pymorphy3` 2.0.6 used via
    `_morph_compat`, `pymorphy2` 0.9.1 present). Recorded, not investigated.
11. **Nothing about quality, precision or recall** — the corpus is unlabelled.
12. **`NER_ONLY` is not a candidate.** Its numbers show one component's share of
    cost under ablation, nothing more.

## 12. What this run does NOT claim

* no production equivalence, and no budget-grade number under contention;
* no architecture adoption recommendation, and no winner between arms;
* no quality/precision/recall figure, and no comparison with D0's 12.35 /
  7.58 ms/text (different corpus, warm-up, process model and sample count — not
  comparable);
* no statement that the 350 MB/worker figure or the P8 <20 s cold-start contract
  is met or broken in production;
* no change to any engine, licensing, scorer, corpus, wiki or git state.

`O-DETECT` remains `OWNER_PENDING`: this run supplies the cost axis only. The
quality axis is a D0-style harness on gold approved through `O-DATA`; per
RUNBOOK-PERF §4.4 neither table alone answers the question.
