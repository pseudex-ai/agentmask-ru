## Что спрашивали

Дословно: «почему если я на 5 минут не сделаю остановку то этой командой можно
обнулить лимит трафика? это какой-то ненадёжный бред, это не должно зависеть от
магического числа 5. 24 часа это тоже ужас — а если у человека прод без меня
лежит, он должен как можно быстрее перезапустить, чтобы всё заработало. Давай
изучать этот вопрос и находить конкретную причину, почему так происходит, и как
это связано с безопасностью.»

**Короткий ответ.** Оба числа — 300 с и 86 400 с — это два разных приближения к
ОДНОЙ величине, которая нигде не названа: **сколько времени лиза продолжает
работать после того, как мы перестали слышать контейнер.** Сегодня она равна
`ttl + grace = 259 200 с = 72 часа`, и из неё механически следует всё остальное.
Пока она 72 часа, «освободить слот через 5 минут молчания» означает отдать
тарифу множитель `72 ч / 5 мин = 864`. Именно поэтому занятость считается по
суточному окну аренды, а не по признаку жизни: суточное окно даёт множитель
`72 / 24 = 3`, и это единственная причина, по которой оно там стоит. Остывание
на 300 с — не защита, а третий ограничитель, и замер показывает, что он **не
связывает вообще**: бюджет освобождений (3 в час) жёстче остывания (12 в час) в
четыре раза на любом тарифе.

Починка поэтому не в том, чтобы поменять 86 400 на 600, а в том, чтобы **назвать
три величины отдельно** и связать их одним неравенством:

```
потолок обхода = (темп перевыдачи слотов) × (время работы без связи с нами)
```

Занятость слота переводится на признак жизни (600 с), время работы без связи
остаётся прежним (72 ч), а темп перевыдачи остаётся ровно тем, каким он уже
есть сегодня (3/ч) — только теперь он ограничивает ВСЕ причины освобождения, а
не одну. Потолок обхода при этом не меняется ни на единицу, а клиент с упавшим
контейнером ждёт 10 минут вместо суток.

## 1. Стенд и что на нём измерено

Всё ниже поднимается одной командой из `prototype/` с активной `.venv`:

```bash
cd prototype && source .venv/bin/activate
python3 $CLAUDE_JOB_DIR/tmp/slot-liveness/e1_dead_slot.py     # и e2…e10
```

`stand.py` (приложение А) запускает НАСТОЯЩИЙ `licensing/devserver.py`
подпроцессом на свободном порту 127.0.0.1 с временной базой и ключом подписи,
сгенерированным на старте; «контейнер» — это пара `(instance_id, pubkey)`, где
`pubkey` берётся из `pseudex.bundle.generate_process_key()`, как в движке.
Двойников нет нигде: `e4`/`e6`/`e10` поднимают настоящий
`pseudex.license.LicenseClient` и берут настоящую аренду.

| № | что меряет | результат |
|---|---|---|
| E1 | сколько держится слот убитого контейнера | **ровно TTL после последней лизы** (60.3 с при `TTL=60`, отношение 1.00) |
| E2 | что ограничивает цепочку освобождений | остывание = точный темп (5.19 ± 0.07 с при `cooldown=5`); бюджет = 3 освобождения в час; без обоих — 12 контейнеров за 0.3 с |
| E2b | что делает release с тем, кто его позвал | отпустивший процесс продлевается и **забирает слот назад**, а чужому отказ врёт про остывание |
| E3 | редеплой на том же томе против нового | тот же том — 200 в обоих случаях; новый том — 409 (300 с после release, до суток после kill) |
| E4 | отчитывается ли ПРОСТАИВАЮЩИЙ инстанс | **да**, по своему таймеру, без единого запроса трафика |
| E5 | цена лизы против цены отчёта | лиза 18.1 мс / 2 034 351 Б; отчёт 3.0 мс / 472 Б |
| E6 | разрешение признака жизни | интервал = `ceil(период/5 с) × 5 с`, дрожи нет |
| E7 | сколько контейнеров влезает под один `instance_id` | **32** на `start`, **128** на `work` |
| E8 | сколько перезапусков выдерживает честный клиент | 16 воркеров — отказ на **третьем** перезапуске за сутки |
| E9 | что видит кабинет, пока слот держит труп | `state: "active"`, `free_at: null` — труп показан работающим |
| E10 | байты | лиза 2 034 351 Б, признак жизни 472 Б, отношение **4310×** |

## 2. Механизм, по строкам

### 2.1 Кто занимает слот: `store.may_lease` (`licensing/store.py:1418`)

Решение целиком в одном запросе:

```sql
SELECT DISTINCT instance_id, pubkey FROM leases
 WHERE org_id=? AND issued_at>=? AND (released_at IS NULL OR released_at>=?)
```

`issued_at>=?` — это `now - window_seconds`, а `window_seconds` приходит из
`server.py:52` как `_TTL_SECONDS` (86 400). Третий параметр —
`now - RELEASE_COOLDOWN_SECONDS` (300). Дальше:

* `instances` — множество `instance_id`; отказ, когда его размер достиг
  `instances_allowed(plan)` (`start` = 1, `work` = 4, `industrial` = 12,
  `enterprise` = 100, `store.py:837`);
* `keys` — множество ключей процессов; отказ, когда размер достиг
  `allowed × processes_allowed(plan)` (32 на инстанс, `store.py:851`);
* быстрый путь: `pubkey in keys` → продление разрешено всегда (и это верно —
  продление не может быть отказано), с привязкой ключа к первому назвавшему его
  `instance_id`.

**В этом запросе нет ни одного признака жизни.** «Брал лизу в последние сутки» —
единственное, чем инстанс считается работающим.

### 2.2 Почему сутки, а не час: клиент продлевается раз в `TTL/3`

`server.py:791` отдаёт `renew_after_seconds = max(1, _TTL_SECONDS // 3)` = 28 800 с
(замер E1 на `TTL=60` печатает `renew_after=20`, на `TTL=3600` — `1200`).
`pseudex/license.py:1112` домножает порог на джиттер `[0.8, 1.0)` — то есть
только ВНИЗ. Значит последняя лиза живого инстанса может быть на 8 часов
старше «сейчас», и окно занятости обязано быть заметно больше 8 часов, иначе
живой контейнер выпадет из собственного потолка между продлениями. Отсюда 24
часа — и отсюда же вывод E1: слот убитого держится `86 400 − возраст последней
лизы`, то есть **от 16 до 24 часов**, а не «до суток в среднем».

### 2.3 Признак жизни, который уже есть и который никто не читает

`pseudex/license.py:174`:

```python
_USAGE_REPORT_SECONDS = float(os.environ.get("PSEUDEX_USAGE_REPORT_SECONDS", "120"))
```

**Сто двадцать секунд, а не триста.** Запись Б26 называет `METER_TARGET_SECONDS`
= 300 — это другая величина: `store.py:1208` использует её только как «сколько
секунд СОБСТВЕННОГО трафика клиента составляет квант ёмкости», это размер
покупки, а не таймер. Настоящий пульс — `_USAGE_REPORT_SECONDS`, он появился
коммитом `05d6720` от 19.09.2026 и первым несёт его тег **v0.3.14**
(`git tag --contains 05d6720`).

Цикл (`license.py:1132`) зовёт `_report_usage()` по времени и **без всякой связи
с трафиком**:

```python
if self._usage_due():
    self._report_usage()
```

`_usage_due` смотрит только на часы. E4 это подтверждает end-to-end: настоящий
`LicenseClient` с `usage_provider`, отдающим нули, и нулём запросов трафика
прислал 4 отчёта за 16 секунд. **Ответ на открытый вопрос Б26: простаивающий
контейнер отчитывается, отдельный пинг изобретать не нужно.**

Сервер на `/v1/usage` (`server.py:956`) зовёт `_store_usage` → `record_usage`, и
тот пишет `usage.updated_at = time.time()` на ОБЕИХ ветках — и на подтверждённой
(`store.py:553`), и на неподтверждённой (`store.py:522`), — а при наличии
`pubkey` ещё и `process_reports.updated_at` (`store.py:821`). То есть в базе
лежат **две** отметки «слышали» с разрешением две минуты: по инстансу и по
процессу. `may_lease` не читает ни одну.

### 2.4 Разрешение и дрожь этой отметки (E6)

Цикл спит `min(5.0, max(1.0, due/4.0))`, а `due = renew_after_seconds` = 28 800 →
**шаг цикла ровно 5 с**. Отсюда наблюдаемый интервал отчётов равен
`ceil(период / 5) × 5`, что E6 и печатает:

```
PSEUDEX_USAGE_REPORT_SECONDS= 3.0  интервалы: [5.01, 5.01, 5.0, 5.01, 5.0, 5.01, 5.01]
PSEUDEX_USAGE_REPORT_SECONDS= 7.0  интервалы: [10.01, 10.01, 10.01]
PSEUDEX_USAGE_REPORT_SECONDS=12.0  интервалы: [15.02, 15.01]
```

При боевых 120 с это ровно 120 с (24 × 5), дрожи ноль. Два уточнения, которые
понадобятся в §4:

* `_report_usage` ставит `_last_usage_monotonic` ДО отправки, поэтому **один
  потерянный POST стоит полного периода**: следующая попытка через 120 с, разрыв
  240 с. `k` потерянных подряд → разрыв `(k+1) × 120` с;
* `instance_id` — это `AUDIT.installation_id()` (`service.py:125`), один на том,
  а `LicenseClient` свой у КАЖДОГО воркера. Значит по инстансу отметка
  обновляется `W` раз за 120 с, где `W` — число воркеров: сигнал кратно
  избыточен.

### 2.5 Освобождение: `release_process`, `slot_free_at`, бюджет

`/v1/release` (`server.py:600`) требует ключ процесса и зовёт
`release_process` (`store.py:1626`), который **не удаляет строку**, а ставит
`released_at`/`released_by='process'`. `slot_free_at` (`store.py:1653`) =
`MAX(released_at) + 300`. До этого момента строка продолжает считаться в
`may_lease` — это и есть остывание.

Сверху стоит второй ограничитель: `releases_last_hour >= release_budget(plan)`
→ 429 `release_budget`, где `release_budget = max(3, instances_allowed)`
(`store.py:1651`).

`prune_leases` (`store.py:1540`) удаляет строки старше `2 × TTL` — это только
гигиена диска, на решения не влияет.

### 2.6 Что из этого следует для клиента — четыре случая, замеренные

**(а) Контейнер убит молча (E1).** Слот держится 16–24 часа. Отказ — дословно:

```
409 instance_limit: тариф допускает 1 инстанс(ов), сейчас активно 1.
Остановите лишний контейнер или перейдите на больший тариф.
```

Кабинет в это время (E9, `/admin/instances`) показывает:

```json
{"instance_id": "vol-dead", "state": "active", "free_at": null,
 "engine_version": "0.3.16"}
```

То есть и отказ, и кабинет утверждают, что контейнер работает. Единственный
рабочий путь — наш `POST /admin/release`. У клиента самообслуживания нет:
`storefront_web/views.py:891` только ПОКАЗЫВАЕТ слоты.

**(б) Цепочка освобождений (E2).** Точные числа:

```
A. остывание 5 с, бюджет снят   : 12 контейнеров за 57.4 с, интервалы 5.19 ± 0.07 с
B. остывание 0 с, бюджет снят   : 12 контейнеров за 0.3 с,  интервалы 0.02 с
C. остывание 0 с, бюджет 3/ч    : 4 контейнера, дальше release 429 release_budget
D. остывание 300 с, бюджет 3/ч  : 1 контейнер, дальше лиза 409 instance_limit
```

Отсюда темп: остывание даёт `3600/300 = 12` перевыдач одного слота в час, бюджет
даёт `max(3, allowed)` в час. На `start` это 12 против 3, на `enterprise` — 1200
против 100. **Бюджет жёстче остывания в 4–12 раз на любом тарифе, то есть
остывание не связывает никогда.** Число 300 не защищает ничего: его снятие не
меняет ни одного достижимого сценария, пока бюджет на месте.

Сколько контейнеров РЕАЛЬНО обслуживают одновременно. Отпустивший слот процесс
держит бандл в памяти, и лестница `LEASED → STALE → EXPIRED` живёт в нём же:

* движок не тронут, цепочку крутит скрипт снаружи — каждый отпустивший на
  следующем продлении (≤ 8 ч) получит 409, а 409 с `instance_limit` лежит в
  `_ANSWER_CODES` (`license.py:124`) и **минует grace**, то есть контейнер
  честно встанет: `3/ч × 8 ч = 24` одновременно обслуживающих на тарифе в один;
* движок после release просто замолкает (firewall на исходящие или патч) — он
  доживает до `ttl + grace = 72 ч`: `3/ч × 72 ч = 216`.

**(в) Редеплой (E3).** На ТОМ ЖЕ томе — 200 в обоих случаях (и после release, и
после kill): `instance_id` берётся с тома, и ветка «этот инстанс уже держит
слот» срабатывает до всех потолков. На НОВОМ томе — 409: 300 с после
корректной остановки (сообщение честное, называет «ТОМ ЖЕ ТОМЕ») и до суток
после kill (сообщение про «остановите лишний контейнер», которого нет).

**(г) Отпустивший забирает слот назад (E2b).** Последовательность
`lease → release → lease` тем же ключом процесса возвращает 200: строка ещё в
окне остывания, значит `pubkey in keys`, значит быстрый путь. Чужой контейнер в
этот момент получает отказ, который врёт: `slot_free_at` смотрит на
`MAX(released_at)` и печатает «освободится через 5 мин», хотя инстанс снова
активен, а `active_instances` в той же секунде показывает `state: "active"`.
**Два определения занятости в одном файле расходятся.**

### 2.7 Два дефекта того же рода, которые Б26 не называет

**Потолок на самом деле по ПРОЦЕССАМ, и его обходят одной переменной (E7).**
`instance_id` выбирает клиент: `service.py:125` читает `PSEUDEX_INSTANCE_ID` и
только при пустом значении берёт идентификатор тома. Поставив одно значение во
всех контейнерах, на тарифе в один инстанс получают **32 рабочие лизы**, на
`work` — **128**:

```
тариф start -> 32 контейнеров с одним instance_id получили рабочую лизу;
               дальше: 409 ... это 32 рабочих процессов, сейчас активно 32
тариф work  -> 128 контейнеров ...
```

Это не новость для кода (комментарий на `store.py:837` описывает именно это как
осознанный остаток), но это самый дешёвый обход из существующих, и он
постоянный, а не темповый.

**Тот же самый потолок ломает ЧЕСТНЫЙ перезапуск (E8).** Ключ процесса
рождается в памяти воркера и умирает с ним; перезапуск контейнера с `N`
воркерами добавляет `N` новых ключей, а старые считаются занятыми всё суточное
окно:

```
  4 воркеров -> перезапуск #9: 409 ... 32 рабочих процессов, сейчас активно 32
  8 воркеров -> перезапуск #5: 409 ...
 16 воркеров -> перезапуск #3: 409 ...
```

`entrypoint.sh` берёт воркеров по числу ядер. Значит клиент на тарифе `start` с
16-ядерной машиной **не может перезапустить свой контейнер третий раз за
сутки**, и отказ говорит ему про «рабочие процессы» — слово, которого нет ни в
одном его экране. Это ровно болезнь Б26, только по второй координате, и
чинится она тем же самым изменением.

## 3. Три срока, названные отдельно

Сегодня в коде одна величина работает за трёх. Разведём.

### T_offline — сколько движок работает, НЕ дозвонившись до нас

**Что это сейчас:** `ttl + grace = 86 400 + 172 800 = 259 200 с = 72 часа`
(`server.py:52,53`; `license.py::state` сравнивает `elapsed` с
`ttl + grace`). Отсчёт идёт от последней УСПЕШНОЙ лизы по `time.monotonic()` с
потолком по стенным часам (`test_clock_freeze.py`).

**Что защищает:** нашу собственную аварию. Лицензионный сервер один; пока он
лежит, чужой прод обязан работать.

**Коротко — что ломается:** наш простой длиннее T_offline останавливает
маскирование у всех клиентов разом. Это единственная точка, где наша
доступность становится их доступностью.

**Длинно — что ломается:** T_offline является **множителем в потолке обхода**.
Контейнер, замолчавший после первой лизы, обслуживает ровно T_offline, и мы об
этом не узнаем ничем: признак жизни отсутствует по построению. Значит любой
темп перевыдачи слотов `B` даёт `B × T_offline` одновременно работающих
контейнеров сверх тарифа.

**Источник истины:** наша целевая доступность, а не свойства клиента. Сегодня
это число не выведено ниоткуда — 24 ч и 48 ч выбраны по отдельности.

**Оговорка, которая всё смягчает:** T_offline не даёт бесплатного ТРАФИКА.
Ёмкость покупается квантами у нас (`/v1/meter`), а счёт строится на
`billable = Σ clamp(acked, granted − Q − R, granted)` по КЛЮЧАМ ПРОЦЕССОВ
(`store.py:1250`). Замолчавший контейнер доживает на предоплаченном резерве, и
этот резерв уже записан нам в `granted`. То есть лишний контейнер покупает
клиенту **параллелизм, а не объём**, и объём он оплачивает по верхней границе
полосы. Потолок инстансов защищает упаковку тарифа, а не выручку; выручку
защищает ёмкость. Это меняет цену ошибки в §4 на порядок.

### T_alive — сколько мы СЧИТАЕМ инстанс живым после последнего признака жизни

**Что это сейчас:** величины нет; её роль играет окно аренды 86 400 с.

**Что защищает:** право клиента перезапуститься. Это единственная из трёх,
которая видна клиенту как время простоя после падения.

**Слишком мало:** живой инстанс, у которого потерялись `k` отчётов подряд,
выпадает из собственного потолка; следующий его запрос — продление, и оно
должно быть пропущено быстрым путём, иначе мы убьём работающий контейнер своей
же бухгалтерией. Пока быстрый путь на месте, цена — кратковременное превышение
на один контейнер, если клиент успел поднять новый.

**Слишком много:** ровно столько клиент и ждёт после падения. Сутки — «ужас»,
и это верное слово.

**Источник истины:** объявленный движком период отчёта, умноженный на
допустимое число потерь. Период известен (`_USAGE_REPORT_SECONDS = 120`),
разрешение измерено (E6: ровно 120 с, дрожь 0), стоимость потери известна
(один потерянный POST = ещё 120 с).

**Предлагаемое число: `T_alive = 600 с = 5 × 120 с`.**
Вывод: нормальный интервал 120 с; `k` потерянных подряд дают `(k+1) × 120`;
порог 600 с переживает **три потери подряд** с запасом 120 с. По инстансу
сигнал ещё и `W`-кратно избыточен (§2.4), поэтому три потери подряд по ВСЕМ
воркерам — событие, которое означает, что связи нет вообще, а тогда контейнер и
не обслуживает. Вверх от 600 с покупается только терпимость к нашему же
недоступному `/v1/usage`; вниз — время простоя клиента. 10 минут — это
«перезапустил и пошёл читать лог».

### T_turnover — с какой скоростью слот может перейти к другому контейнеру

**Что это сейчас:** два ограничителя на одну задачу —
`RELEASE_COOLDOWN_SECONDS = 300` (темп на слот) и
`release_budget = max(3, instances_allowed)` в час (темп на организацию). Замер
E2 показывает: бюджет жёстче всегда, остывание не связывает никогда.

**Что защищает:** потолок тарифа в условиях, когда «замолчал» и «остановился»
снаружи неразличимы. Это **единственный** ограничитель, который остаётся
осмысленным после перехода занятости на признак жизни.

**Слишком мало:** клиент с падающим деплоем на свежих томах ждёт.

**Слишком много:** потолок обхода растёт линейно: `B × T_offline`.

**Предлагаемое число: оставить `max(3, instances_allowed)` в час** — ровно то,
что уже работает, — но считать им ВСЕ причины освобождения, а не только
`/v1/release`. Обоснование не эстетическое: это сегодняшняя связывающая
величина, и сохранив её, мы сохраняем потолок обхода неизменным при том, что
окно занятости сокращается в 144 раза.

### Связывающее неравенство

```
одновременно обслуживающих сверх тарифа ≈ T_turnover_rate × T_offline
```

| конфигурация | темп | T_offline | потолок обхода |
|---|---|---|---|
| сегодня (окно 24 ч, бюджет 3/ч) | 3/ч | 72 ч | 216 |
| наивная починка: занятость 600 с, БЕЗ бюджета | ограничен задержкой (E2: ~40/с) | 72 ч | сотни тысяч |
| занятость 600 с, бюджет 3/ч | 3/ч | 72 ч | **216** |
| то же + T_offline 24 ч | 3/ч | 24 ч | 72 |
| то же + T_offline 6 ч | 3/ч | 6 ч | 18 |

Вторая строка — та самая «ненадёжная» конструкция, которой боялись, когда
ставили 300 с; и она действительно ненадёжна, но не из-за числа 300, а из-за
отсутствия третьей строки. Третья строка — предложение: потолок буква в букву
сегодняшний.

## 4. Модель угроз

**Кто.** Заказчик с валидным ключом и root на своём железе. Это весь противник:
`docs/tz-license-packaging.md` §3.4 принимает, что бандл он увидеть может, а
исходники — нет; `docs/metering-integrity.md` §5.5 перечисляет то же по
биллингу. Посторонний без ключа сюда не входит вовсе — `/v1/lease` требует ключ,
`/v1/release` требует ключ и ключ процесса.

**Чего он хочет.** Не бесплатного трафика (см. оговорку в §3: объём считается
ёмкостью по ключам процессов и оплачивается по верхней границе), а
**параллелизма**: больше контейнеров, чем куплено, — отказоустойчивость,
несколько площадок, нагрузка.

**Чего нельзя остановить и что об этом честно сказать.** Root на своей машине
может взять лизу и отрезать контейнеру исходящий доступ. Дальше движок
обслуживает T_offline на предоплаченном резерве, и никакая наша проверка этого
не увидит: признак жизни — это сигнал, который нам ПРИСЫЛАЮТ, а не который мы
снимаем. Поэтому вопрос не «как запретить», а **«за какое время мы заметим и
что напишем в счёте»**. Ниже это и есть третий столбец.

| трюк | что даёт сегодня | что даёт после починки | чем ограничен |
|---|---|---|---|
| **контейнер умер молча** (OOM, kill, ребут хоста) | держит слот 16–24 ч; клиент стоит (E1) | слот свободен через 10 мин; перевыдача стоит 1 единицу бюджета | T_alive, T_turnover |
| **цепочка `/v1/release`** | 24 одновременно на честном движке, 216 на молчащем (E2) | **то же самое** | бюджет 3/ч (остывание не связывало и убирается) |
| **взять лизу и замолчать** | 1 новый контейнер за 24 ч → 3 одновременно | 1 за 10 мин, но перевыдача берёт бюджет → **216**, как у цепочки | бюджет 3/ч × T_offline |
| **один `PSEUDEX_INSTANCE_ID` на всех** | 32 контейнера на тарифе в один, постоянно (E7) | без изменений; ключи мёртвых процессов перестают занимать место через 10 мин, что потолок **ужесточает** | потолок процессов 32 × allowed |
| **повторное использование ключа процесса** | привязка ключа к первому `instance_id`, отказ + WARN в логе (`store.py:1481`) | без изменений | требует патча бинарника (ключ рождается в памяти) |
| **замороженные часы** (LD_PRELOAD) | grace не продлевается: монотоника первична, стенные часы — потолок (`test_clock_freeze.py`, гейт L11) | **строго лучше**: T_alive считается ПО НАШИМ часам — `usage.updated_at` ставит сервер (`store.py:553`), клиентские часы в занятость не входят вообще | наша сторона |
| **патч, который никогда не отчитывается** | отчёта нет → слепой шаг ёмкости ЗАВЫШАЕТ (`issue_quantum`), `unacked_quanta` растёт, аномалия видна | то же + инстанс теряет слот через 10 мин, то есть молчание перестаёт быть бесплатным способом ДЕРЖАТЬ место | ёмкость + аномалии |
| **честный клиент перезапускается** (не атака, но ломается так же) | 16 воркеров → отказ на 3-м перезапуске за сутки (E8) | ключи мёртвых воркеров выпадают через 10 мин → перезапусков сколько угодно, лишь бы реже раза в 10 мин | — |

**Что каждый контроль на самом деле запрещает.**

* *Признак жизни* не запрещает ничего. Он только перестаёт наказывать честного
  за то, что мы не умеем отличить труп от живого.
* *Бюджет перевыдачи* — единственный настоящий запрет: он ограничивает ТЕМП
  появления новых обслуживающих контейнеров, и через `B × T_offline` —
  их количество.
* *Потолок процессов* запрещает дешёвую форму обхода через одинаковый
  `instance_id`, и после перехода на признак жизни начинает означать «32 ЖИВЫХ
  процесса», а не «32 ключа, виденных за сутки».
* *Ёмкость* — то, что защищает деньги; она к слотам отношения не имеет и в этом
  документе не меняется.

**Чего этот план не закрывает и не делает вид, что закрывает.** Root с
firewall'ом получает T_offline работы на каждый добытый слот; тридцать два
контейнера под одним `instance_id` остаются; счёт остаётся зажатым полосой
`Q + R`, а не точным. Всё это уже записано в `docs/metering-integrity.md` §5.5 и
остаётся в силе.

## 5. Конструкция

Исходное предложение владельца — занятость = «видели недавно», TTL остаётся
терпимостью к нашей аварии, остывание заменяется правилом «кто отчитывается
после release — снова занимает слот, и это аномалия». Ниже оно атаковано и
изменено в двух местах.

### 5.1 Что выстояло

**Занятость = «видели недавно».** Источник — `max(lease.issued_at,
usage.updated_at, process_reports.updated_at)`, всё уже есть в базе, миграции не
нужны. Ставит отметку СЕРВЕР, значит трюки с часами контейнера бессильны.

**TTL остаётся терпимостью к нашей аварии.** Да — и переименовать его в голове:
это половина T_offline, а не «окно занятости».

**Отчитывается ли простаивающий.** Да (E4). Отдельного пинга не нужно, и это
экономит движковый релиз.

### 5.2 Что не выстояло: «остывание заменяется аномалией»

Аномалия — это наблюдение, а не ограничитель. Если занятость падает до 600 с, а
ограничителя темпа нет, потолок обхода становится `T_offline / T_alive = 432`
на каждый купленный слот (строка 2 таблицы §3). Аномальный отчёт мы при этом
увидим — и будем смотреть на него, пока клиент обслуживает четыреста
контейнеров. **Остывание убирается не потому, что его заменяет аномалия, а
потому, что бюджет освобождений уже делает его работу в четыре раза строже
(E2).**

Правило «кто отчитывается после release, тот снова занимает слот» остаётся, но
как ЧАСТЬ занятости, а не вместо ограничителя: отметка `usage.updated_at`
свежее `released_at` означает «инстанс жив», и слот занят. Заодно это чинит
ложь из E2b: занятость станет одним определением на весь файл.

### 5.3 Что добавлено: бюджет перевыдачи вместо бюджета освобождений

Сегодня `releases_last_hour` считает только строки с `released_by='process'`.
После перехода на признак жизни появляется вторая причина освобождения —
молчание, — и она обязана попасть под тот же счётчик, иначе бюджет обходится
простым «не звать `/v1/release`».

Правило: **единица бюджета тратится в момент ДОПУСКА нового `instance_id`,
который стал возможен только потому, что прежний занимавший лапсировал**
(замолчал или отпустил слот). Не тратится:

* продление (быстрый путь по ключу процесса) — как и сегодня;
* перезапуск на ТОМ ЖЕ томе: `instance_id` тот же, никого не вытесняем;
* новый ключ процесса под уже допущенным инстансом, пока живых ключей меньше
  `processes_allowed(plan)` — это воркеры одного контейнера;
* наш собственный `POST /admin/release` — это спасение клиента, а не его расход.

Исчерпанный бюджет — не «нельзя», а «через M минут», и M считается и печатается
(см. §6).

### 5.4 Почему не «продлеваться раз в минуты», хотя это сделало бы release проверяемым

Соблазнительная мысль: если лиза действительна 15 минут, отпустивший её процесс
не сможет обслуживать дольше 15 минут, и release станет проверяемым. Она
неверна в двух местах.

**Во-первых, арифметика отказа.** Движок обслуживает `ttl + grace`, а не `ttl`.
Сократив TTL с 24 ч до 15 мин при grace 48 ч, мы уменьшим T_offline с 72 ч до
48 ч — на треть, а не качественно. Отпустивший слот и замолчавший процесс
по-прежнему живёт двое суток. Проверяемым release становится только для
ЧЕСТНОГО движка, который и так честно встаёт на следующем продлении с 409
(`_ANSWER_CODES` минует grace).

**Во-вторых, цена.** Замер E5/E10: ответ `/v1/lease` — **2 034 351 байт**
(бандл пересобирается и запечатывается на ключ процесса), медиана 18.1 мс;
`/v1/usage` — **472 байта**, медиана 3.0 мс. Отношение по байтам **4310×**.
Отсюда исходящий трафик при 10 000 процессов (нагрузочная планка из
`docs/tz-license-packaging.md` §2.6.4):

| период продления | наш исходящий |
|---|---|
| 28 800 с (сегодня) | 706 КБ/с ≈ **5.7 Мбит/с** |
| 600 с | 33.9 МБ/с ≈ **271 Мбит/с** |
| 120 с | 169.5 МБ/с ≈ **1.36 Гбит/с** |
| признак жизни 120 с (отчёт) | 39 КБ/с ≈ **0.31 Мбит/с** |

То есть получить разрешение в две минуты по лизе стоит в 4400 раз дороже, чем
по отчёту, который уже ходит. **Признак жизни обязан ехать на отчёте, а не на
аренде.** Если когда-нибудь понадобится короткий TTL ради уменьшения T_offline,
сначала нужен дешёвый ответ на продление (см. шаг 8).

### 5.5 Как меняется опыт клиента в четырёх случаях

| случай | сегодня | после |
|---|---|---|
| контейнер упал (OOM/kill/ребут), поднимают НА ТОМ ЖЕ томе | поднимается сразу (E3) | поднимается сразу, бюджет не тратится |
| контейнер упал, том пересоздан (`compose down -v`) | 16–24 ч простоя, отказ называет несуществующий контейнер | 10 мин, затем поднимается; отказ в эти 10 мин называет срок |
| корректная остановка, новый том | 300 с | сразу (release освобождает немедленно), 1 единица бюджета |
| редеплой на том же томе | сразу | сразу |
| карусель контейнеров | 4 за первый час, дальше 429 | то же самое |

## 6. Что говорим клиенту

**Где это рождается и куда доезжает.** Строка возвращается из
`store.may_lease` → `server.lease` кладёт её в `{"error": "instance_limit",
"detail": …}` с кодом 409 → `license._request_lease` поднимает
`LicenseError(code, detail)` → `service.py:253` (и `proxy.py:258`) **печатает
`detail` дословно** и следом статический `explain(error.code)` из
`license.REMEDIES`. Отсюда важное для совместимости: **текст в `detail` доезжает
до всех уже выпущенных движков без единого релиза**; врёт только вторая строка,
статическая, и её правка едет с ближайшим релизом движка. Кроме старта, те же
данные видны в `/license` (503, поле `remedy`, `service.py:504`) → баннер
локального интерфейса (`localui/static/app.js`) и `pseudexctl doctor`
(`pseudexctl:937`); список слотов — в кабинете
(`storefront_web/views.py:891`) и у поддержки (`/admin/instances`).

Правило, которому все четыре текста подчинены: **отказ обязан назвать путь,
который работает, и не называть того, который не работает.**

**(1) Тариф занят ЖИВЫМИ контейнерами.** Здесь «остановите лишний» — правда.

```
тариф допускает 1 контейнер, и он сейчас работает: vol-a1b2c3d4
(признак жизни 41 с назад). Остановите его — слот освободится сразу — или
смените тариф: https://pseudex.ru/app/
```

**(2) Прежний контейнер молчит, но бюджет перевыдачи исчерпан.**

```
тариф допускает 1 контейнер. Прежний (vol-a1b2c3d4) молчит 12 мин и больше
не считается работающим, но за последний час слот уже переходил к новому
контейнеру 3 раза — это потолок, иначе тариф обходится каруселью контейнеров.
Слот освободится через 9 мин. Если это переразвёртывание, поднимите контейнер
НА ТОМ ЖЕ ТОМЕ (-v pseudex-data:/data): он займёт свой слот сразу и бюджет не
тратит.
```

**(3) Потолок рабочих процессов (дефект E8 — сегодня этот случай не объясняется
ничем).**

```
тариф допускает 1 контейнер — это 32 рабочих процесса, и сейчас живых 32
(инстанс vol-a1b2c3d4). Если это перезапуск, подождите 10 мин: процессы
прежнего запуска перестают считаться через 10 минут молчания. Если контейнеров
действительно несколько — уменьшите PSEUDEX_WORKERS или смените тариф.
```

**(4) Статический текст движка,** `license.REMEDIES["instance_limit"]` (едет с
релизом движка; сегодня там «Остановите лишние или смените тариф»):

```
Тариф допускает меньше одновременно работающих контейнеров, чем запущено.
Что именно занято и когда освободится — в строке выше. Контейнер, который
остановлен или упал, перестаёт занимать слот через 10 минут молчания;
переразвёртывание НА ТОМ ЖЕ ТОМЕ слот не теряет. Свои контейнеры видно
в кабинете: https://pseudex.ru/app/
```

**Кабинет и `/admin/instances`.** `active_instances` отдаёт третье состояние:
`active` (признак жизни свежее T_alive), `silent` (молчит, с `last_seen` и
«перестанет занимать слот в HH:MM»), `released` (отпущен). Сегодняшнее
`cooling`/`free_at` уходит вместе с остыванием. Это же чинит E9: труп перестаёт
показываться работающим.

## 7. План

Обозначения: **[С]** — только сервер, едет с платформенным релизом
(`platform/vX.Y.Z`), движковой версии не требует; **[Д]** — нужен движок, то
есть версия, поле в лизе и совместимость с уже работающими.

### Шаг 1 [С] · Занятость по признаку жизни

*Файлы/функции.* `licensing/store.py`: новый приватный `_occupancy(org_id,
window_seconds, alive_seconds)`, которым пользуются `may_lease` и
`active_instances` — одно определение вместо двух разошедшихся (§2.6г).

```sql
SELECT l.instance_id, l.pubkey,
       MAX(l.issued_at, COALESCE(u.updated_at,0), COALESCE(p.updated_at,0)) AS last_seen,
       COALESCE(l.engine_version,'')
  FROM leases l
  LEFT JOIN usage           u ON u.org_id=l.org_id AND u.instance_id=l.instance_id
  LEFT JOIN process_reports p ON p.org_id=l.org_id AND p.pubkey=l.pubkey
 WHERE l.org_id=? AND l.issued_at>=? AND l.released_at IS NULL
```

Занят, если `last_seen >= now − alive_seconds` — **для движков, которые умеют
пульс**; иначе старое правило `issued_at >= now − window_seconds`. Признак
умения: версия движка не ниже **0.3.14** (первый тег, содержащий `05d6720`);
пустая строка и `1.0.0` (все образы до D-053) — старое правило. **Сравнение
версий — В PYTHON, кортежем** (`server._version_tuple`, `server.py:425`), НЕ в
SQL: `SELECT '0.3.9' >= '0.3.14'` возвращает 1, и это ровно та ловушка, на
которой уже обожглась `active_instances` («0.3.9» > «0.3.10» держала
обновлённый инстанс на старой версии целое окно, `store.py:1346`). Быстрый путь
`pubkey in keys` СОХРАНЯЕТСЯ на окне TTL, а не T_alive: продление не может быть
отказано.

*Миграция.* Ни одной: `usage.updated_at`, `process_reports.updated_at`,
`leases.engine_version` уже есть, индексы (`leases_org_issued`, PK обеих таблиц
отчётов) покрывают запрос.

*Что пинит сегодняшнее поведение.* `licensing/test_metering_attacks.py:244`
(«остывающий слот занимает место в потолке»), `:247` («переразвёртывание на том
же `instance_id` проходит немедленно»), `licensing/test_admin_api.py:472`
(«карусель контейнеров упирается в остывший слот»),
`licensing/test_store_upgrade.py:92` (форма `active_instances`).

*Новая проверка, которая обязана краснеть без шага.* Строка аренды возрастом
20 мин с `usage.updated_at` возрастом 20 мин **не** считается занимающей слот;
та же строка со свежим `usage.updated_at` — считается; строка с
`engine_version=''` ведёт себя по-старому. И перезапуск E8: 16 воркеров, три
поколения ключей, третье допускается, если два первых замолчали.

*Риск.* Движок, у которого `/v1/usage` заблокирован, а `/v1/lease` — нет,
между продлениями считается мёртвым. Держится быстрым путём по ключу процесса;
наблюдаемо как рост `reports_missing`.

### Шаг 2 [С] · Бюджет перевыдачи вместо бюджета освобождений

*Файлы/функции.* `store.releases_last_hour` → `turnover_last_hour` (считать
`released_by IN ('process','silence')`); в `lease_if_allowed`, ВНУТРИ той же
критической секции, при допуске нового `instance_id`, вытесняющего лапсировавший
слот: пометить строки лапсировавшего `released_at=last_seen,
released_by='silence'` (только там, где `released_at IS NULL`) и списать
единицу. `server.release` продолжает отвечать 429 сверх бюджета.

*Миграция.* Нет: `released_at`/`released_by` существуют, `released_by` —

*Что пинит.* `licensing/test_admin_api.py:496` («бюджет освобождений

*Риск.* Двойное списание за слот, который и отпустили, и признали молчащим —

### Шаг 7 [решение владельца, не код] · Размер T_offline

Таблица §3 — это весь выбор. 72 ч покупают терпимость к нашей аварии и стоят

единственного лицензионного сервера останавливает всех. Входные данные, которых

лицензирования.

### Шаг 8 [Д, необязательный] · Дешёвое продление

Если T_offline решат уменьшать, короткий TTL становится нужен, а он упирается в
2 МБ на продление (§5.4). Ход: при совпадении `bundle_version` отдавать
подписанное окно без бандла (~1 КБ), клиент держит уже загруженный.
2 034 351 Б → ~1 КБ делает продление раз в 10 минут дешевле сегодняшнего раза
в 8 часов. Это отдельная работа и отдельный контракт лизы.

**Порядок.** 1 → 2 → 3 → 4 → 5 одной платформенной выкаткой (они друг без друга

## Приложение А · Стенд

```python
# stand.py — НАСТОЯЩИЙ licensing/devserver.py на 127.0.0.1, временная база,
# эфемерный ключ подписи. Ни одного двойника; прод не участвует.
import os, socket, subprocess, sys, time, uuid, httpx
PROTO = "/Users/igor/Projects/Obscura/prototype"

def free_port() -> int:
    s = socket.socket(); s.bind(("127.0.0.1", 0))
    port = s.getsockname()[1]; s.close(); return port

class Stand:
    def __init__(self, **knobs: str) -> None:
        self.port, self.admin_port = free_port(), free_port()
        self.db = f"/tmp/stand-{uuid.uuid4().hex[:8]}.db"
        env = dict(os.environ); env.update({
            "PSEUDEX_LICENSE_DB": self.db,
            "PSEUDEX_LICENSE_ADMIN_TOKEN": "stand-admin",
            "PSEUDEX_LICENSE_STOREFRONT_TOKEN": "stand-shop",
            "PSEUDEX_LICENSE_PORT": str(self.port),
            "PSEUDEX_LICENSE_ADMIN_PORT": str(self.admin_port),
            "PSEUDEX_LOG_LEVEL": "WARNING"}); env.update(knobs)
        self.proc = subprocess.Popen([sys.executable, "-m", "licensing.devserver"],
                                     cwd=PROTO, env=env)
        self.base = f"http://127.0.0.1:{self.port}"
        self.admin = f"http://127.0.0.1:{self.admin_port}"
        for _ in range(200):
            try:
                if httpx.get(f"{self.base}/health", timeout=1.0).status_code == 200:
                    return
            except Exception:
                time.sleep(0.05)
        raise RuntimeError("stand did not come up")

    def issue(self, org: str, plan: str) -> str:
        return httpx.post(f"{self.admin}/admin/issue",
                          json={"org_id": org, "plan": plan},
                          headers={"Authorization": "Bearer stand-admin"},
                          timeout=10.0).json()["key"]

    def instances(self, org: str) -> dict:
        return httpx.get(f"{self.admin}/admin/instances", params={"org_id": org},
                         headers={"Authorization": "Bearer stand-admin"},
                         timeout=10.0).json()

    def stop(self) -> None:
        self.proc.terminate()
        try: self.proc.wait(timeout=5)
        except subprocess.TimeoutExpired: self.proc.kill()

class Container:
    """Контейнер, как его видит сервер: идентификатор ТОМА и ключ процесса,
    который он генерирует в памяти."""
    def __init__(self, stand: Stand, key: str, instance_id: str) -> None:
        sys.path.insert(0, PROTO)
        from pseudex.bundle import generate_process_key
        self.stand, self.key, self.instance_id = stand, key, instance_id
        self.pk = generate_process_key(); self.lease_id = None

    def lease(self):
        r = httpx.post(f"{self.stand.base}/v1/lease", timeout=30.0, json={
            "key": self.key, "instance_id": self.instance_id,
            "process_id": f"{self.instance_id}-1", "pubkey": self.pk.public,
            "engine_version": "0.3.16", "lease_contract": 3,
            "lease_id": self.lease_id, "nonce": uuid.uuid4().hex})
        if r.status_code == 200:
            self.lease_id = r.json().get("lease_id")
        return r

    def release(self):
        return httpx.post(f"{self.stand.base}/v1/release", timeout=10.0,
                          json={"key": self.key, "instance_id": self.instance_id,
                                "pubkey": self.pk.public})
```
