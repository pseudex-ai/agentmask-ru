# Как встать в разрыв LLM-трафика и чего это стоит

**Дата:** 2026-08-15 · **Статус:** завершён, четыре ветки сведены
**Вопрос:** как перехватывать весь исходящий LLM-трафик приложения клиента при минимуме
действий с его стороны — и возможна ли «нулевая конфигурация» вообще.

---

## Ответ

**Основной путь — быть OpenAI-совместимым эндпоинтом, на который клиент направляет
трафик одной переменной окружения. Прозрачный перехват (CA + forward-proxy) —
второй уровень для тех, кто не может править конфигурацию приложений.**

Обоснование в двух фактах, оба проверены:

1. Никто на рынке не делает прозрачный перехват. Девять продуктов (LiteLLM, Portkey,
   Helicone, Cloudflare AI Gateway, Kong, Envoy AI Gateway, Arch/Plano, Langfuse,
   OpenRouter) — **все** требуют сменить адрес. Ни один не документирует ни
   `HTTPS_PROXY`, ни установку CA.
2. Прозрачный перехват при этом **технически работает** — я его собрал и провёл через
   него реальный стриминговый вызов с инструментами. Цена: собственный CA в trust store
   каждого рантайма, и это N разных процедур с тихими отказами.

То есть выбор не между «умеем» и «не умеем», а между **одной переменной у клиента** и
**сертификатом в каждом его образе**.

---

## Что измерено на этой машине

Это не цитаты, а замеры. Поднимался TLS-сервер с сертификатом, подписанным приватным CA;
каждый клиент запускался отдельным процессом с разными переменными окружения.

### Кого можно заставить доверять нашему CA

| рантайм | `SSL_CERT_FILE` | `REQUESTS_CA_BUNDLE` | `NODE_EXTRA_CA_CERTS` |
|---|---|---|---|
| Python `urllib` | **работает** | нет | — |
| Python `httpx` | **работает** | нет | — |
| Python `openai` SDK | **работает** | нет | — |
| `curl` | **работает** | (`CURL_CA_BUNDLE` работает) | — |
| Node 25 `fetch`/undici | **работает** | — | **работает** |

`[A]` — измерено, каждая ячейка отдельным процессом.

Два вывода, которые меняют дизайн:

- **`REQUESTS_CA_BUNDLE` не работает для `httpx`** — только для `requests`. А `openai` и
  `anthropic` SDK сидят на `httpx`. Инструкция «поставьте REQUESTS_CA_BUNDLE» молча не
  сработает на главном клиенте.
- **Одна переменная `SSL_CERT_FILE` покрывает весь Python, curl и Node 25.** Это лучше,
  чем я ожидал: не N процедур, а одна — для этих рантаймов.

Ошибка `openai` SDK при недоверенном CA — `APIConnectionError: Connection error.`
Причина видна только через `__cause__`. `[A]` Диагностика у клиента будет мучительной.

### Перехват реального трафика — работает

Собран минимальный TLS-терминирующий forward-proxy (~120 строк, выпускает leaf-сертификат
на каждый SNI на лету — ровно как Squid ssl_bump и mitmproxy). Через него проведён
**настоящий** запрос к **OpenRouter** (не к OpenAI) со стримингом и вызовом инструмента.

```
openrouter.ai  req=673B  resp=3348B  plaintext_readable=True  sse=True
  PII VISIBLE IN PLAINTEXT to the proxy
```

Настройка со стороны клиента: `HTTPS_PROXY` + `SSL_CERT_FILE`. **Без root, без iptables,
без правки кода.** `[A]`

### Аргументы вызова инструмента приходят фрагментами

На том же прогоне, по проводу:

```
"arguments":""
"arguments":""
"arguments":"{\"…                    ← 3 фрагмента, склейка даёт целый JSON
```

`[A]` Здесь фрагментов оказалось три, но их число не гарантировано ничем: значение может
разъехаться по любому числу чанков. Это и есть корень проблемы детокенизации в потоке —
токен, разрезанный между чанками, нельзя сопоставить по образцу.

## Механизмы перехвата и их цена

Сводка ветки ресёрча по транспорту (полные цитаты и ссылки — в разделе «Источники»).

| механизм | что делает клиент | нужен root? | что ломается |
|---|---|---|---|
| смена `base_url` | одна переменная, рестарт | нет | ничего; не работает там, где адрес нельзя задать |
| `HTTPS_PROXY` + CONNECT | переменные окружения | нет | **тело остаётся зашифрованным** — виден только хост/SNI |
| MITM + приватный CA | прокси + CA в trust store каждого рантайма | нет* | pinning; любой пропущенный рантайм падает наглухо |
| iptables/eBPF redirect | привилегированный компонент в netns | **да**, `NET_ADMIN` | NAT-порядок, петли, UDP/QUIC; для тела всё равно нужен CA |
| Istio/Linkerd | установка меша, `ServiceEntry` на каждый хост | **да** | приложение должно ходить по `http://`, иначе виден только SNI |
| DNS override | `hostAliases`/CoreDNS + CA | нет | надо перечислить все хосты заранее |

\* root не нужен для explicit-режима; появляется только вместе с прозрачным redirect.

**Ключевая находка ветки:** тело запроса читаемо только в трёх механизмах — MITM, DNS+CA
и Istio-с-TLS-origination — и все три требуют приватный CA в каждом рантайме. Смена
`base_url` даёт тот же открытый текст **за одну переменную и без привилегий**.

Отдельные грабли, которые стоит знать до обещаний клиенту:

- **JVM игнорирует `HTTP_PROXY`/`HTTPS_PROXY` полностью** — только системные свойства
  `-Dhttps.proxyHost`.
- **Go безусловно обходит прокси для `localhost`** — зашито в `ProxyFromEnvironment`.
- **У Go на macOS и Windows нет `SSL_CERT_FILE`** — переменная работает только на Unix
  кроме macOS.
- `NODE_EXTRA_CA_CERTS` **игнорируется**, если у процесса setuid root или Linux
  capabilities, и читается только при старте.
- Сертификатный pinning неисправим без правки приложения.

## Что делают конкурирующие продукты

**Ни один из девяти не предлагает прозрачного перехвата.** Все требуют переконфигурации
приложения — либо `base_url` в SDK, либо маршрут в шлюзе, на который надо указать хостом.

| продукт | как трафик доходит | лицензия |
|---|---|---|
| LiteLLM Proxy | `base_url` + pass-through эндпоинты | MIT (кроме `enterprise/`) |
| Portkey Gateway | `base_url` + заголовки `x-portkey-*` | MIT |
| Helicone | `base_url`, либо один общий шлюз + заголовок `Helicone-Target-Url` | Apache-2.0 / шлюз **GPL-3.0** |
| Cloudflare AI Gateway | `base_url`; Universal Endpoint **объявлен устаревшим** | закрытая |
| Kong AI Gateway | обратный прокси, маршрут Kong | Apache-2.0 |
| Envoy AI Gateway | Gateway API route | Apache-2.0 |
| Arch → Plano | локальный listener `:12001/v1` | Apache-2.0 |
| Langfuse | **не прокси** — обёртка импорта, асинхронная телеметрия | MIT (кроме `ee/`) |
| OpenRouter | `base_url` | закрытая |

Ближе всех — **Helicone generic gateway**: один фиксированный адрес плюс заголовок
`Helicone-Target-Url`, выбирающий любого из 20+ разрешённых провайдеров. Это
произвольный провайдер за одну смену конфигурации — но всё ещё смена конфигурации.

**Вывод для позиционирования:** «поменяйте адрес» — не наша слабость, а отраслевая норма.
Обещать «поднял docker и всё» нельзя, потому что этого не делает никто, и клиентский
безопасник это знает.

## Форматы: где именно ломается возврат значения в аргумент

Это самая содержательная часть, и она меняет оценку сложности.

### Одинаковый путь ≠ одинаковая семантика

| провайдер | путь | где текст пользователя | аргументы вызова |
|---|---|---|---|
| OpenAI | `/v1/chat/completions` | `messages[].content` — строка **или массив** | `arguments` — **строка** JSON |
| Anthropic | `/v1/messages` | `content` — строка **или массив блоков** | `input` — **объект** |
| Gemini | `:generateContent` | `contents[].parts[].text` — **всегда массив** | `args` — **объект** |
| YandexGPT | `/foundationModels/v1/completion` | `messages[].text` — **не `content`** | `arguments` — Struct → объект |
| GigaChat | `/api/v1/chat/completions` | `messages[].content` | `arguments` — **словарь, не строка** |
| vLLM | оба пути сразу | по пути | синтезируется парсером из текста |

Два подвоха, которые стоят отдельного упоминания:

- **GigaChat отвечает на тот же путь, что и OpenAI, но `arguments` у него объект, а не
  строка**, плюс есть `functions_state_id`, который обязан пережить круг. Отличить по
  форме тела нельзя — только по хосту. `[B]`
- **YandexGPT в LiteLLM отсутствует вообще** — проверены все 137 провайдеров. Адаптер
  придётся писать самим по протобуфам `yandex-cloud/cloudapi`. `[A]`

Определение провайдера по `хост + путь + заголовок авторизации` разделяет диалекты без
коллизий и покрывает ~90% без конфигурации. Остаток — self-hosted на произвольном хосте
и OpenAI-подобные российские. `[B]`

### Четыре несовместимых режима фрагментации

| провайдер | как приходят аргументы в потоке |
|---|---|
| OpenAI | фрагменты JSON-строки, `required: [index]` — всё остальное опционально |
| Anthropic | `input_json_delta.partial_json`, **режет внутри слова** |
| Gemini | целые части; но есть недокументированный `partialArgs` с фрагментацией по значениям |
| vLLM | границы токенизатора произвольной модели — гарантий нет вообще |
| **GigaChat, YandexGPT** | **целиком** |

Дословный пример из документации Anthropic — одно значение разрезано на четыре события:
`"{\"location\":"` · `" \"San"` · `" Francisc"` · `"o,"` · `" CA\"}"`. `[A]`

`" Francisc"` / `"o,"` — разрез посреди слова. Телефон `+79991234567` режется так же.
**Вывод: сопоставить токен с дельтой в потоке невозможно в принципе** — для трёх из шести
провайдеров. Единственная корректная реализация — копить до границы блока.

Это ровно то, что уже делает наш `proxy.py`, и теперь понятно, что это не временное
упрощение, а **единственно верный дизайн**.

### Ловушка, которую стоит записать до реализации

Подстановка внутрь `arguments` — это правка **JSON-строки**: значение с кавычкой или
слэшем надо переэкранировать, а изменение длины сдвигает все последующие смещения. Плюс
спецификация OpenAI прямо предупреждает, что модель *не всегда* генерирует валидный JSON,
поэтому цикл «разобрать — изменить — собрать» может упасть на входе, который провайдер
считает допустимым. `[A]`

Ещё одна: у Gemini ключ может ехать **в query-параметре** `?key=`, поэтому прокси,
пересылающий только заголовки, потеряет учётные данные. `[A]`

### Хорошая новость для российского рынка

**GigaChat и YandexGPT — самый простой случай из всех шести**: аргументы приходят целиком,
фрагментации нет. То есть у наших основных провайдеров задача, которая у Anthropic
принципиально требует буферизации, решается тривиально.

## Что это значит для pseudex

### Решение: три уровня, и мы НЕ пишем слой нормализации

Главный вывод из форматной ветки — **не строить адаптеры под шесть провайдеров.**
LiteLLM под MIT уже покрывает 137 провайдеров и тратит на это 115 КБ только на
трансформацию Anthropic. Наша ценность — маскирование, а не маршрутизация.

**Уровень 1 — у клиента уже есть шлюз (LiteLLM, свой прокси).** Наш сайдкар,
`/mask` + `/unmask` одним callback. Мультипротокольность достаётся бесплатно: шлюз уже
привёл всё к одному виду. Это **самый зрелый** наш код, и именно он покрывает случай
«клиент ходит в Anthropic родным SDK».

**Уровень 2 — шлюза нет.** OpenAI-совместимый эндпоинт: клиент ставит
`OPENAI_BASE_URL=http://pseudex:4000/v1`. Рантайм безразличен — Go, PHP, Java, Node,
голый curl. Реализовано в `pseudex/proxy.py`; проверено, что вызовы инструментов там
намеренно буферизуются, и форматная ветка подтвердила, что это единственно верный дизайн.

**Уровень 3 — конфигурацию править нельзя.** `HTTPS_PROXY` + наш CA. Доказано на реальном
трафике. Продавать как «режим для закрытых систем», никогда как основной: разговор про
приватный CA убьёт сделку, которая прошла бы за одну переменную.

Жёсткое требование к третьему уровню, из практики российских инженеров: **перехват
только по списку хостов LLM-провайдеров, никогда не глобально.** Глобальный прокси
ломает pip, npm и обновления пакетов — это первая претензия, которую озвучивают, и она
справедлива. Плюс ГОСТ-TLS обходить стороной: устройство, вскрывающее ГОСТ-трафик, само
становится СКЗИ и требует сертификации ФСБ.

Почему такой порядок, а не обратный: цена для клиента растёт строго вниз — callback,
переменная, сертификат в каждом образе. Начинать разговор с самого дорогого варианта
значит проигрывать сделки, которые закрылись бы первым.

### Чего сознательно не делаем

**Не пишем адаптеры под Anthropic/Gemini.** Клиент с этими провайдерами ставит LiteLLM
(он у него, скорее всего, и так есть) и подключает нас уровнем 1.

**Исключение — YandexGPT.** Его в LiteLLM нет вообще, а для РФ-рынка он профильный.
Если клиенты им пользуются, адаптер писать нам, по протобуфам `yandex-cloud/cloudapi`.
Хорошая новость: у GigaChat и YandexGPT аргументы приходят целиком, без фрагментации —
это самый простой случай из шести.

### Что надо починить до этого

Проход по коду нашёл три дефекта именно в прокси-режиме:

1. `TENANTS = Tenants("tenants.db")` — **относительный путь**, `PSEUDEX_DB_DIR`
   игнорируется. В контейнере таблица арендаторов ложится мимо тома и пропадает при
   рестарте вместе со всеми ключами клиентов.
2. Колонка ключа переименовывалась дважды (`obscura_key` → `veilgate_key` →
   `pseudex_key`) **без миграции**, а `CREATE TABLE IF NOT EXISTS` молча пропускает
   существующую таблицу. Апгрейд ломается на первой записи с невнятной ошибкой.
3. `_mask_messages` в прокси отстал от сайдкара: нет кеша, нет отгрузки в threadpool,
   нет multi-part контента. Под нагрузкой прокси слабее.

Что при этом **сделано правильно** и переделывать не надо: вызовы инструментов в прокси
намеренно не стримятся — «token-by-token detok of streamed tool args can't retract an
already-sent fake prefix, so we buffer — correctness over smoothness». Ровно та проблема
фрагментации, которую я замерил выше, уже решена буферизацией.

### Про арендаторов

Сейчас клиент должен зарегистрировать ключ провайдера и получить `sk-ps-…`. При тарифе
по контейнерам (один контейнер = один клиент) таблица арендаторов не окупается: лишний
шаг при подключении и хранение чужого секрета. Pass-through — пересылка заголовка
клиента наверх — убирает и то, и другое. Объём правки ~15 строк.

## Как к перехвату относятся в отрасли и в РФ

### Рынок раскололся надвое

**Сетевые старожилы** (Zscaler, Netskope, Palo Alto, Cato) перехватывают TLS с CA,
который ставит клиент. Zscaler говорит это прямым текстом как о предусловии: без
включённого SSL-инспектирования их AI-DLP просто не работает. `[A]`

**AI-нативные** (Lakera, Prompt Security, Wiz, Cisco Inspection API) — **не перехватывают**.
Lakera это чистый API: приложение само шлёт текст на `api.lakera.ai/v2/guard`. `[A]`

Самое интересное — аргумент изнутри отрасли. Prompt Security (куплена SentinelOne)
публично пишет, почему прокси — неправильное место:

> «When prompts are processed and reasoning happens on-device, there is simply nothing
> useful for a proxy to inspect.» `[A]`

То есть «перехватывать всё на сетевом уровне» — не консенсус, а одна из двух школ, и
вторая считает её тупиковой.

### В России MitM — норма документа, но не норма умолчания

UserGate в собственной документации пишет без эвфемизмов: `[A]`

> «UserGate NGFW с функцией SSL-инспектирования выступает в роли доверенного посредника
> (Man-in-the-Middle, MitM)… необходимо добавить корневой сертификат центра сертификации
> в доверенные корневые сертификаты.»

Так что просьба «поставьте наш корневой сертификат» для российского безопасника —
знакомая процедура, а не экзотика. Но три вещи ломают наивный оптимизм:

**Ideco по умолчанию НЕ подменяет сертификаты** — фильтрует по SNI, а расшифровка
включается отдельным правилом и требует настройки рабочей станции **каждого**
пользователя. `[A]` То есть отраслевой умолчательный режим в РФ — как раз без перехвата.

**Половину HTTPS расшифровать нельзя** — pinning, клиентские сертификаты. Это оценка
Дениса Батранкова, известного российского инженера по NGFW. `[B]`

**ГОСТ-TLS — отдельный класс продуктов.** Обычный NGFW его не вскрывает вовсе, а
устройство, которое трогает ГОСТ-трафик, само становится СКЗИ и требует сертификации
ФСБ. `[B]` Для нас это значит: **никогда не быть общим egress-прокси**, только по
списку хостов LLM-провайдеров.

Регуляторного запрета нет: ни ФСТЭК, ни ФСБ не предписывают и не запрещают
SSL-инспекцию. Сертификации она не мешает — UserGate, Ideco и Континент 4 её везут. `[B]`

### Возражения инженеров, которые мы услышим дословно

С Хабра, тред про DPI: `[C]`

> «5 потенциальных точек перехвата/изменения информации вместо двух. Что, простите, в
> этом более безопасного?»

> «прощай обновления пакетов, pip и прочие… по факту это создает больше проблем, чем
> решает»

Второе — прямое техническое требование к нашему третьему уровню: **перехват обязан быть
ограничен хостами LLM-провайдеров.** Глобальный `HTTPS_PROXY` сломает клиенту pip, npm и
обновления, и виноваты будем мы.

Опрос Ideco/SOC FORUM (декабрь 2025, n=119): только **8,4%** используют NGFW на ~100%
функций, 41%+ называют слабую производительность под нагрузкой критичным недостатком, а
10,9% прямо жалуются на «медленную или нестабильную SSL/TLS-инспекцию». `[B]`

Вывод для лендинга: перехват как **опция для закрытых систем** — понятная и продаваемая
позиция. Перехват как **основной способ подключения** — это разговор, в котором нас
сравнят с NGFW, у которого производительность считается главной болью рынка.

---

## Критический анализ

**Сильнейший контраргумент к «основной путь — base_url»:** это механизм сотрудничества,
а не принуждения. Инженер клиента может вернуть адрес обратно на провайдера, и ПД
потекут. Для продукта, который продаётся как соответствие 152-ФЗ, это дыра в самом
обещании.

Ответ: honest one. Прозрачный перехват её тоже не закрывает — `NO_PROXY`, свой
`http_client`, pinning, или просто другой контейнер обходят и его. Единственное реальное
принуждение — сетевое: закрыть исходящий доступ к API провайдеров на файрволе и оставить
маршрут только через нас. Это делает клиент, не мы, и об этом честно писать в
документации для безопасника.

**Что должно быть верно, чтобы вывод держался:** что OpenAI-формат покрывает
большинство клиентов. Если окажется, что российский средний бизнес массово ходит в
GigaChat и YandexGPT напрямую их родными SDK — вывод меняется, и нужны адаптеры
форматов. Эта ветка ресёрча ещё не вернулась.

**Чего я не проверял:** поведение Go (нет на машине), JVM, gRPC-транспорта; работу
перехвата под HTTP/2 и pinning в SDK; поведение при больших телах и длинных таймаутах.

## Открытые вопросы

- **Меняет ли терминация TLS наш статус по 152-ФЗ** — прямого ответа не нашли. Регулятор
  про SSL-инспекцию не высказывается вовсе, а мы остаёмся внутри контура клиента, так
  что оператором становимся вряд ли. Но это рассуждение, а не найденная норма — перед
  запуском третьего уровня стоит спросить юриста явно.
- **Живой прогон `pseudex/proxy.py` конец-в-конец не удался**: лицензионный клиент не
  доверился локальному серверу, `SSL_CERT_FILE` не помог (в `license.py` клиент строится
  с явным `verify`). Причина в транспорте лицензии, не в маскировании, но круг через
  прокси на живой модели пока не подтверждён.
- **Go и JVM не проверены эмпирически** — на машине нет ни того, ни другого. По
  документации: JVM игнорирует `HTTP_PROXY`, у Go на macOS нет `SSL_CERT_FILE`.
- **Доля клиентов, ходящих в GigaChat/YandexGPT напрямую родными SDK**, неизвестна. От
  неё зависит, нужен ли нам собственный адаптер Яндекса.
- Gemini `functionCall.partialArgs` — недокументированный седьмой формат, замечен только
  в исходниках Vercel AI SDK.
