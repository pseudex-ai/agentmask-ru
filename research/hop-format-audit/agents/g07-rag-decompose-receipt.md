# Группа 07: rag + decompose + receipt

**Данные.** Все числа — из `research/hop-format-audit/agents/00-case-metrics.json` (54 кейса группы).
Все цитаты — дословно из прогона `prototype/bench/runs/2026-09-28/v5-live-cohort2-450-v5/`
(коммит `a7571ee`, `deepseek-flash`, одна живая рука — **I**, то есть шлюз в боевом пути;
парных рук C/C′ в этом прогоне нет). Файлы кейса: `corpus.v5.json` → `*.arms.v5.jsonl` (написано/восстановлено),
`*.canary.jsonl` (точные байты, которые модель читала), `*.hops.jsonl` (вердикты по хопам).

**Что за метрики.** `end_to_end` — «инструмент получил настоящее значение» по ВСЕМ объявленным OUT/tool_arg
хопам, `absent` и `unmasked` идут в знаменатель промахом. `form OUT/tool_arg` — совпала ли ФОРМА
(падеж, разделители, префикс, порядок слов), а `unmasked` — это «лист не нёс подмены» и он тоже промах.
`multi_all_out` — ход, где все обязательные OUT/tool_arg верны и по значению, и по форме.
`coverage`/`leak` — по объявленным IN-хопам: ни одного куска значения не осталось / значение заменено.

**`chain_value`/`chain_form` в этой группе не существуют.** Не «низкие» — знаменатель НОЛЬ.
`chain_*` строится по переходам «OUT-хоп, чей `source_hop` указывает на IN/tool ДРУГОГО инструмента».
В rag-кейсах `source_hop` хопа `kb_search.query` указывает на IN/user, то есть на сообщение клиента,
а не на результат `crm_find_contact`, хотя фактический перенос «прочитал карточку → понёс имя в запрос к базе»
в прогоне происходит (rag-034, звонок 4: запрос «Крылова Тамара два метра» → «Лебедева Ирина два метра»).
Такой хоп записывается как недекларированный (`hop_index=-1`) и попадает только в form-строки.
Итог: 36%, о которых говорит бриф, приходят из других групп; здесь рука-передача rag не измеряется вовсе.

**`end_to_end` = 58.2% при `leak` 99.7%.** Разрыв — это не «шлюз перестал защищать», а 56 промахов
на 134 объявленных OUT/tool_arg хопах, и они раскладываются по причинам без остатка:

## Что работает хорошо

**1. Письменный идентификатор раскладывается по частям безупречно — decompose-003 против decompose-000.**
Это контролируемая пара: один и тот же шаблон, тот же `passport_verify`, те же 9 объявленных хопов,
разница только в регистре источника.

decompose-003 (написано: «сверьте паспрот 0312943300 … снилс 14604486963 бударина василиса гордеевна»):
подмена `i1 = "0025071207"` с частями `{"series": "0025", "number": "071207"}`;
модель написала `"number": "071207", "series": "0025"` — то есть ровно разложила подмену по полям,
на какие её и просил системный промпт; шлюз вернул `"number": "943300", "series": "0312"`,
СНИЛС «529-699-125 51» → «146-044-869 63», ФИО «Фомина Капитолина Кирилловна» → «Бударина Василиса Гордеевна».
Все 9 хопов `observed` и `same`, `end_to_end` 6/6, `multi_all_out` 1/1. Форма в обе стороны совпала,
включая переформатирование СНИЛС из сплошных цифр в «146-044-869 63».

decompose-000 — тот же кейс вслух («сорок ноль пяять шестьсот шесть ноль девятнадцать»):
подмена приходит СЛОВАМИ («ноль ноль два ноль ноль сорок восемь четыре восемьдесят девять»),
и разложить её по полям уже нечем: см. паттерн P3.

**2. Форма на ходе «инструмент → модель» идеальна: `form IN/tool` = 241/241 (100%).**
Каждый объявленный IN/tool хоп вернулся в той форме, в какой агент его читал, — включая канон,
которым инструмент печатает значение (ISO-дата, `+7 (916) …`, строчная фамилия в JSON-поле).
Например, rag-046: настоящая карточка держит `"address": {"city": "сортавала", "street": "ленина", "house": "1б", "flat": "1"}`,
а модель читает `"street": "абрикосовая", "house": "3", "flat": "224"` — канон инструмента переложен
в подмену той же формы, и ни один кусок настоящего адреса в JSON не остался (город «сортавала» стоит
в обоих, потому что город подмена не трогает — см. P7б).

**3. Восстановление внутри свободной прозы — и без овермаскирования соседей.**
decompose-007: модель НЕ вызвала инструмент (уточняющий вопрос про «завтра с десяти до двух … к 9 часам»),
но в ответе перечислила всё: `reply_raw` «Екатеринбург, Ивовый проезд, д. 107, подъезд 11, кв. 156, получатель Тихонова Татьяна, тел. +79972188179»,
а клиент прочитал «Екатеринбург, Неркасова, д. 170, подъезд 6, кв. 119, получатель Лебедева Ирина, тел. +79875487262» —
восстановлены улица, дом, подъезд и квартира по отдельности, в предложении, где рядом стоят слова,
напоминающие адресные. Тут же — негатив из кейса «к 9 часам» остался «к 9:00» и не был замаскирован:
`overmask` 54/54 по всей группе.

rag-034, звонок 4: запрос `"Крылова Тамара два метра"` → `"Лебедева Ирина два метра"`.
Имя с фамилией восстановлено внутри свободного текста, а рядом стоящий числовой негатив
(«два метра», он же объявленный `negatives`) не тронут — ни в значение, ни в форму запроса шлюз не вмешался.

**4. Переиндексация по цифровой подписи спасает там, где модель переписала подмену своими разделителями.**
rag-008: модель написала `{"query": {"phone": "+45985880975"}}` (это подмена, см. P4),
шлюз вернул `+79628863588` — инструмент получил настоящий номер, `end_to_end` этого кейса 1/1.

## Разбор худших кейсов

### decompose-002 (1/3) — «производная форма» уносит имя из объявленных листьев

`hops.jsonl`, кейс `CARD:4276060070335511`, регистр `voice_raw`:

```
h0 IN/user  i1 CARD — подмена «ноль семь двадцать один восемь восемьдесят шесть ноль сорок семь пятьдесят шесть ноль шесть десять», форма совпала
h1 IN/user  i2 NAME — подмена «егор бобров», форма совпала
h2 OUT/tool_arg i1 payment_create:payment_method_data.card.number        observed  «4276060070335511» ← «0721886047560610»
h3 OUT/tool_arg i2 payment_create:payment_method_data.payer_bank_details.full_name  unmasked  «» / «»   ← ПРОМАХ
h4 OUT/tool_arg i2 payment_create:receipt.customer.full_name                        unmasked  «» / «»   ← ПРОМАХ
h-1 OUT/answer  i2 NAME  «DMITRIY KUZNETSOV» ← «EGOR BOBROV», форма разошлась: script                  ← ПРОМАХ
```

Что было написано и что ушло в инструмент (`arms.v5.jsonl`):

```
written : ... "card": {"cardholder": "EGOR BOBROV",  "number": "0721886047560610"}
restored: ... "card": {"cardholder": "DMITRIY KUZNETSOV", "number": "4276060070335511"}
```

ПОЧЕМУ: системный промпт кейса сам велит «держатель карты — латиницей заглавными, как на карте»,
а схема `payment_create` имеет отдельный лист `payment_method_data.card.cardholder` с описанием
«Имя держателя ЛАТИНИЦЕЙ заглавными». Модель положила имя туда и больше никуда. Шлюз восстановил
этот лист КОРРЕКТНО (в инструмент ушло `DMITRIY KUZNETSOV`) — но хоп объявлен на
`payer_bank_details.full_name` и `receipt.customer.full_name`, которые относятся к другим способам
оплаты (`b2b_sberbank`) и к чеку. Обе клетки `end_to_end` потеряны, хотя настоящее имя до инструмента доехало.
Это не промах движка, это объявление, которое требует от агента листа, к которому его собственный
промпт не направляет (P2).

Вторая потеря — форма на ответе: `produced «DMITRIY KUZNETSOV»` против `reference «EGOR BOBROV»`,
расхождение `script`. Подмена была кириллической («егор бобров»), модель сама перевела её в латиницу,
шлюз вернул фамилию тоже латиницей, но собственной транслитерацией. Компаратор различает латиницу
по ПОДПИСИ транслитерации (`form_tables.TRANSLIT_SIGNATURES`: `latin:icao` — `shch`, `iu`, `ia`;
`latin:gost` — `shh`, `cz`, `yu`+`j`, `ya`+`j`; `latin:bgn` — `yu`, `ya`, `kh`, `ts`, финальная `y`;
иначе `latin:unknown`). Проверено на движке: `name_script('DMITRIY KUZNETSOV') = latin:bgn`
(финальная `y`), `name_script('EGOR BOBROV') = latin:unknown` — и `form_match` называет это
расхождением письменности. Обе строки латинские; расходятся конвенции романизации (P9).

Третья потеря — не хоп, но видная: в переотправленном контексте собственный вызов агента замаскирован
по-новому (точные байты `canary.jsonl`, `model_request`):

```
"cardholder": "REDACTED2aada2"      ← что модель читает во втором запросе
"cardholder": "EGOR BOBROV"         ← что она сама написала в первом
```

То есть агент видит не свою прошлую запись, а безымянную заглушку (P5).

### decompose-007 (0/5, `multi_all_out` 0/1, `out_absent` 1.0) — агент не позвонил, и это не промах шлюза

Все пять объявленных OUT/tool_arg хопов — `absent`: `address.locality`, `address.street`,
`address.building`, `contact.name`, `contact.phone` при `tool=courier_book`. Вызовов `courier_book` нет.
Ответ (`arms.v5.jsonl`):

> «Уточните, пожалуйста, время вызова курьера — в заявке получилось противоречиво: «завтра с 10:00 до 14:00» и одновременно «к 9 часам». Какой интервал указать?»

ПОЧЕМУ: в сообщении клиента два противоречивых интервала, а системный промпт велит «переспрашивай
только то, чего не хватает для вызова». Модель сочла, что не хватает именно интервала.
`end_to_end` 0/5 здесь целиком принадлежит поведению агента, и `out_absent` (диагностика рядом
с form_hOUT) — единственное место, где это видно; без него `form OUT/tool_arg` кейса просто «н/п».

Один промах формы всё-таки есть и он шлюзовый: `h-1 OUT/answer LOC` — `produced «Неркасова»`
против `reference «Ивовый проезд»`, расхождение `generic`. В подмене `i1` части такие:
`{"entrance":"11","flat":"156","house":"107","street":"екатеринбург ивовый"}` — название города
сидит в улице; при обратном перекладывании словосочетание «Ивовый проезд» превратилось в «Неркасова»
без слова «проезд», и клиент читает адрес без типа улицы.

### rag-046 (0/2) — диктовка словами: модель оцифровала подмену неверно, шлюз не угадал

Клиент продиктовал: «восемь девятьсот шестьдесят два сто сорок один пятьсот шестьдесят восемсь семь»
(настоящее `+79621415687`). Подмена `i20` выдана В ТОМ ЖЕ регистре, словами:
«восемь девятьсот шестьдесят четыре семьсот сорок семьсот девяносто три шесть» (подделка `+79647407936`).
Модель:

```
CALL 1 crm_find_contact  written == restored  {"query": {"phone": "+79647477936"}}
```

Восемь написала верно, а «семьсот сорок семьсот» прочитала как лишнюю семёрку: `+79647477936`
вместо `+79647407936`. Ни один токен волта на такой промах не отзывается, поэтому инструмент
получил ПОДДЕЛКУ (это и есть `unmasked`, `h2`), карточка не нашлась (пустой `contacts`), и обе
карточные IN/tool-обязанности (`h3`, `h4`) стали `absent`.

Дальше модель искала по теме: `CALL 2 kb_search {"k": 5, "query": "доставка 11 паллет условия"}` —
и в запрос имени не понесла, поэтому `h5 OUT/tool_arg i19 kb_search:query` = `unmasked`
(`written == restored == "доставка 11 паллет условия"`), и это второй промах `end_to_end`.

И третье, что видно только в байтах: в переотправленном контексте собственный звонок агента
замаскирован ДРУГИМ телефоном —

```
MASKED: {"query": {"phone": "+79391654411"}}
REAL  : {"query": {"phone": "+79647477936"}}
```

То есть агент не может посмотреть на свой предыдущий вызов и увидеть, что он ошибся (P5).
`turns=52` у этого кейса против 21–37 у decompose (67 у decompose-000 — там своя петля на диктовке).

И ещё одна потеря, видная клиенту и не видимая ни одной метрике, — производная форма, которую движок
не перевернул:

```
reply_raw: **Клиент:** Юдин Назар Петрович (Nazar Petrovich Yudin), инициалы Н.П.Ю.
reply    : **Клиент:** Букин Сергей Иванович (Sergei Ivanovich Bukin), инициалы Н.П.Ю.
```

ФИО и латинское написание восстановлены, а СЖАТЫЕ ИНИЦИАЛЫ остались от подмены: клиент читает рядом
своё настоящее имя и «Н.П.Ю.» другого человека. Сравнение с rag-034, где та же конструкция
восстановлена верно («инициалы Т.С., лат. Tamara Sergeevna Krylova» → «инициалы И.П., лат. Irina Petrovna Lebedeva»),
показывает, что дело не в классе форм вообще, а в конкретной форме записи: «Н.П.Ю.» в конце строки
без продолжения не опознаётся, а «Т.С.» в связке с полным именем — опознаётся.

### rag-034 (0/2, `turns=102`) — тот же класс, доведённый до петли

Подмена `i20` словами: «восемь девятьсот пятьдесят четыре пятьдесят сорок двадцать три пять»
(подделка `+79545040235`). Модель оцифровала её дважды и оба раза неверно:

```
CALL 1 crm_find_contact  written == restored  {"query": {"phone": "+7954504235"}}     ← 10 цифр
CALL 3 crm_find_contact  written == restored  {"query": {"phone": "+79545042355"}}    ← 11 цифр, лишняя 5
```

Причём mock отказывает на первом же: `tool_result` — `{"error": {"code": "phone_not_e164", "field": "query.phone", "message": "поле query.phone: phone_not_e164: +7954504235"}}`.
Тот же отказ в переотправке читается моделью так (точные байты):

```
MASKED: "message": "поле query.phone: phone_not_e164: REDACTED998663"
REAL  : "message": "поле query.phone: phone_not_e164: +7954504235"
```

Проверка `carries_any('PHONE', [подмена-словами], текст)` даёт `True` для правильной оцифровки
`+79545040235` и `79545040235` (в иголках есть цифровая подпись подмены: `('digits','9545040235')`)
и `False` для обеих написанных моделью строк. То есть шлюз не «пожадничал»: он не мог отобразить
чужой номер обратно, не угадывая. Но `end_to_end` = 0/2, и петля на 102 хода — следствие того же места.
Четвёртый звонок (`kb_search "Крылова Тамара два метра"` → `"Лебедева Ирина два метра"`) показывает,
что свободный текст с именем восстанавливается там, где имя действительно написано.

### decompose-000 (4/6, `multi_all_out` 0/1) — диктованный паспорт разложен по частям, и настоящий паспорт утёк в результате

Продиктовано: «сорок ноль пяять шестьсот шесть ноль девятнадцать» (настоящее `4005 606019`).
Подмена — словами, у неё ПУСТЫЕ части: `substitutes["i1"] = ["ноль ноль два ноль ноль сорок восемь четыре восемьдесят девять", {}]`
(сравните decompose-003, где у подмены `{"series":"0025","number":"071207"}`). Модель разложила
подмену по полям правильно и шлюз восстановил оба:

```
written : {"passport": {"number": "048489", "series": "0020"}}
restored: {"passport": {"number": "606019", "series": "4005"}}
```

а `hops.jsonl`:

```
h3 OUT/tool_arg i1 passport_verify:passport.series  unmasked  produced «4005»  reference «0020»   ← ПРОМАХ
h4 OUT/tool_arg i1 passport_verify:passport.number  unmasked  produced «606019» reference «048489» ← ПРОМАХ
```

ПОЧЕМУ: наблюдатель восстанавливает части подмены разбором её ПОВЕРХНОСТИ (`parts_of(type, surface)`).
Из прогона слов «0020» не выводится, части остаются пустыми, и лист `series` не опознаётся как наш —
хотя значение до инструмента доехало. `multi_all_out` 0/1 из-за этих двух клеток.

И то, что важнее любых метрик: результат `passport_verify` возвращает НАСТОЯЩИЙ паспорт в открытом виде —
`canary.jsonl`, `tool_result`:

```
MASKED: { "person": {"last_name": "сазонов", "first_name": "роман"}, "passport": {"series": "4005", "number": "606019"}, "snils": "788-337-700 63" }
REAL  : { "person": {"last_name": "букин",   "first_name": "сергей"}, "passport": {"series": "4005", "number": "606019"}, "snils": "805-387-569 27" }
```

Серия и номер паспорта одинаковы в маскированных и настоящих байтах — модель их прочитала,
и это видно в её собственном ответе: `reply_raw` пишет «Обратите внимание: в системе паспорт
значится как серия **4005 № 606019** — прошу сверить с оригиналом документа, так как на слух
серия и номер были названы иначе», то есть модель сравнила НАСТОЯЩИЙ номер из результата инструмента
с подменой `0020 048489`, которую сама же и написала (и из-за утечки сравнение выглядит осмысленным).
Кейс не объявляет ни хопа IN/tool, ни `returns` для этой ноги, поэтому ни `leak`, ни `coverage`,
ни `toolresult_masked` этого не видят: `leak` 3/3, `coverage` 3/3, а инструмент получил верные
`series`/`number` — то есть по метрикам кейс «справился».

Родственный эффект — на decompose-003, где утечки нет: там модель написала «в базе паспорт числится
как **0312 943300**, а вы называли **0025 071207**», а после восстановления клиент читает
«как **0312 943300**, а вы называли **0312 943300**» — сравнение схлопнулось в тавтологию.
Это цена подмены, которую агент использует в СРАВНЕНИИ: обе половины фразы восстанавливаются
в одно и то же настоящее значение.

### rag-008 (1/1 `end_to_end`, но `form OUT/tool_arg` 0/1 и `coverage` 3/4) — телефон, прошедший контрольную сумму СНИЛС

Клиент написал `+79628863588`. Точные байты:

```
MASKED: это мухина вероника телефон +45985880975 поднимите протокол по теме гарантия и скажите что там по мне кстати за проезд наличными
REAL  : это павлова тамара телефон +79628863588 поднимите протокол по теме гарантия и скажите что там по мне кстати за проезд наличными
```

`+45985880975` — это не российский номер: 11 голых цифр встали на место прогона ПОСЛЕ знака «+»,
а сам «+» остался литералом. Записанные спаны кейса: `{'1': [[4,18],[28,39]]}` — прогон `79628863588`
начинается с индекса 28, тогда как объявленное место значения — `[27,39]`, вместе с «+».
Воспроизводится тривиально (`testkit.load_dev_bundle()`, `Detector().detect`):

```
detect('+79628863588') -> [('Span', 1, 12, '79628863588', 'SNILS')]
validate_snils('79628863588') -> True
```

Одиннадцать цифр российского номера с кодом страны удовлетворяют контрольной сумме СНИЛС,
а `_PRIORITY` ставит контрольные суммы (6) выше телефонов (5), поэтому прогон объявлен СНИЛС,
и `_render_token('SNILS')` выдаёт 11 голых цифр. Отсюда сразу три следствия: `form OUT/tool_arg` 0/1
(подмена с префиксом `+45` против настоящего `+7` — расхождение `prefix`/`grouping` по построению),
`coverage` 3/4 (спан на символ короче объявленного места значения, проверка вложенности падает)
и `end_to_end` 1/1 (значение спасла переиндексация по цифровой подписи при восстановлении).
В группе таких телефонов три кейса: rag-008 (`i4`/`i13`), rag-025 (`i18`), rag-048 (`i16`).

## Паттерны причин

**P1. Объявленный обязательный OUT-хоп, которого задача агента не требует.** 30 свидетелей — все rag-кейсы,
где `h5 OUT/tool_arg i19 kb_search:query` объявлен `optional=False`, а `crm_find_contact.query.phone` —
`optional=True` (по корпусу: 41 телефонный хоп `optional=True`, 31 именной `optional=False`).
Агент всегда несёт телефон в поиск карточки и почти никогда не несёт имя в тематический
поиск по базе знаний: в `written` стоит `"перевыпуск карты клиенту"`, `"возврат товара условия"`,
`"доставка 11 паллет условия"` — тема без человека, и `_out_status` честно говорит `unmasked`
(лист есть, подмены в нём нет). В 26 случаях промах виден прямо в `hops.jsonl`; ещё в 4
(rag-013/019/030/033) строка хопа в файл прогона не попала, но метрика его считает —
`end_to_end` у них всё равно 1/2. Отсюда `end_to_end` 1/2 в 27 кейсах, 0/2 ещё в трёх
и `multi_all_out` ноль по всей группе. Единственный кейс, где имя в запросе есть, — rag-027
(`"рассрочка 21 гектар Боброва"`), и у него `end_to_end` 2/2, `form OUT/tool_arg` 3/3.

**P2. Производная форма вместо объявленного листа.** 14 хопов в 7 кейсах: decompose-002/005/008,
receipt-000/002/003/005. Везде одно и то же: `payment_create` даёт отдельный лист
`card.cardholder` («латиницей заглавными, как на карте») и отдельные листья-идентичности
`payer_bank_details.full_name` / `receipt.customer.full_name`, а объявлен именно второй.
Модель заполняет первый (он и описан как «как на карте»), шлюз восстанавливает его правильно,
объявленный лист остаётся пустым. `end_to_end` падает вдвое, `form_hOUT` тоже, потому что `unmasked`
идёт в знаменатель.

**P3. Подмена, выданная в регистре источника («диктовка»), не разложима по частям и плохо оцифровывается.**
Две стороны одного механизма.
*(а) Частей нет.* Для письменного идентификатора подмена имеет части (`{"series":"0025","number":"071207"}`),
для продиктованного — пустой словарь, потому что поверхность подмены это прогон русских слов.
Свидетели: decompose-000 (`passport.series`/`passport.number` → `unmasked` при восстановленном значении),
decompose-002/005/008 и receipt-* (там тот же эффект на NAME-листьях, но с другой причиной — P2).
*(б) Оцифровка моделью.* Три свидетеля — rag-034, rag-035, rag-046: модель переводит словесную подмену
в цифры и ошибается (`+79647477936` вместо `+79647407936`; `+7954504235`, затем `+79545042355`),
шлюз не может отобразить чужой прогон и оставляет в инструменте подделку. Заметьте: правильная
оцифровка распозналась бы (цифровая подпись подмены есть в иголках) — то есть это не слепота
инструмента, а именно совместный отказ «регистр подмены + цифровая форма листа».

**P4. Приоритет контрольной суммы над формой: 11-значный прогон, проходящий СНИЛС, съедает телефон.**
`+7 962 886 35 88` → `79628863588` проходит `validate_snils`, `_resolve` отдаёт прогон СНИЛС
(приоритет 6 против 5), спан начинается ПОСЛЕ «+», `_render_token('SNILS')` выдаёт 11 голых цифр,
«+» остаётся литералом → `+45985880975`. Свидетели: rag-008, rag-025, rag-048
(3 из 254 телефонных упоминаний группы, 219 телефонных item-ов; 4 упоминания, потому что `i4` и `i13`
в rag-008 — один и тот же номер). Последствия тройные и все измеряемые: подмена перестаёт быть
телефоном (форма OUT расходится по `prefix`/`grouping` по построению), спан короче объявленного
места значения на один символ (`coverage` 3/4 у rag-008 — единственная coverage-потеря группы,
где виноват именно приоритет типов; вторая — пропуск детекции имени в rag-024, P8; три — ложные
срабатывания на общем слове, P7а; шестая в rag-024 не атрибутирована и требует отдельного прохода),
а значение на выходе спасает только переиндексация по цифровой подписи.

**P5. Эхо собственного вызова агента перемаскируется заново — в другую подмену или в `REDACTED…`.**
8 кейсов: decompose-002/005/008, receipt-000/002/003/005 (через `cardholder`) и rag-034 (через тело ошибки).
Точные байты: `"cardholder": "EGOR BOBROV"` ушло в инструмент как `DMITRIY KUZNETSOV`, а в следующем
запросе модель читает `"cardholder": "REDACTED2aada2"`; receipt-000 — `REDACTEDce0a51`, receipt-002 —
`REDACTEDf17744`, receipt-005 — `REDACTED8a26b0`, decompose-008 — `REDACTEDcbe771`.
В rag-034 хуже: собственный телефон агента `+7954504235` в переотправке стал `+9551910737`
(третья по счёту подмена одного и того же прогона в одном диалоге), а эхо того же значения в теле
ошибки — `REDACTED998663`. Механизм в коде виден: `envelope._neutral_redaction` — «консервативная
замена для эха, чья привязка неоднозначна», `REDACTED<6hex>`, вне индекса токенов.
Следствие для продукта: агент не может учиться на своей же истории — он не видит, что написал,
и в rag-034/046 именно это удерживает петлю (`turns=102` и `52`).

**P6. Голый адъективный/фамильный стрит без родового слова и без дома не рождается как кандидат.**
20 свидетелей из 23 находок «настоящее значение стоит в маскированном результате инструмента» — это
улица ЧУЖОГО клиента в `hits[].text` / `body`. Точные байты rag-001: `MASKED` содержит
«Вторым заявителем идёт Мухин Савва по адресу октябрьский телефон +79752903722», `REAL` —
«Кузнецов Дмитрий по адресу октябрьский …»: имя и телефон заменены, улица — нет. Воспроизведение
на движке показывает границу класса точно: после «по адресу» маскируются `шумайлова`, `лермонтова`,
`гончарук` (это фамилии в лексиконе имён — их ловит именной путь, тип NAME), и НЕ маскируется ни одно
из `октябрьский`, `светлый`, `репина`, `комсомольский`, `садовая`, `кирова`, `союзная`, `вольная`,
`челюскинцев`, `коммунаров`, `строительный`, `лесная`, `зелёный`, `северный`, `смольный`, `дзержинского` —
адресный путь без родового слова и без дома не срабатывает, а именной их не знает.
Кейсы объявляют эти улицы (`returns.result_item_ids` включает `i10`), но НИ ОДНОГО хопа на них нет,
поэтому и `leak` (99.7%), и `coverage` (98.3%) их не видят. В ответ клиенту они не попадают ни разу —
проверено по всем 54 `final_answer`.

**P7. Инструмент и объявление расходятся в том, что считать «не защищено».**
*(а)* 3 из 5 не-`leaked` coverage-потерь — ложные: `item_survives_in` ищет кусок НАСТОЯЩЕГО значения
в маскированном тексте, а в тексте стоит подмена ДРУГОГО человека, случайно делящая слово:
rag-015 `reference «Кузнецова Ольга»` против `«Мещерякова Ольга»` в тексте, rag-035
`«Лебедев Максим»` против `«Лебедев Ратмир»`, rag-047 `«Битюкова Зинаида»` против `«Наумова Зинаида»`.
*(б)* `address.locality` (`decompose-001`, `decompose-004`) — хоп, который не может стать `observed`
по построению: подмена город НЕ меняет (`можга школьная дом 64 …` → `Можга, улица Мятная 14, подъезд 22, кв. 167`),
потому что город — не ПД. Агент пишет `"locality": "Можга"`, шлюз правильно ничего не трогает,
`_out_status` говорит `unmasked` — и это промах. То же слово `unmasked` покрывает и «агент не заполнил
лист» (14 хопов P2), и «в листе чужое значение» (3 хопа P3б), и «лист сохранил нетронутый город» (2 хопа P7б).

**P8. Редкая фамилия строчными в чате доходит до модели целиком.** rag-024 — единственный `leaked`
хоп группы из 359. Точные байты:

```
MASKED: алло это авченко ефим телефон 8 993 720 08 03 посмотрите что у вас в базе по теме перевыпуск по мне да и заказ 128
REAL  : алло это авченко ефим телефон 8 912 695 49 52 посмотрите что у вас в базе по теме перевыпуск по мне да и заказ 128
```

Телефон замаскирован, имя — нет. На движке: `detect('это авченко ефим')` → пусто,
`detect('алло это Авченко Ефим телефон 8 912 695 49 52')` → `NameSpan 'Авченко Ефим'`,
`detect('это павлова тамара')` → `NameSpan`. То есть заглавная форма ловится NER-ом, строчная
опирается на лексикон имён, и редкая фамилия в нём отсутствует — ровно тот класс, который
`CLAUDE.md` называет «72.1% пропусков MASSIVE — слов нет в словаре вовсе, кандидат не рождается».
Слово `unmasked` тут не при чём: значение не заменено НИКАК.

**P9. Латинское имя против латинского имени считается расхождением ПИСЬМЕННОСТИ.** Самый массовый
класс формы в группе: 50 хопов из 60 form-промахов — это ровно `OUT/answer NAME ('script',)`,
и все 50 — латиница против латиницы. Признак `script` (`form.name_script`) различает не алфавит,
а ПОДПИСЬ романизации (`latin:icao` / `latin:gost` / `latin:bgn` / `latin:unknown`), поэтому
`form_match('NAME','Bukin','Yudin')` = `script` (unknown против bgn), `form_match('NAME','DMITRIY KUZNETSOV','EGOR BOBROV')` = `script`
(bgn против unknown). Свидетели: 17 кейсов, 50 хопов — decompose-002, rag-001/005/007/011/016/018/029/031/032/037/038/046/047,
receipt-000/003/005. Кейсы сами провоцируют класс: в rag и receipt системный промпт велит
«инициалы и латинское написание имени заполняй сам по ФИО», в платёжных — «держатель карты — латиницей
заглавными». Отдельно замечу механизм у движка: подмена была КИРИЛЛИЧЕСКОЙ, модель перевела её в латиницу
САМА, и `translit.align` («перенимай конвенцию агента») остался без входных данных — перенимать было нечего,
поэтому движок отрисовал настоящее имя своей конвенцией (`DMITRIY` с финальной `y` → `latin:bgn`),
а модель свою (`EGOR`) ни под одну подпись не подвела. Во всех случаях, которые я прочитала глазами
(decompose-002, rag-046, receipt-000), `produced` — это НАСТОЯЩЕЕ имя в латинице агента,
и расхождение помечено только признаком `script`.

**P10. Сжатые инициалы в ответе переворачиваются не всегда.** rag-046 — «инициалы Н.П.Ю.»
остаются от подмены рядом с восстановленным «Букин Сергей Иванович (Sergei Ivanovich Bukin)»;
rag-034 — «инициалы Т.С., лат. Tamara Sergeevna Krylova» восстанавливаются в «инициалы И.П.,
лат. Irina Petrovna Lebedeva». Разница ровно в записи: «Н.П.Ю.» стоит последним словом строки,
«Т.С.» — в связке с полным написанием. Клиент rag-046 читает своё настоящее ФИО и инициалы
другого человека; ни одна из 13 метрик этого не видит (`form OUT/answer` сравнивает `produced`
с подменой, а инициалы в `produced` просто отсутствуют как отдельное значение).

## Диагностические гипотезы

Каждая — правило или механизм движка, а не подкрутка кейса; каждая убивает целый класс,
а не одну строку.

**G1. Телефонный прогон должен принадлежать телефону целиком, вместе с «+» и транковым «8».**
Механизм: (а) при пересечении спан-кандидатов проверять, не покрывает ли телефонный распознаватель
тот же прогон с префиксом, и отдавать прогон телефону, если он валиден по libphonenumber
(контрольная сумма СНИЛС остаётся сильнее там, где телефонного чтения нет);
(б) границу спана тянуть до «+»/ведущей «8», чтобы длина совпадала с объявленным местом значения.
Убивает P4 целиком: `form OUT/tool_arg` у rag-008, `coverage` 3/4 и странные подмены `+45…`/`+95…`,
а заодно снимает `_ECHO_*`-путаницу при переотправке (P5 в части телефонов).
Проверка: 4 упоминания в группе, 3 кейса; на полном прогоне — все телефоны с 11-значным прогоном,
проходящим mod 101, доля ≈1/101.

**G2. Подмена продиктованного идентификатора обязана быть либо разложимой, либо помеченной как неразложимая.**
Сегодня слово-прогон не несёт частей вообще, и разложенный агентом лист (`passport.series` = «0020»)
не опознаётся как наш, хотя восстановление сработало. Механизм: у мятного токена должна быть
КАРТА ЧАСТЕЙ и для словесной поверхности (прогон слов ↔ позиции цифр известны в момент минта:
`spoken.run_to_digits` их уже считает), а не только для цифровой; тогда `leaf_holds` отвечает
на вопрос «этот лист несёт мою часть» в обоих регистрах. Заодно это даёт движку возможность
проверять частичный перенос (модель написала `series` верно, `number` — нет), чего сейчас нет.
Убивает P3а и половину P3б.

**G3. Эхо уже восстановленного значения перемаскируется СВОЕЙ подменой, а не новой.**
Механизм: на ноге переотправки транскрипта искать значение в волте по настоящему ключу (он там есть:
инструмент получил настоящее значение именно потому, что волт его знает) и подставлять ИСХОДНУЮ
подмену; `REDACTED<6hex>` оставить только для случая, когда значение волту неизвестно вовсе
(пришло из результата инструмента, не из сообщения). Убивает P5: 8 кейсов группы, `REDACTED…`
в `cardholder`, `+9551910737` вместо `+7954504235`, и саму причину петли `turns=102`.
Это же чинит `consistency`-семейство: сейчас один человек за диалог получает два разных имени.
Родственный на той же ноге: производная форма обязана переворачиваться и в ответе — сжатые инициалы
подмены не должны доживать до клиента рядом с настоящим ФИО (P10, rag-046 против rag-034).

**G4. Объявление кейса не должно требовать хоп, к которому сам кейс не ведёт агента.**
Механизм: при сборке корпуса разрешать `required` OUT/tool_arg хоп на лист только если
(а) этот лист не альтернативен другому листу той же сущности в описании инструмента
(`card.cardholder` против `payer_bank_details.full_name`) и (б) системный промпт кейса или
текст задачи требует переноса значения именно туда. Иначе — `optional=True`.
Убивает P1 (30 кейсов) и P2 (7 кейсов) = 44 из 56 промахов `end_to_end` группы.
Без этого никакая работа над движком не сдвинет `end_to_end`, потому что знаменатель наполовину
состоит из того, чего агент делать не обязан.

**G5. Безродовая улица должна рождаться из адресного словаря и в адъективной форме.**
Механизм: маркер-less путь сейчас требует либо родового слова, либо морфологического согласования;
нужен отдельный проход «одно слово в форме прилагательного/притяжательного, присутствующее в ГАР
как стрит-стем, в пределах N символов от адресной подсказки (`по адресу`, `ул.`, `проживает`)» —
и он должен отдавать ADDR, а не NAME, потому что подмена фамилией (`бабаян` вместо `шумайлова`)
на улице выглядит правдоподобно, но тип неверен. Свидетели: 20 кейсов rag, улица ЧУЖОГО клиента.
Отдельно: `returns.result_item_ids` без хопа — дыра в инструменте, значение, объявленное возвращённым,
обязано попадать хотя бы в `toolresult_masked`, иначе 20 утечек не видит ни одна из 13 метрик.

**G6. Три разных «не защищено» должны печататься тремя разными клетками.**
Сейчас одно слово `unmasked` означает «агент листа не заполнил» (14 хопов), «агент заполнил его
другим значением» (3 хопа) и «движок сам решил не трогать» (2 хопа `address.locality`).
Механизм: разложить `_out_status` на `leaf_empty` / `leaf_foreign` / `engine_kept` — первые две
принадлежат агенту, третья движку, и `end_to_end` должен считать промахом только третью и вторую.
Там же — вторая половина G6: `coverage` не должна считать куском настоящего значения слово,
которое в этом же тексте стоит как ПОДМЕНА ДРУГОГО объявленного элемента (три ложных свидетеля
P7а: Ольга/Лебедев/Зинаида). Без этого «−1% на coverage/leak» будет чиниться не там, где болит.

**G7. Латиница против латиницы — не расхождение письменности.** 50 из 60 form-промахов группы —
это ровно `OUT/answer NAME ('script',)`, и почти все они латиница против латиницы
(`'Bukin'` = `latin:unknown` против `'Yudin'` = `latin:bgn`; `'DMITRIY KUZNETSOV'` = `latin:bgn`
против `'EGOR BOBROV'` = `latin:unknown`). Механизм: у признака `script` должно быть два значения
для букв — `cyrillic` / `latin`, а вопрос «какой системой романизации» должен стать ОТДЕЛЬНЫМ
признаком, который воздерживается (`no opinion`), когда хотя бы одна сторона `latin:unknown`.
Это тот же урок, который инструмент уже выучил на оси значений («A BENCHMARK'S OWN CONVENTION
IS A FOURTH CONVENTION»), но на оси формы он ещё не применён. Цена бездействия измерена:
`form OUT/answer` 569/631, и 50 промахов из 62 — этот класс, при полностью верной оси значений.
Двигает `form_hOUT` группы с 84.9% к ~91% одним правилом.
