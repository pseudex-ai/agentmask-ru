# Подмены с валидной контрольной суммой из диапазонов, невозможных для человека

**Вопрос.** Модель, которой системный промпт велит проверять контрольные суммы,
отвергает подмену с невалидной суммой и не вызывает инструмент (v4 small:
16 из 36 троек семейства `validate`). Продукт чеканит невалидные суммы
намеренно — чтобы подмена никогда не была чьим-то настоящим номером. Оба
требования законны. Есть ли для каждого типа диапазон, который проходит КАЖДУЮ
проверку агента и API и при этом не может принадлежать человеку?

**Ответ коротко.** Для ИНН, паспорта и карты — да, по структуре номера; для
СНИЛС — нет, и это надо принять и записать, а не обойти.

---

## СНИЛС — безопасного валидного диапазона НЕТ

Алгоритм (ПФР, воспроизведён на странице ТФОМС Ростовской области и в статье
«Контрольное число»): каждая из девяти цифр умножается на номер позиции с
конца, сумма делится на 101; при сумме < 100 контрольное число равно сумме,
при 100 и 101 — «00», при > 101 — остаток по тем же правилам. И ключевая
оговорка: **«проверка контрольного числа проводится только для номеров больше
номера 001-001-998»** [B].

Первая версия плана читала это как «номера ниже 001-001-998 не присваиваются».
Это неверно: оговорка существует потому, что эти номера БЫЛИ присвоены ДО
введения алгоритма — самым ранним застрахованным — и у них контрольное число
не сходится. То есть это не резерв, а живые люди, и подмена из этого диапазона
с валидной суммой всё равно совпала бы с реальным номером (или, что хуже,
валидатор без оговорки её отвергнет, а с оговоркой — примет любую).

Пространство валидных СНИЛС ≈ 10⁹ при ~1.5·10⁸ выданных: случайная валидная
подмена — чей-то настоящий номер примерно в одном случае из семи. Никакого
структурного поля (регион, год) в СНИЛС нет — резервировать нечего.

**Решение (03.09):** СНИЛС остаётся с невалидной суммой. Цена измерена: агент,
проверяющий СНИЛС, откажется вызывать инструмент.

**Пересмотр (04.09).** Цена оказалась весь остаток семейства `validate` (12 из
24 троек третьего живого прогона). Довод «случайная валидная подмена — чей-то
настоящий номер в одном случае из семи» верен для ВСЕЙ страны, но подмена
живёт в одной беседе: настоящий носитель того же номера, войдя в ДРУГУЮ беседу,
не принимается за нашу подмену (`tokens.minted_in`), а в ту же беседу не
входит с вероятностью, которой нет. Это тот же довод, на котором стоят фейковые
имена (каждое — настоящее имя) и фейковые улицы. Обратное направление —
подмена, равная значению, которое у клиента уже есть, — отвергается
`_unique_token`. Поэтому СНИЛС чеканится ВАЛИДНЫМ, никогда ≤ 001-001-998.

## ИНН физлица — регион «00»

Структура 12-значного ИНН: цифры 1–2 — код региона постановки на учёт, 3–4 —
номер инспекции, 5–10 — порядковый номер, 11–12 — контрольные [C]. Веса:
n1 = (7,2,4,10,3,5,9,4,6,8), n2 = (3,7,2,4,10,3,5,9,4,6,8); остаток 10 → 0 [A].
Коды регионов ФНС — 01–92 плюс 99 для межрегиональных инспекций; кода «00»
не существует.

**Решение:** ИНН чеканится с регионом «00» (первые две цифры) и валидными
контрольными. Агент, проверяющий веса, принимает; ФНС-API, проверяющий код
инспекции, — нет, но такой проверки у агента нет, а в нашем моке — только веса.
Коллизия с человеком невозможна по структуре.

## Паспорт РФ — серия с регионом «00»

Серия XX XX: первые две цифры — код ОКАТО региона выдачи, вторые две —
последние две цифры года выпуска бланка (допустимо отклонение на 1–3 года);
источник — Положение о паспорте гражданина РФ (постановление Правительства
№ 828 от 08.07.1997, с 2023 — № 2267) [D]. Кода ОКАТО «00» не существует.

**Решение:** серия «00YY», где YY — правдоподобный год (1997–2026), номер —
шесть случайных цифр. Проверка формата (4+6) проходит; регион у агента не
проверяется; человек с такой серией невозможен.

## Банковская карта — MII «0»

ISO/IEC 7812: PAN = IIN (первая цифра — Major Industry Identifier) + номер
счёта + контрольная цифра по Луну [E]. Диапазоны эмитентов: Visa — 4,
Mastercard — 51–55 и 2221–2720, «Мир» — 2200–2204. MII «0» зарезервирован за
ISO/TC 68 и другими отраслевыми назначениями, MII «1» — авиакомпании, «7» —
нефтяные компании; ни один банк карту с таким первым знаком не выпускает.
Публичные «тестовые» номера (4111 1111 1111 1111 и подобные) намеренно НЕ
используются: модель узнаёт их как тестовые и ведёт себя иначе.

**Решение:** карта чеканится с первой цифрой «0» и валидной цифрой Луна. Луна
проходит; агент, требующий «начинается с 2/4/5», отвергнет — это измеримо и
редко; платёжный API отвергнет неизвестный BIN, но до API подмена не доходит —
инструмент получает настоящий номер.

## Расчётный счёт и БИК — вне задачи

Ключ счёта: письмо ЦБ РФ от 08.09.1997 № 515 — к 20 цифрам счёта
приписываются три последние цифры БИК, веса 7-1-3 циклически, ключ = младший
разряд от (сумма mod 10) × 3 [F]. БИК: «04» + код региона по ОКАТО + код
подразделения ЦБ + номер банка; «00» в регионе означает подразделение за
пределами страны и НЕ является невозможным [G]. Реквизиты юрлица не
персональные данные (Recital 14 / 152-ФЗ ст. 3), волт их не подменяет —
задача не стоит.

## Что меняется в движке

* `vault.py`: генераторы ИНН, паспорта и карты — валидная сумма + невозможный
  диапазон; СНИЛС — как прежде. `_unique_token` (backwards) и `minted_in`
  (forwards) — без изменений.
* `test_product.test_tokens_are_not_valid_documents` переименовывается по
  смыслу: подмена ИНН/паспорта/карты валидна по сумме И структурно невозможна;
  подмена СНИЛС невалидна по сумме.
* v4 `validate` скриптовым агентом с политикой `validator`: отказов по ИНН и
  карте быть не должно; по СНИЛС — остаются и считаются.
